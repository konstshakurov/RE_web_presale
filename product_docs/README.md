# product_docs — живая документация re_web_presale

Статус: метод принят к применению 26.10.2026 (решение за владельцем — Константин; см. «Что утверждается»).
Назначение: ОДНО место, где видно, **как продукт устроен сейчас** — по бизнес-функциям, системным
компонентам и архитектуре — с трассировкой к требованиям BABOK, задачам Linear, коду и тестам.

## Зачем это нужно (проблема на 26.10)

| Что сейчас | Чем мешает |
|---|---|
| `output/reports/` — 100+ файлов-«событий» BABOK по времени (`5_2_requirement_update_*` ×22, 5 `coverage_check`…) | это журнал процесса, а не описание продукта: ответ на «как сейчас работает назначение?» требует сборки из 10+ файлов |
| `output/data/.../specs/` — 77 требований по типам (fr_/nfr_/br_/uc_), не по функциям | нет «шапки функции», не видно, что относится к одной функции |
| `architecture/` — C4, ADR, пробы, отчёты | отдельная вселенная, на требования ссылается только текстом |
| утверждённые требования отстают от кода (FR-025 `v1.0` до сих пор «OAuth 1.0a», в коде — сессионная cookie) | документация врёт; изменения жили в пробах и CR, а не в спецификации |

## Принятое решение

**Два слоя + одно правило. Новый `project_id` и папку `re_web_presale_v2` не заводим.**

```
СЛОЙ 1 — ЖУРНАЛ (как было, не трогаем)          СЛОЙ 2 — ЖИВАЯ ДОКУМЕНТАЦИЯ (product_docs/)
output/data/<pid>/…  JSON + specs/ (MCP)         «как устроено сейчас», по функциям и компонентам
output/reports/<pid>/… события BABOK 3–7         ссылается на ID требований, а не копирует текст
  → неизменяемая история, аудит, граф 5.1          → точка входа для человека и агентов
```

1. **Слой 1 (`output/`) остаётся единственным источником текста требований и графа трассировки.**
   Все MCP-инструменты и скиллы Бабока пишут туда как раньше. Требование живёт ровно в одном месте
   (`specs/fr_0xx_…md`, правится через 5.2 `update_requirement` / CR 5.4) — копий нет.
2. **Слой 2 (`product_docs/`) — это «паспорта» и описания «как реализовано»**: карточка бизнес-функции,
   страницы системных компонентов, ссылки на дизайн (`design/KON-N`) и архитектуру (`architecture/`).
   Он не дублирует формулировки FR, а указывает на них и фиксирует расхождения.
3. **Правило актуальности (Definition of Done любой фичи/CR):** задача не Done, пока обновлены
   (а) требование в слое 1 через CR/5.2, (б) карточка БФ и страница компонента в слое 2,
   (в) строка в `INDEX.md`, (г) `python product_docs/check_product_docs.py` без ошибок. Это пункт чек-листа в Linear-задаче.

**Почему не `output/reports/re_web_presale_v2`:** `project_id` — ключ графа трассировки и бейзлайна 5.5;
второй идентификатор разорвёт связи MVP ↔ этап 2, а MCP-инструменты откажутся видеть требования v1.
Этап 2 — это **релиз внутри того же проекта**: метка `Версия 2` в Linear (уже есть), поле «Релиз»
в карточке БФ, новый бейзлайн v2.0 через 5.5 после первого пакета этапа 2.

**Почему не «каждая глава Бабока = новые MD в `output/` через CR» (вариант а):** работает, но
`output/` и дальше растёт линейно по числу событий (за 3 недели MVP — 100+ файлов), и понять
текущее состояние можно только пересборкой. Журнал нужен (аудит BABOK), а читать его как
документацию — нельзя. Поэтому журнал сохраняем, а «читаемую поверхность» выносим в слой 2.

## Что взято из примеров (скрины 1 и 2)

| Идея из примера | Как применено |
|---|---|
| Единица документации — **бизнес-функция** с «шапкой» (скрин 1), в ней BR / ФТ / UI / UC | `01_business_functions/BF-NN_*/README.md` — шапка со ссылками на BR/FR/NFR/UC (слой 1) и UI (`design/`) |
| **Запросы на изменения — отдельные документы**, после внедрения БФ актуализируется (новая версия), запрос хранится для истории (скрин 1) | CR-NNN остаются в `output/` (5.4); в карточке БФ — таблица «История изменений» со ссылкой на CR и версией БФ |
| **Системные компоненты отдельно от бизнес-функций** и связаны ссылками в обе стороны (скрин 2: продуктовое пространство ↔ System Components ↔ ИТ-архитектура) | `02_system_components/<компонент>/` ↔ карточка БФ; архитектура остаётся в `architecture/` (C1/C2/ADR), страницы компонентов ссылаются на неё как на «C3-решение» |
| **Префиксы и шаблоны страниц**: SRV, DB, API, FLV, MON, PROC (sequence), ERR | те же префиксы в именах файлов; шаблоны — `_templates/` |
| Технические решения C3: ERD, UML Sequence, API, таблицы маппинга, потоки данных | `API_*`, `SEQ_*`, `MAP_*`, `FLV_*` внутри папки компонента; диаграммы регистрируются в графе 5.1 (`COMP-SEQ-*`, `COMP-API-*`) |

Чего **не** берём: многоуровневую иерархию доменов LSNext/Kafka stream catalog — у нас один продукт, одна БФ-сетка, один набор компонентов; лишние уровни сделали бы навигацию тяжелее.

## Рендер диаграмм

Исходники диаграмм — `.puml` (проверка правил: `skills/analyst_uml_sequence_getanalyst/scripts/validate_sequence.py`). Отрисовка в SVG — официальным образом PlantUML в Docker, ничего не устанавливая в систему:

```bash
bash product_docs/render_diagrams.sh                 # все product_docs/**/seq/*.puml
bash product_docs/render_diagrams.sh путь/к/файлу.puml
```

SVG кладётся рядом с `.puml` и коммитится; скрипт завершается с ошибкой, если PlantUML нашёл синтаксическую ошибку. Публичный сервер plantuml.com не использовать: имена систем и полей не должны уходить наружу.

## Проверка актуальности

```bash
python product_docs/check_product_docs.py          # проверка
python product_docs/check_product_docs.py --fix    # обновить таблицы требований в карточках из графа 5.1
```

Скрипт (только стандартная библиотека) сверяет карточки БФ и `INDEX.md` с графом 5.1 и файлами. **Ошибки** (код возврата 1): ID нет в графе, версия/статус в карточке не совпадают с графом, битые ссылки, БФ есть в INDEX без карточки или наоборот, `planned` без «Планируемого изменения», неизвестный статус. **Предупреждения**: требование не покрыто ни одной БФ, требования в `under_change`, компонент без БФ, БФ `implemented` без компонента, `.puml` без свежего `.svg`. Запускать перед закрытием любой задачи, которая меняет требования или поведение (DoD «слой 2 обновлён»), и после каждого пакета 5.5.

## Структура

```
product_docs/
  README.md                метод и правила (этот файл)
  INDEX.md                 реестр: БФ ↔ требования ↔ компоненты ↔ задачи ↔ релиз; расхождения
  _templates/              bf_card.md, component_page.md
  01_business_functions/   BF-NN_<имя>/README.md  — шапка бизнес-функции
  02_system_components/    <компонент>/            — SRV/API/SEQ/MAP/FLV/ERR
     jira_integration/     ← полностью описан: SRV, API ×2, SEQ ×6, MAP, FLV
     app_db/, cv_db/       ← SRV + MAP_tables + ERD (модель данных)
     auth/, llm_gateway/   ← обзорные паспорта
  (ссылки)  architecture/  — C1/C2, ADR, нагрузка, развёртывание (пишет Arch / архитектор)
  (ссылки)  design/        — решения UX (пишет UX)
  (ссылки)  output/        — слой 1: журнал и требования BABOK (пишут MCP/аналитик)
```

## Порядок работы по Бабоку для новой фичи этапа 2 (не меняется)

3 план → 4.1–4.5 выявление → 7.1 спецификация (FR/UC/BR в слое 1) → 7.2/7.3 верификация и
валидация → 5.1 трассировка (включая `COMP-*`) → 5.3 приоритет → 5.4 CR (если меняется утверждённое) →
5.5 бейзлайн v2.0. **Добавляется один финальный шаг: «синхронизировать product_docs»** (БФ-карточка,
компонент, INDEX). Фича = новая БФ или новая версия существующей; CR → строка в «Истории изменений».

## Где хранится ERD и модель данных

| Что | Слой | Где |
|---|---|---|
| Логическая ERD и словарь данных (ERD-001, DD-001) — требования | 1 | `output/data/<pid>/specs/erd_*`; в карточках БФ — ссылка |
| Физическая модель, ER-диаграмма, таблицы, DDL — техническое решение | 2 | `02_system_components/app_db/` и `cv_db/`: `README.md` (SRV, миграции), `MAP_tables.md`, `ERD_*.md` (Mermaid) |
| Первоисточник схемы | код | `db/migrations/` — страница объясняет, не дублирует DDL |

Файл `output/reports/…/db_physical_model_KON-29.md` остаётся в журнале как запись о задаче (он отражает состояние до V007/V008); правится и актуализируется страница компонента. Правило общее: **результат проектирования (ERD, API, sequence) живёт на странице компонента; журнал хранит факт, что работа выполнена.**

## Жизненный цикл страниц и карточек: `planned` → `implemented`

| Статус | Смысл | Кто ставит |
|---|---|---|
| `planned` | целевое состояние: требования утверждены (5.5), решение описано, реализации ещё нет | аналитик — карточка БФ; Arch — «целевые» страницы компонентов (контракты, диаграммы) |
| `in_dev` | задачи в работе | Arch/TL при декомпозиции |
| `implemented` | реализовано, принято QA, страницы приведены к факту | аналитик (после DoD), по сигналу Dev/QA |

В карточке БФ для `planned` обязателен раздел **«Планируемое изменение»**: что добавляется и что меняется (по ID требований), какие компоненты и контракты затрагиваются, ссылка на `design/` (если есть UI), открытые вопросы. Страница компонента со статусом `planned` помечается в заголовке; текущее состояние и целевое на одной странице разделяются подзаголовками «Сейчас» / «Планируется».

## Сценарий новой бизнес-функции

Вход для Arch (агента или человека) и Dev — **два источника**, а не «только product_docs»:
1. утверждённые требования-дельта в слое 1 (5.4/5.5, бейзлайн v2.0) — что менять;
2. карточка БФ, страницы компонентов, `architecture/`, код — где менять и что уже есть.

Задача в Linear ссылается на `BF-NN`, ID требований и страницы компонентов, а не на файлы `output/reports/`.

```
Аналитик (Бабок: требования в output/, 5.5)
  → карточка БФ: planned + версия + «Планируемое изменение»
  → сигнал готовности
  → Arch / архитектор-человек: декомпозиция в Linear; целевые страницы (planned); ADR
  → UX → апрув владельца (если UI)
  → Dev → QA
  → страницы implemented, INDEX обновлён (DoD)
```

**Ворота для Arch:** задача не берётся в работу без карточки БФ `planned` с утверждёнными требованиями; Arch называет причину и возвращает задачу аналитику (по аналогии с воротами UI: Dev не стартует без `decision.md` `approved`).

## Передача между ролями (агент или человек)

Порядок одинаков, кто бы ни принимал работу. Если архитектор или TL — живой человек, а Dev/QA — агенты, функции Arch (в том числе декомпозицию в Linear) выполняет человек.

**Сигнал готовности аналитики — формальный** (сообщения в чате недостаточно: оно не оставляет следа для агентов и других ролей). Он состоит из трёх признаков:
1. карточка БФ в статусе `planned` с версией и разделом «Планируемое изменение»;
2. бейзлайн v2.0 утверждён по 5.5 (ссылка на пакет утверждения);
3. комментарий или задача в Linear: «аналитика по BF-NN завершена» со ссылками на карточку и пакет.

**Один писатель на область:**

| Область | Пишет |
|---|---|
| `output/` (требования, граф 5.1), `01_business_functions/` | только аналитик |
| `02_system_components/` — страницы, API/SEQ/MAP/FLV «как есть» | аналитик |
| блок «Архитектурное решение» страниц компонентов, `architecture/` | Arch / архитектор |
| `design/` | UX |
| код и тесты | Dev / QA / DevOps |

Пробел или противоречие в требованиях архитектор не правит сам — заводит Issue или CR (5.4) аналитику. Замечания к карточке — комментарием в Linear; аналитик отвечает 5.2 или CR и меняет версию карточки. Решения, меняющие скоуп или срок, принимает владелец.

Доступ живому архитектору: чтение `product_docs/`, `output/`, `design/`; запись — `architecture/` и блок «Архитектурное решение». Разграничение держится правилом (таблица выше); механизм `CODEOWNERS` по папкам пока не используется — включается, если у проекта появится живой архитектор и работа через pull request.

## Что утверждается владельцем

1. Принять модель «два слоя» и каталог `product_docs/` (альтернатива — всё в `output/reports/<pid>/living/`; функционально то же, но смешивается с журналом).
2. Принять первичную нарезку БФ из `INDEX.md` (её предложил аналитик по 40 FR; правится дешево, пока карточек мало).
3. Принять DoD «слой 2 обновлён» как обязательный пункт задач этапа 2.
4. Принять статусы `planned` / `implemented`, ворота для Arch и порядок передачи между ролями (см. выше).
