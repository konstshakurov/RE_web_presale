# Нормочасы аналитики на продуктовом проекте (ПП)

**Происхождение:** методика разработана в проекте `Estimate_re_pp` (2026) —
изучение шаблонов артефактов СимбирСофт, опрос 40 ИТ-специалистов о нужности
и детализации артефактов на продуктовых проектах, критерии Блоков A/B/C
(`estimation_criteria_pp.md`), базовые ставки для аналогии —
`normo_hours_catalog.md`. Подробности исследования и ход разработки — в
`projects/Estimate_re_pp/output/` (`artifact_inventory.md`,
`survey_results_analysis.md`, `normo_hours_pp_draft.md`).

**Чем отличается от `normo_hours_catalog.md`:** тот каталог рассчитан на
максимально подробную аналитику (25+ позиций, ставки калиброваны компанией
под этот сценарий). Здесь состав артефактов сужен по данным реального опроса
потребителей, детализация — по факту того, что команды **реально
используют**, а часовые ставки — по независимой LLM-экспертизе объёма работы
для лёгкого продуктового/agile-процесса (не унаследованы напрямую от
«тяжёлой» шкалы каталога, хотя и выведены из неё пропорционально).

---

## 0. Статус шкалы: стартовая, подлежит калибровке

**Часовая шкала раздела 3 — стартовая, не проверенная эмпирически.** Она
получена LLM-экспертизой (не измерениями на реальных проектах СимбирСофт) и
должна использоваться с этим статусом до первой калибровки.

**Условие калибровки:** после того как по этой методике будут оценены и
проведены **2–3 реальных продуктовых проекта**, плановые часы по каждому
артефакту сравниваются с фактически потраченными, и ставки раздела 3
корректируются по факту.

**До калибровки — любая оценка по этой методике должна сопровождаться
пометкой «оценка по стартовой, не откалиброванной шкале» в отчёте BA.**

---

## 1. Правило выбора уровня: детализация → сложность

Детализация артефакта описывается 4 градациями (Не нужен / Краткая / Средняя
/ Подробная). Часовая шкала (раздел 3) задана по тем же 3 уровням сложности
1/2/3, что и `normo_hours_catalog.md`. Сопоставление:

| Детализация | Уровень сложности (расчёт часов) |
|---|---|
| Краткая | 1 (простой) |
| Средняя | 2 (средний) |
| Подробная | 3 (сложный) |

**Правило выбора уровня по умолчанию:** берётся дефолт-уровень из таблиц
раздела 3 (выведен как мода ответов опроса на момент разработки методики).
**Экономное правило при близком разрыве голосов опроса:** если мода
опережала следующий по популярности вариант менее чем на 10 п.п. и этот
сосед — более дешёвый уровень, дефолт взят по более дешёвому уровню
(конкурентоспособность КП по стоимости — приоритетнее).

**Важно:** это дефолт для *базовой детализации текста*, не для объективной
сложности объекта (число ролей, ветвлений и т.д.) — если сама система
объективно сложнее (см. критерии 1/2/3 в `normo_hours_catalog.md` для
соответствующего пункта), финальное решение по уровню — за BA, дефолт не
должен маскировать реальную сложность. Критерии Блоков A/B/C
(`estimation_criteria_pp.md`) могут скорректировать уровень для конкретного
артефакта (например, Блок C1 — управленческая аудитория — поднимает уровень
у ТЗ и «Бизнес-целей»).

### 3.2 Новые позиции (также добавлены в `normo_hours_catalog.md` как 2.8, 2.9, 4.9, 4.10 — с полной, не дисконтированной шкалой)

| Артефакт | Ед. измерения | Пункт каталога | Дефолт-уровень | **Итоговая ставка** |
|---|---|---|---|---|
| Статусная модель | 1 модель (объект) | 4.9 | 1 (Краткая) | **2 ч./ед.** |
| NoSQL БД | 1 сущность/коллекция | 4.10 | 1 (Краткая) | **3 ч./ед.** |
| Бизнес-цели | документ (фикс.) | 2.8 | 1 (Краткая) | **2 ч.** |
| ТЗ — компоновка (сборка документа) | документ (фикс.) | 2.9 | 3 (Подробная; усиливается Блоком C при управленческой аудитории) | **8 ч.** |

**Важно про ТЗ:** «ТЗ — компоновка» не включает содержимое разделов ТЗ
(бизнес-процессы, роли, ФТ, сущности, интеграции) — они считаются отдельными
строками в 3.1/3.2. Эта строка — только сборка, введение, термины,
форматирование готового документа.

### 3.3 Руководства — ситуативные (5.1 каталога, ставка пересчитана на продуктовый объём)

Включение зависит от архитектуры продукта, не от опроса (данных по этим трём
артефактам нет — см. п. 4 ниже):

| Артефакт | **Итоговая ставка** | Включать, если |
|---|---|---|
| Руководство пользователя | **18 ч.** | есть интерфейс конечного пользователя |
| Руководство администратора | **17 ч.** | есть админ-панель/бэкофис |
| Руководство по развёртыванию | **18 ч.** | self-hosted / on-prem развёртывание (не нужно для чистого SaaS без доступа клиента к инфраструктуре) |

### 3.4 Исключено по умолчанию

**Конкурентный анализ / SWOT** — не включается в типовую продуктовую оценку.
Это pre-sale-активность, а не задача аналитика на проекте — включать только
по прямому запросу (например, отдельная услуга «исследование рынка»).

## 4. Известное ограничение методики

По трём «Руководствам» (3.3) нет данных о нужности/детализации — они выпали
из финальной анкеты при разработке методики (детали —
`projects/Estimate_re_pp/output/survey_results_analysis.md`). Ставки 3.3
получены применением того же типового понижающего коэффициента, что и для
артефактов с данными, а не по собственным замерам — при калибровке (раздел 0)
обратить на них особое внимание в первую очередь.

## 5. Иллюстративный пример (не реальная оценка, только для проверки методики)

Гипотетический малый продукт: 8 ФТ-совокупностей, 5 ролей, 3 US, 2 сущности
реляционной БД, 2 REST-интеграции, есть админ-панель, нет брокера сообщений
и NoSQL, ТЗ нужен управленцам (Блок C1 = да → детализация ТЗ на максимум,
уже дефолт).

| Артефакт | Кол-во | Ставка | Часы |
|---|---|---|---|
| ФТ | 8 | 5 ч. | 40 |
| ТЗ — компоновка | 1 | 8 ч. | 8 |
| REST/SOAP | 2 | 6 ч. | 12 |
| Роли (база + 4 доп.) | 5 | 2 ч. + 4×1 ч. | 6 |
| Бизнес-цели | 1 | 2 ч. | 2 |
| User Story | 3 | 1,5 ч. | 4,5 |
| НФТ | 30% от ФТ (мин. граница) | 30% × 40 | 12 |
| Сущности / БД | 2 | 2,5 ч. | 5 |
| Руководство администратора | 1 | 17 ч. | 17 |
| **Итого (минимальная оценка, от)** | | | **≈106,5 ч.** |

Для сравнения: тот же состав по полному каталогу СимбирСофт (уровень 3
везде, все пункты, включая Карту экранов и Прототипы) дал бы существенно
больше — методика продуктового проекта компактна за счёт трёх факторов
сразу: (а) более узкий состав артефактов, (б) более низкий дефолт-уровень
детализации, (в) собственная более экономная часовая шкала (раздел 0).
