# Критерии для запроса у пользователя перед оценкой продуктового проекта (ПП)

**Назначение:** минимальный набор вопросов, которые аналитик (или платформа)
задаёт руководителю/заказчику **в начале каждой новой оценки** продуктового
проекта — до того, как определять состав артефактов, детализацию и
сложность. Это конкретизация Шага 1 «Вид оценки и границы» из `SKILL.md` на
ветке ПП — короче, чем границы полной методики, с приоритетом на
бизнес-критерии.

**Принцип:** сначала блок A (бизнес-ограничения) — он важнее всего, так как
главное ограничение продуктового проекта обычно — конкурентоспособность КП по
срокам/стоимости. Блоки B и C уточняют состав артефактов и их детализацию, но
не должны противоречить решению, принятому в блоке A.

**Происхождение:** критерии и данные Блока B/C выведены по итогам проекта
`Estimate_re_pp` (2026) — опрос 40 ИТ-специалистов СимбирСофт о нужности и
детализации артефактов на продуктовых проектах, см.
`projects/Estimate_re_pp/output/survey_results_analysis.md` (историческое
исследование, не обязательная зависимость для использования этого файла).

## Блок A — Бизнес-ограничения (спрашивать первыми, всегда)

| № | Критерий | Как влияет на оценку |
|---|---|---|
| A1 | Это оценка для **коммерческого предложения** (конкурс с конкурентами) или **внутренняя оценка** уже подтверждённого проекта? | КП → держим нижнюю границу нормочасов и минимальный достаточный набор артефактов (см. Блок B/C), буфер риска не закладываем в базовую цифру. Внутренняя оценка → можно закладывать больше запаса под специфику проекта. |
| A2 | Есть ли **фиксированный срок** (дедлайн) на этап аналитики? Если да — сколько недель/часов? | Если расчётный минимум превышает срок — в первую очередь урезается детализация ситуативных артефактов (Блок C ниже) до «Краткая», затем исключаются необязательные пункты. Урезание всегда фиксируется как допущение в отчёте. |
| A3 | Есть ли **фиксированный бюджет** (потолок часов/денег) на этап аналитики? Если бюджет назван **в деньгах**, а не в часах — дополнительно уточнить **среднюю ставку аналитика (руб./час)**, чтобы перевести бюджет в часы. | Аналогично A2 — сжимаем объём под потолок, явно перечисляем в отчёте, что именно урезано и какой ценой (риск). Бюджет в деньгах переводится в часы по формуле `часы = бюджет ÷ ставка` — полученное значение используется как ограничение по часам наравне со сроком из A2; если пересчитанные из бюджета часы и срок из A2 расходятся — явно зафиксировать это расхождение в допущениях отчёта. |
| A4 | Документация будет вестись **AI-агентом**, **аналитиком-человеком** или гибридно (AI-черновик + проверка человеком)? | AI-агент допускает более быстрый черновой проход по типовым артефактам (User Story, ролевая модель, статусная модель) — нормочасы на первичную генерацию можно снижать, но **не на валидацию** (её всегда делает человек). Указывать в отчёте отдельной строкой, какие пункты предполагают AI-черновик. |

## Блок B — Архитектурный и продуктовый контекст (определяет состав ситуативных артефактов)

Эти артефакты востребованы не всегда, а по ситуации — решение зависит от
конкретной архитектуры продукта:

| № | Критерий | Если ДА | Если НЕТ |
|---|---|---|---|
| B1 | Есть ли в архитектуре продукта **асинхронные интеграции / брокер сообщений** (Kafka, RabbitMQ и т.п.)? | Включить «Асинхронная интеграция» | Исключить полностью |
| B2 | Используется ли в стеке **NoSQL БД** (документная/key-value)? | Включить «NoSQL БД» | Исключить, оставить только реляционные «Сущности / БД» |
| B3 | Проект — **разработка с нуля** или **доработка/развитие** существующей системы? | Доработка → добавить экспертную оценку по аналогии с Этапом 0 `normo_hours_catalog.md` (приёмка/анализ существующей системы) — этого пункта нет в базовом наборе продуктовых артефактов | С нуля → Этап 0 не нужен |
| B4 | Сколько **внешних систем интеграции** (REST/SOAP) предполагается? (число, не да/нет — этот артефакт нужен почти всегда) | Число используется как количество единиц для расчёта (по аналогии с 4.6/4.7 «оценка на 1 метод») | — |
| B5 | Нужна ли **статусная модель** — есть ли в продукте объекты со сложным жизненным циклом (статусы, переходы)? | Включить «Статусная модель» | Исключить, статусы описываются внутри функциональных требований |

## Блок C — Организационный контекст / аудитория документации

| № | Критерий | Как влияет на оценку |
|---|---|---|
| C1 | Кто основные потребители документации — **только команда разработки**, или есть **управленцы/presale/заказчик**, которым нужен формальный ТЗ и обоснование бизнес-целей? | Разработчикам чаще достаточно детализации «Средняя», управленцам и заказчику обычно нужна «Подробная» для ТЗ и пункта «Бизнес-цели». Наличие управленческой аудитории — довод поднять детализацию именно этих двух артефактов, даже если остальное держим кратким. |
| C2 | Нужно ли **формальное согласование ТЗ с заказчиком** (презентация, подписание)? | Да → добавить экспертную оценку по аналогии с Этапом 3 `normo_hours_catalog.md` (презентация + согласование ТЗ). Нет → исключить, прямая экономия нормочасов. |

## Как это используется в оценке (порядок применения)

1. Спросить Блок A целиком — он определяет общий «бюджет консервативности»
   оценки (по нижней границе / с запасом) и задаёт целевой потолок часов,
   если он есть.
2. Пройти Блок B пункт за пунктом — каждый ответ включает или исключает один
   ситуативный артефакт из состава (Конкурентный анализ / SWOT исключён по
   умолчанию всегда, отдельно переспрашивать не нужно, только если
   пользователь сам запросит pre-sale-активность).
3. Блок C — точечная коррекция уровня детализации у ТЗ и «Бизнес-целей» (и
   любых артефактов, если явно есть управленческая аудитория).
4. Результат прохождения Блока A–C — это входные данные для расчёта по
   `normo_hours_pp.md`: конкретный список артефактов + целевой уровень
   детализации по каждому, с которым уже считаются часы.
