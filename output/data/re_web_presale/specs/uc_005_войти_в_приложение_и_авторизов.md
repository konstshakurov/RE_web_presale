## Общая информация

| Атрибут | Значение |
|---------|----------|
| Актор (primary) | РН / РО / Presale-менеджер |
| Акторы (secondary) | LDAP, Jira |
| Предусловие | Учётная запись пользователя добавлена администратором в список доступа. |
| Постусловие | Создана сессия приложения; в системе есть зашифрованный сессионный токен Jira пользователя (при отказе Jira — статус отказа, запись в Jira заблокирована). |
| Триггер | Пользователь открывает приложение. |

## Основной сценарий (Happy Path)

1. Пользователь вводит корпоративный логин и пароль в форму входа, совместимую с менеджером паролей браузера: стандартная схема username/current-password (autocomplete); пароль НЕ очищается до завершения ответа сервера; при отказе входа поле пароля очищается; во время отправки поля доступны только для чтения; в Chrome учётные данные дополнительно передаются через Credential Management API. При успешном входе браузер может предложить сохранить учётные данные — приложение не препятствует.
2. Система проверяет их в LDAP и наличие в списке доступа.
3. Система создаёт сессию приложения.
4. Тем же вводом пароля система создаёт сессию Jira (пароль живёт только в памяти запроса и не сохраняется).
5. Система сохраняет зашифрованный сессионный токен Jira.

## Альтернативные сценарии

4а. Пользователь уже входил ранее — при каждом входе сессия Jira создаётся заново, прежний токен заменяется.

## Сценарии исключений

2а. Пользователя нет в списке — вход отклонён, даже если LDAP-вход успешен.
4б. Jira отказала при верных данных LDAP (неверный пароль в Jira, блокировка входа, недоступность) — вход в приложение выполнен, чтение кэша доступно, запись в Jira заблокирована с текстом отказа; при недоступности Jira прежний токен сохраняется.
5а. Сессия Jira истекла во время работы (401) — система запрашивает пароль повторно, введённые данные не теряются; после ввода пароля прерванная операция продолжается с невыполненных шагов.

## Бизнес-правила и ограничения

NFR-006 — приложение пароль не хранит. Срок сессии приложения 8 ч не меняется; решение по «Запомнить меня» владельцем не принято (при необходимости отдельный CR).

## Критерии приёмки

1. При успешном входе менеджер паролей браузера предлагает сохранение учётных данных; повторный вход выполняется по сохранённым данным.
2. Пароль не очищается до завершения ответа сервера; при отказе входа поле пароля очищается; во время отправки поля readOnly.
3. В Chrome учётные данные передаются дополнительно через Credential Management API.
4. Пользователя нет в списке доступа — вход отклонён при успешном LDAP (2а).
5. Отказ Jira при верных данных LDAP — вход в приложение выполнен, запись в Jira заблокирована с текстом отказа (4б).
6. Истёкшая сессия Jira (401) — повторный ввод пароля без потери введённых данных, операция продолжается (5а).
7. Недоступность сервиса — сообщение об ошибке (503), ввод сохраняется.
