этой Jira невозможен (8.13.0), но он и не нужен.** Чтение и запись

Оговорка, которую нельзя закрыть технически: сессия конечна по времени. После её

**Осталось открытым (не мешает закрыть KON-30, требует решения владельца):**
восстановление истёкшей сессии, фоновый опрос без пользователей и формулировки

## 3. Что не работает

| Проверка | Результат |
|---|---|
| PAT (`Authorization: Bearer`) | **Невозможно.** Появился в 8.14, здесь 8.13.0. Подтверждено: в профиле нет раздела Personal Access Token, `applinks/user-menu` → 404 |
| Полный граф workflow через REST | **Недоступно.** Переходы видны только из текущего статуса. FR-026 это учитывает |
| `GET /rest/api/2/issue/{key}/attachment` | **404.** Вложения берутся из поля задачи |
| `GET /rest/api/2/issue/{key}/createmeta` | **404.** Работает `/rest/api/2/issue/createmeta?projectKeys=…` |
| CORS | **Выключен.** Заголовка `Access-Control-Allow-Origin` нет даже на preflight. Браузер не может ходить в REST Jira напрямую — нужен серверный посредник, что для веб-приложения естественно |
| Автоматическое восстановление сессии | **Нет.** Только с паролем |
| Фоновый опрос токеном без пользователя | **Нет.** Долгоживущего пользовательского токена на 8.13.0 не существует |
| `allowedValues` для большинства полей | **Недоступно.** `editmeta` покрывает лишь 39–50 полей задачи. Список значений приходит только для полей конкретного перехода |
| Дети эпика через `parent` | **Всегда 0.** `parent = X` не работает, нужно `"Epic Link" = X` или Agile API |

## 4. Выбранный способ аутентификации и почему

**Выбран сессионный токен: заголовок `Cookie: JSESSIONID=<token>`.**

| Способ | Вердикт | Обоснование |
|---|---|---|
| **Session cookie** | **выбран** | Токен, а не пароль: шифруется и хранится по NFR-006. Действия видны как действия пользователя. Работает на чтение и запись |
| Basic auth | отклонён как основной | Требует пароль на каждом вызове, то есть хранение пароля — прямое нарушение UC-005 и NFR-006 |
| `POST /rest/auth/1/session` | **заблокирован в коде** | Форма подтверждена пробой, но обмен требует пароль. Реализован как `SessionLoginProvider` с `enabled=False`; попытка включить без решения владельца поднимает `PermissionError` |
| Application Link (OAuth 1.0a) | не нужен | см. раздел 6 |

**Форма запроса, подтверждённая пробой** (важно, потому что распространённая
документация ошибается):

```json
{"username": "<логин>", "password": "<пароль>"}
```

Вложенный объект `{"session": {"username": …, "password": …}}` Jira 8.13.0
отклоняет: `400 Unrecognized field "session" (Class
com.atlassian.jira.rest.auth.AuthParams)`. Плоская форма даёт настоящий отказ
`401` с `x-seraph-loginreason: AUTHENTICATED_FAILED` и телом
`{"errorMessages": ["Ошибка доступа"], "errors": {}}` — проверено на живом
экземпляре, токен при отказе не выдаётся.

**Где проходит граница между кодом продукта и пробой.** В
`src/jira_client/auth.py` обмен пароля на сессию заблокирован: попытка создать
`SessionLoginProvider` без явного решения владельца поднимает
`PermissionError`. Одноразовый обмен для самой пробы выполняет
`input/jira/probe_raw/probe_live.py` — скрипт вне git, пароль в нём живёт
только в памяти процесса и не пишется ни в журнал, ни в дамп. Проверено:
зашифрованного значения токена нет ни в одном файле `probe_raw/`.

**Как переживает истечение сессии.** Никак: уведомления нет, первый запрос после
истечения возвращает 401. Обнаружение — вызов `/rest/api/2/myself` перед
операцией; он отвечает 401 раньше любого другого. Это подтверждено на практике:
сессия браузера, полученная 01.10, к 05.10 была мертва, и все защищённые
эндпоинты отдавали 401.

## 5. Как хранить учётные данные

Требуемые требования: **NFR-006** (шифрование, ключ в env, ничего в логах),
**UC-005** (пароль не сохраняется), **FR-025** (токен зашифрован).

| Актив | Где живёт | Шифрование |
|---|---|---|
| `JIRA_SESSION_TOKEN` | env в момент запроса; в приложении — только зашифрованным | **AES-256-GCM**, ключ `JIRA_TOKEN_ENCRYPTION_KEY` из env |
| Ключ шифрования | только env или менеджер секретов | не шифруется, но и не попадает в репозиторий |
| Пароль пользователя | **не хранится нигде** | — |

Реализовано в `src/jira_client/crypto.py` (`TokenVault`): AES-256-GCM,
случайный nonce на каждое шифрование, значение — одна base64-строка.

Утечки в логах исключены конструктивно и проверены тестами
(`tests/test_no_secrets.py`): у стратегий аутентификации переопределён
`__repr__`, `safe_summary()` отдаёт только признаки «задано / не задано»,
`client.last_call` содержит путь, код и длительность — без тела и заголовков.

**Риск, требующий согласования с владельцем.** Восстановление истёкшей сессии
невозможно без пароля. Варианты:

1. пользователь вводит пароль повторно, система сразу создаёт сессию и
   **не сохраняет его** — пароль живёт только в памяти запроса;
2. просить у администратора Jira включить Application Link (запасной путь);
3. обновление Jira до 8.14+, где появляется PAT, — вне нашего контроля.

Вариант 1 не нарушает UC-005 буквально (пароль не сохраняется), но требует
явного подтверждения: это решение владельца, не разработки.

## 6. Нужен ли запасной вариант Application Link

**Да, оставить его как запасной путь. Как основной — не нужен.**

Сессионная cookie закрывает и чтение, и запись, и требование «действия видны от
имени пользователя». Application Link нужен только там, где сессии не
хватает: **фоновый опрос по расписанию, когда ни один пользователь не в
сессии.**

Это ровно то, что требует FR-028: «Фоновый опрос ДОЛЖЕН идти токеном любого
активного пользователя (только чтение); если токенов нет, опрос
приостанавливается». На 8.13.0 такого токена не существует, поэтому:

- этап 1 — опрос **привязан к сессиям активных пользователей**; при отсутствии
  активных сессий опрос приостанавливается, как FR-028 и предписывает;
- этап 2 — если приостановка опроса окажется неприемлемой, включается
  Application Link.

Проверка согласия администратора (ISS-001) уже подана 01.10, риск RK-001
закрыт фактом работоспособности без него.

## 7. Обязательные поля и transition id для записи

**Проверено 2026-10-05 на живой Jira с сессией пользователя.** Источник:
`GET /rest/api/2/issue/ANALYTICS-5871?expand=transitions.fields` → 200, сырой
ответ `input/jira/probe_raw/A26_transition_171_shape.json`.

Текущий статус задачи: `id=11503`, «Поиск кандидата». Доступно **4 перехода**:

| `transition id` | Имя перехода | Целевой статус |
|---|---|---|
| 21 | Кандидат назначен | Кандидат назначен |
| **171** | **Кандидатов нет** | **Кандидатов нет** |
| 181 | Требуется кандидат | Требуется кандидат |
| 801 | В найм | Найм |

### Целевой переход: `id=171`, «Кандидатов нет»

У перехода **одно** поле, и Jira считает его **необязательным**:

| `fieldId` | Имя поля | `required` | Допустимые значения |
|---|---|---|---|
| `customfield_16100` | Причина отсутствия кандидата | **`false`** | 8 вариантов, id ниже |

Допустимые значения `customfield_16100`:

| `id` | Значение |
|---|---|
| 16702 | Нет специалистов данного уровня, но есть слабее |
| 16703 | Нет специалистов конкретного набора стека |
| 16704 | Нет специалистов с нужной отраслевой экспертизой |
| 16705 | Нет специалистов с нужным специфичным стеком (в комментах стек) |
| 21300 | Низкая ставка |
| 20603 | Увольнение/декрет кандидата |
| **23300** | **Требуется очное присутствие** — значение из постановки, существует |
| 25200 | Есть прямой запрос |

**Постановка требует перехода «Кандидатов нет» с обязательными полями, и
`required: false` у единственного поля — обманчиво.** Причина в том, что
обязательность лежит не в схеме поля, а в экранном поле комментария: Jira не
перечисляет его в `transitions.fields` и поэтому не показывает как обязательное.
Фактически причина всё равно нужна, поэтому интеграция должна задавать её всегда,
независимо от `required`.

### Главное открытие пробы: переход требует комментарий

Первая попытка выполнить переход получила:

```
HTTP 400 {"errorMessages": [], "errors": {"comment": "Необходимо добавить комментарий"}}
```

Комментарий **не объявлен** в `transitions.fields`, поэтому в
`required_fields` его нет и заранее проверить его невозможно — нашёлся он только
по ответу Jira. Форма `fields: {"comment": …}` не подходит: Jira отвечает 400
`Field does not support update 'comment'`. Работает только `update.comment.add`:

| Форма | Ответ Jira |
|---|---|
| `fields: {"comment": "текст"}` | 400 `Field does not support update 'comment'` |
| `fields: {"comment": {"body": "текст"}}` | 400 то же |
| `update: {"comment": [{"add": {"body": "текст"}}]}` | **204, переход выполнен** |

Тело успешного запроса целиком:

```json
{"transition": {"id": "171"},
 "fields": {"customfield_16100": {"id": "23300"}},
 "update": {"comment": [{"add": {"body": "KON-30: переход …"}}]}}
```

Следствие для FR-026: список переходов вместе с обязательными полями, который
Jira отдаёт через REST, **неполон**. Обязательное экранное поле комментария в
нём отсутствует. Интеграция обязана либо всегда передавать комментарий, либо
разбирать ошибку `errors.comment` и повторять переход с комментарием.

### Где обязательные поля есть на самом деле

Переход `id=801` «В найм» содержит три поля с `required: true`:

| `fieldId` | Имя поля | `required` | Допустимые значения |
|---|---|---|---|
| `customfield_20810` | Включает НДС | **да** | Да (20999), Нет (21000) |
| `customfield_20811` | Валюта | **да** | руб. (21001), EUR (21002), GBR (21003), KZT (21004), USD (21005) |
| `customfield_20812` | Единица измерения | **да** | ч (час) (21006) |

Это те же поля, что FR-015 называет ставкой, — то есть на переходе «В найм» надо
заполнить ставку целиком, иначе Jira отклонит переход. Проверку обязательности
надо делать до отправки, а не после отказа.

### Найденная ошибка формы ответа (исправлена)

`transitions[].fields` Jira 8.13.0 отдаёт **словарём** «`fieldId` → описание», а
не списком:

```json
"fields": {"customfield_16100": {"required": false, "name": "Причина отсутствия кандидата",
                                 "fieldId": "customfield_16100", "allowedValues": [...]}}
```

Первая версия клиента ждала список и при обходе словаря получала строки-ключи,
из-за чего `FieldSpec` не создавался и **все поля перехода, включая
обязательные, терялись молча**. Клиент отправил бы переход без ставки и получил
отказ от Jira вместо того, чтобы собрать её сам. Исправлено в
`src/jira_client/models.py` (`_field_specs`), закрыто 7 регрессионными тестами.
Список тоже поддерживается — без `expand=transitions.fields` Jira иногда
отдаёт массив.

### Как клиент это делает

| Что | Значение |
|---|---|
| Поиск перехода | по `id`, по имени целевого статуса или по вхождению в название |
| Обязательные поля | `transitions[].fields[].required` при `expand=transitions.fields` |
| Значения поля | `transitions[].fields[].allowedValues` — **только** для полей перехода |
| Тело перехода | `{"transition": {"id": "…"}, "fields": {…}, "update": {"comment": [{"add": {…}}]}}` |
| Предзапись | переходы перечитываются перед сменой статуса (FR-028) |
| Локальная валидация | недостающие обязательные поля отсекаются **до** вызова Jira, а не после 400 |
| Комментарий перехода | передаётся через `update.comment.add`, метод `transition(comment=…)` |

### Что осталось сделать

Ничего: запись выполнена и проверена, результат в разделе 2.2.
| Вложение | требуется заголовок `X-Atlassian-Token: no-check`, иначе Jira отклоняет загрузку |

## 8. Поведение при отказах (FR-029, ISS-013)

Правило NFR-009: **не более 10 с на вызов**. Повторы внутри этого лимита
означали бы нарушение, поэтому **повторы выключены по умолчанию**; признак
`retryable` подсказывает вызывающему коду, оправдан ли повтор вообще.

| Код | Текст Jira | Исключение | `retryable` |
|---|---|---|---|
| 401 | `Client must be authenticated…` | `JiraAuthError` | нет |
| 401 | `У вас нет доступа для просмотра данного запроса. Необходимо ввести имя пользователя` | `JiraAuthError` | нет |
| 401 | `Вы не авторизованы…` | `JiraPermissionError` | нет |
| 401 | `Ошибка доступа` | `JiraAuthError` | нет |
| 401 | **HTML-страница на 13 КБ** | `JiraAuthError` | нет |
| 403 | любой | `JiraPermissionError` | нет |
| 404 | `ЗАПРОС НЕ СУЩЕСТВУЕТ` | `JiraNotFoundError` | нет |
| 400 | `Ошибка в запросе JQL: …` + `errors{}` | `JiraBadRequestError` | нет |
| 400 | `{"errors": {"comment": "Необходимо добавить комментарий"}}` | `JiraBadRequestError` | нет |
| 400 | `Field does not support update 'comment'` | `JiraBadRequestError` | нет |
| 429 | перегрузка | `JiraRateLimitedError` | **да** |
| 503 | перегрузка | `JiraRateLimitedError` | **да** |
| 5xx | сбой Jira | `JiraServerError` | нет |
| — | таймаут 10 с | `JiraTimeoutError` | **да** |
| — | сеть / TLS | `JiraUnavailableError` | **да** |

### Два вывода, которые меняют поведение приложения

**Код 401 неоднозначен — Jira отдаёт им пять разных ситуаций.** Если
смотреть только на код, приложение покажет пользователю неверную причину и
нарушит FR-029. Клиент различает их по телу:

| Причина | `reason` | `needs_reauthorization` |
|---|---|---|
| Нет аутентификации | `no_credentials` | **да** |
| Нужен вход | `login_required` | **да** |
| Не хватает прав | `no_permission` | **нет** |
| Отказ аутентификации | `auth_failed` | нет |
| Недействительная cookie | `invalid_cookie_or_expired` | **да** |

Различение принципиально: «нет прав» авторизацией **не лечится** — там нужен
администратор Jira, и FR-026 требует показать отказ как есть.

**Недействительная cookie ломает даже анонимные эндпоинты.** Если в запросе
присутствует неверная или пустая cookie, Jira отдаёт 401 **HTML-страницей на
13 КБ** — в том числе для `/rest/api/2/field` и `/rest/api/2/status`, которые
без cookie отвечают 200. Проверено перебором пяти вариантов заголовка Cookie.

Практические следствия:

1. «Jira недоступна» и «сессия истекла» — **разные состояния**, и их нельзя
   смешивать: клиент обязан отличать 401 от сетевой ошибки;
2. HTML-страницу нельзя показывать пользователю — клиент сжимает её до одной
   строки с причиной, исходный текст остаётся в дампе пробы;
3. после истечения сессии приложение не может даже прочитать метаданные
   полей, поэтому проверять сессию надо **до** любых операций.

## 9. Влияние на требования

| Требование | Влияние |
|---|---|
| **FR-008** (назначение с передачей в Jira) | **Выполнимо и проверено на записи:** комментарий 201, вложение 201, переход 204 с причиной. Все три операции в одном сценарии, от имени пользователя |
| **FR-025** (OAuth 1.0a) | **Требует правки формулировки.** Предлагаемая формулировка: «…от имени конкретного пользователя через сессионный токен Jira; при отзыве доступа (401) система запрашивает повторную авторизацию, не теряя введённых данных». Основание: PAT невозможен, Application Link не нужен. Относится к аналитику |
| **FR-026** (смена статуса по переходам Jira) | **Выполнимо с оговоркой.** Переходы с обязательными полями запрашиваются корректно, но REST **не показывает** обязательное экранное поле комментария — на переходе 171 это выяснилось только по ответу Jira 400. Требование «не вводить своих ограничений» соблюсти нельзя, пока обязательность определяется пробой отказа |
| **FR-028** (опрос и кэш) | **Частично.** Инкрементальный JQL, узкий запрос полей, Agile API для детей эпика — работают. **Фоновая часть упирается в отсутствие долгоживущего токена**: опрос привязан к активным сессиям и при их отсутствии приостанавливается, как FR-028 и предписывает |
| **UC-005** (вход и авторизация) | **Требует правки.** Шаги «перенаправление в Jira для разрешения доступа» и «сохранение access token» не применимы без OAuth. Нужна формулировка «система создаёт сессию в Jira по учётным данным, введённым пользователем, и сохраняет сессионный токен зашифрованным» |
| **NFR-006** (защита токенов) | **Выполнимо** критерий (2): ключ в env, в коде и репозитории его нет — проверяется тестом |
| **NFR-009** (10 с на запись) | **Выполнимо**: таймаут жёстко задан в конфиге, большие значения молча урезаются до 10 с |
| **RK-001 / условие 5.5** | **Снимаются полностью.** Чтение и запись фактически выполнены без технической учётки и без Application Link |

## 10. Реализованный клиент

`src/jira_client/` — Python, единственная зависимость `httpx`
(`cryptography` нужна только для `TokenVault`).

| Файл | Назначение |
|---|---|
| `client.py` | HTTP-слой: чтение, запись, пагинация, отображение кодов в исключения |
| `config.py` | Конфигурация из env, жёсткий таймаут 10 с, `safe_summary()` без секретов |
| `auth.py` | Сессионная cookie, Basic, заблокированный `SessionLoginProvider` |
| `errors.py` | Классификация 401 по телу, сжатие HTML-отказа |
| `crypto.py` | AES-256-GCM для сессионного токена |
| `fields.py` | ID полей из FR-015/FR-028, отбор заполненных |
| `models.py` | Безопасные модели без e-mail |
| `.env.example` | Шаблон без значений |
| `tests/` | 258 тестов, покрытие 97 %, сеть не используется |

Соответствие постановке: конфиг и учётные данные только из переменных
окружения; секретов в коде нет; тесты обезличены; повторные запросы
выключены ради NFR-009.

Харнесс пробы — `input/jira/probe_raw/probe_live.py`, вне git (правило
`.gitignore`: `input/*`). Он читает `.env`, при отсутствии токена сам получает
сессию, прогоняет этап чтения, а с флагом `--write` — этап записи. Секреты в
дампы не пишет: проверено, что значение токена не встречается ни в одном файле
`probe_raw/`.

## 11. Открытые вопросы

1. **Как восстанавливать истёкшую сессию.** Требует пароля. Нужно решение
   владельца: повторный ввод пароля без сохранения (вариант 1 из раздела 5)
   или переход на Application Link.
2. **Фоновая часть FR-028.** Приемлемо ли, что опрос приостанавливается без
   активных сессий пользователей?
3. **Формулировки FR-025 и UC-005** требуют правки под сессионный токен вместо
   OAuth. Влияет на критерии приёмки — решение за аналитиком.
4. **Обязательность на переходах неполна через REST.** Переход 171 требует
   комментарий, но не объявляет его в `transitions.fields` (раздел 7). Нужно
   решение аналитика: зафиксировать в требованиях, что смена статуса всегда
   сопровождается комментарием, иначе Jira откажет.
5. **Срок жизни сессии** на этом экземпляре не измерен: он влияет на то, как
   часто пользователю придётся переавторизовываться. Замеряется после первого
   входа.
6. **Запись выполнена на боевой задаче** `ANALYTICS-5871` и не откатывалась.
   Комментарии `519001`, `519002` и вложение `328390` оставлены как доказательство
   для `close_approval_condition`. Если аналитику нужна чистая задача — удалить по
   этим id (раздел 2.2).
7. **Два расхождения, зафиксированные в выгрузке и требующие уточнения у
   владельца процесса:** в `SA-2219` статус «В процессе» при резолюции «Готово»;
   поле `Epic link потребности` (`customfield_11032`) при наличии ещё и
   `customfield_10101` — какое из них каноническое, из пробы не следует.
