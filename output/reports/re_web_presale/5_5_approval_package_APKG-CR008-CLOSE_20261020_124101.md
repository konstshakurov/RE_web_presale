### FR-018: Ввод ставки при назначении
**Тип:** functional | **Версия:** 3.0 | Приоритет: Should  
**Owner:** Руководитель направления Аналитики  

Ставка «от производства» вносится при назначении кандидата, а не при найме. В окне «Назначить» (FR-008) система ДОЛЖНА предоставлять поле «Ставка, руб. с НДС» со свободным вводом, без встроенной логики расчёта. Поле обязательно, если в потребности признак «Кто предлагает ставку» = «Производство» (БП-2); если ставку предлагает «Клиент», система свою ставку НЕ вводит и НЕ отправляет (клиентская ставка показывается справочно). Рядом с полем система ДОЛЖНА показывать ставку из потребности (FR-001) и среднюю/медианную ставки (FR-019) как ориентир (предложение). Запись в Jira: ставка не входит в поля перехода и не пишется через PUT /issue (поля 20809–20812, 21105 не на экранах редактирования и переходов); система ДОЛЖНА передать её отдельным вызовом custom REST endpoint ScriptRunner POST /rest/scriptrunner/latest/custom/rateCalculationLogic от имени пользователя в рамках действия «Назначить» — после успешного назначения. Тело: issueKey, currentUserUsername и все поля: 21105 «Кто предлагает ставку» (22412 = Производство; передаётся всегда), 20809 «Планируемая ставка» (число-строка), 20810 «Включает НДС» (20999 = Да), 20811 «Валюта» (21001 = руб.), 20812 «Единица измерения» (21006 = ч); справочники — по id. Система ДОЛЖНА: проверять значения справочников у себя до отправки; не отправлять пустую ставку (Jira отвечает 500); после записи перечитывать «Планируемую ставку» и сверять — Jira на неверный id справочника и на отсутствие 21105 отвечает 200, но ничего не записывает; ошибку 500 на несуществующий ключ показывать как ошибку запроса, а не недоступность Jira. Если назначение прошло, а запись ставки нет, система ДОЛЖНА явно сообщить об этом оператору, сохранить введённое и дать повторить (FR-029). При переходе «Найм» ставка не вводится (FR-011).

**CR-история:** CR-007 (approved_modified/Approved_with_Modification); CR-008 (approved_modified/Approved_with_Modification)

### FR-035: Фильтр потребностей по группам статусов
**Тип:** functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Раздел «Потребности» ДОЛЖЕН предоставлять фильтр по группам статусов в один клик (ссылки над таблицей, у каждой — счётчик потребностей). Группы по умолчанию (статусы workflow Jira типа «Аналитик»): «Без кандидата» — Требуется кандидат, Поиск кандидата, Найм, Отказ по кандидату, Интервью не пройдено; «Кандидат назначен» — Кандидат назначен; «Интервью» — Подготовка к интервью, Интервью состоялось, Интервью пройдено, Интервью не пройдено; «Закреплён» — Закреплен за проектом. Критерии приёмки: (1) клик по группе сразу оставляет в таблице потребности только с её статусами; (2) счётчик группы равен числу потребностей в ней; (3) при первом входе активна группа «Без кандидата»; (4) любая потребность видна хотя бы в группе «Прочие» или в режиме «Все статусы»; (5) после повторного входа активна ранее выбранная группа.

Кнопка показывается, только если Jira отдаёт этот переход для текущего статуса потребности (FR-026): «Требуется кандидат» → Поиск / Найм / Кандидатов нет; «Поиск кандидата» → Найм / Кандидатов нет; «Кандидатов нет» → Поиск / Найм; «Найм» → Поиск / Кандидатов нет; «Кандидат назначен» → Поиск / Найм / Кандидатов нет. Для прочих статусов (включая «Отказ по кандидату») кнопок нет; «Кандидат назначен» выставляется только при назначении (FR-008).

При переходе «Кандидатов нет» ДОЛЖНЫ запрашиваться обязательные поля Jira: «Причина отсутствия кандидата» (значения справочника Jira: Нет специалистов данного уровня, но есть слабее; …конкретного набора стека; …нужной отраслевой экспертизой; …нужным специфичным стеком (стек в комментарии); Низкая ставка; Увольнение/декрет кандидата; Требуется очное присутствие; Есть прямой запрос) и «Комментарий» (видимость «для всех»). Для «Поиск кандидата» — подтверждение одним кликом. Для «Найм» (переход «В найм») Jira требует ставку целиком — «Включает НДС», «Валюта», «Единица измерения» (customfield_20810–20812): значения предзаполняются из потребности, при отсутствии запрашиваются; проверка обязательности — до отправки (проба KON-30). Саму ставку («Планируемая ставка», 20809) при найме не вводят: она вносится при назначении (FR-018); значения справочников передаются по id, полученным у Jira. Значения справочника и обязательные поля ДОЛЖНЫ запрашиваться у Jira, а не храниться в приложении (см. FR-026).

**CR-история:** CR-005 (approved/Approved); CR-007 (approved_modified/Approved_with_Modification); CR-008 (approved_modified/Approved_with_Modification)


### FR-026: Смена статуса потребности по переходам Jira
**Тип:** functional | **Версия:** 1.3 | Приоритет: Should  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА запрашивать у Jira допустимые переходы из текущего статуса потребности (вместе с обязательными полями) и показывать пользователю только переходы в «Поиск кандидата», «Найм» и «Кандидатов нет» (белый список). Статус «Кандидат назначен» выставляет Jira при назначении через «Назначить» (FR-008), отдельной кнопки нет. Прочие переходы в приложении НЕ ДОЛЖНЫ показываться: их ведут клиентская служба и автор потребности. Система НЕ ДОЛЖНА вводить собственных ограничений сверх белого списка: права определяются правами пользователя в Jira. Отказы Jira (403 и др.) показываются как есть.

**CR-история:** CR-005 (approved/Approved); CR-007 (approved_modified/Approved_with_Modification); CR-008 (approved_modified/Approved_with_Modification)
