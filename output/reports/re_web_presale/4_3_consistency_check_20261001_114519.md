## Проблемы по критериям

### Полнота

**ISS-003** 🟡 Существенная  
- **Проблема:** Выгрузка Jira закрыла вопросы 8 и 9 из 4.2: статусы сотрудников (10 шт.) — это статусы типа Epic, статусы потребностей (19 шт., тип Аналитик) — отдельный workflow. Но не определено, какие из 10 статусов сотрудника означают «доступен для назначения» для фильтра FR-002.  
- **Пример:** 4.2 FR-002 («например: На проекте, Скоро освобождается, Не на проекте»); ANALYTICS-5853.md §D.3 (статусы типов Epic и Аналитик)  
- **Источник:** `4_2_elicitation_results + input/jira/ANALYTICS-5853.md`  
- **Рекомендация:** Заменить пример в FR-002 фактическим перечнем 10 статусов Jira и зафиксировать, какие считаются «доступными» по умолчанию.

**ISS-008** 🟡 Существенная  
- **Проблема:** FR-022: не определено, как сопоставляются папки с CV и карточки сотрудников в Jira и как отсекаются уволенные. В карточке есть признаки для сопоставления (Epic Name = ФИО, «ID пользователя» customfield_11515, «Ссылка на резюме» customfield_10710 на OwnCloud, «Дата актуализации CV» 17400, статусы Уволен / Декрет), но решение не зафиксировано. Тип потребности «Аналитик» и карточка связаны полем «Профиль сотрудника» (10707), а не прямой ссылкой на эпик.  
- **Пример:** 4.2: FR-022, белое пятно 3; ANALYTICS-96.md §C.1; ANALYTICS-5853.md §E.3 (связь linked с ANALYTICS-1149)  
- **Источник:** `4_2_elicitation_results + input/jira/ANALYTICS-96.md`  
- **Рекомендация:** Зафиксировать ключ сопоставления (ФИО или ID пользователя) и правило отсечения по статусам карточки; отдельно решить, использовать ли «Ссылка на резюме» как источник CV.

**ISS-009** 🟡 Существенная  
- **Проблема:** FR-015 перечисляет источники правил клиента, но в эпике они заданы структурированными полями: «Условия для производства» (21801), «Критерии приемки» (20909), «Штрафы» (20910), «Привлечение 3х лиц» (20907), «Разрешение на PR» (20913), «Рекомендации» (12000), а в потребности — «Рисовать опыт нельзя» (20302). Состав вкладки «Важные условия для производства» не определён; правило «не завышать опыт» может проверяться по структурному полю, а не по тексту.  
- **Пример:** 4.2: FR-015, БП-6; SA-2219.md §C.1; ANALYTICS-5853.md §C.5  
- **Источник:** `4_2_elicitation_results + input/jira/SA-2219.md`  
- **Рекомендация:** Определить перечень полей эпика и потребности, которые приложение показывает как правила клиента, и какие из них влияют на информирование о нарушении.

**ISS-010** 🟡 Существенная  
- **Проблема:** FR-011: не выявлено, какое поле Jira хранит причину для статуса «Кандидатов нет», и какие поля обязательны на переходах в «Кандидат назначен», «Кандидатов нет», «Найм». REST возвращает переходы только из текущего статуса задачи; в выгрузке текущий статус — «Кандидат назначен», поэтому нужных переходов нет. Полный граф workflow недоступен через REST.  
- **Пример:** 4.2: FR-011; ANALYTICS-5853.md §D.2, §D.4; _api_notes.md §6.2  
- **Источник:** `input/jira/ANALYTICS-5853.md + input/jira/_api_notes.md`  
- **Рекомендация:** Попросить администратора Jira выгрузить схему workflow типа Аналитик либо дать тестовые задачи в статусах «Требуется кандидат» и «Поиск кандидата» для снятия переходов с полями.

**ISS-011** 🟡 Существенная  
- **Проблема:** Нет требований по защите персональных данных: CV и карточки содержат ПДн сотрудников, срок хранения бессрочный (NFR-004), шифрование, резервное копирование, права доступа к БД CV и политика удаления не заданы. Хранение OAuth-токенов пользователей и ключа шифрования описано только решением от 01.10.  
- **Пример:** 4.2: NFR-004, NFR-006, NFR-007; FR-004  
- **Источник:** `4_2_elicitation_results`  
- **Рекомендация:** Добавить НФТ по ПДн (обоснование хранения, шифрование данных и токенов, резервное копирование, роли доступа) и уточнить, нужно ли согласование с ИБ компании.

**ISS-012** 🟡 Существенная  
- **Проблема:** Не определено, как приложение получает новые потребности и обновления статусов из Jira (периодический опрос или вебхуки, период, объём выборки), и нет НФТ по времени отклика (в т.ч. работа LLM). Jira отдаёт тела задач большого объёма (до ~600 полей), дети эпика читаются только через Agile API.  
- **Пример:** 4.2: FR-001, FR-020, NFR-002; _api_notes.md §5.3, §6.5  
- **Источник:** `4_2_elicitation_results + input/jira/_api_notes.md`  
- **Рекомендация:** Зафиксировать способ получения данных и допустимую задержку актуальности; запрашивать только нужные поля (параметр fields).

**ISS-013** 🟢 Незначительная  
- **Проблема:** Не описано поведение приложения при отказе Jira (401 отозванный токен, 403 нет прав, недопустимый переход, конфликт при повторном назначении по FR-010) и когда у пользователя из списка приложения нет прав в Jira.  
- **Пример:** 4.2: FR-010, FR-021; решение 01.10 «права = права пользователя в Jira»  
- **Источник:** `4_2_elicitation_results`

### Точность

**ISS-007** 🟡 Существенная  
- **Проблема:** Правило «корпоративное CV = имя файла заканчивается на SimbirSoft» не подтверждается образцами из Jira: вложение «Тимофей_Ц_Аналитик_Simbirsoft_ЛМ.docx» содержит Simbirsoft в середине имени, в ином регистре и с суффиксом клиента (ЛМ); вложение «Циликов Андрей 29.05.26 CV.docx» построено по другой схеме имени. Правило будет давать ошибочную классификацию.  
- **Пример:** input/jira/attachments/ANALYTICS-5853, input/jira/attachments/SA-2219; решение пользователя от 30.09.2026  
- **Источник:** `input/jira/attachments + решение 30.09`  
- **Рекомендация:** Уточнить правило: регистр, положение маркера, расширение, суффикс клиента; предусмотреть ручное подтверждение типа CV при загрузке для неоднозначных имён.

**ISS-015** 🟢 Незначительная  
- **Проблема:** В данных Jira статус и резолюция не согласованы (SA-2219: статус «В процессе», резолюция «Готово»). Резолюцию нельзя использовать как признак закрытости потребности или эпика.  
- **Пример:** SA-2219.md §A, примечание о несогласованности  
- **Источник:** `input/jira/SA-2219.md`  
- **Рекомендация:** В логике фильтров и дублей опираться на статус (id и категорию), а не на резолюцию; отразить в FR-014 и FR-020.

### Непротиворечивость

**ISS-001** 🔴 Критическая  
- **Проблема:** Способ доступа к Jira в артефакте 4.2 (личная LDAP-учётка, служебная учётка или токен, ограничение «доступ по LDAP», NFR-006) не соответствует возможностям Jira Server 8.13.0: персональных токенов (PAT) нет, обновление пока невозможно. Решение от 01.10.2026 (вход в приложение по корпоративному LDAP + список разрешённых пользователей; действия в Jira от имени пользователя через OAuth 1.0a / Application Link; токен пользователя хранится зашифрованно) в артефакты ещё не внесено и зависит от согласия администратора Jira.  
- **Пример:** 4.2: раздел «Незакрытые темы» п.1, NFR-006, «Ограничения: Jira — доступ по LDAP»; _api_notes.md §2 «Почему не PAT»  
- **Источник:** `4_2_elicitation_results + input/jira/_api_notes.md`  
- **Рекомендация:** Переписать NFR-006 и ограничения под принятую схему, добавить FR на вход по LDAP + список допустимых пользователей и на OAuth-авторизацию в Jira при первом входе; завести как риск и внешнюю зависимость согласование Application Link администратором Jira.

**ISS-002** 🟡 Существенная  
- **Проблема:** Ограничение «права РО и РН в Jira ограничены статусами Кандидат назначен, Кандидатов нет, Найм» и БП-1 противоречат решению от 01.10.2026: приложение не ограничивает операции у себя, права определяются правами самого пользователя в Jira. FR-011 перечисляет только два статуса, FR-020 показывает все. Не определено, какие переходы приложение предлагает пользователю.  
- **Пример:** 4.2: БП-1, раздел «Ограничения» (последний пункт), FR-011, FR-020  
- **Источник:** `4_2_elicitation_results`  
- **Рекомендация:** Переформулировать БП-1 как внешнюю политику Jira, а не правило приложения; добавить FR: список переходов строится из ответа Jira для текущего статуса потребности (включая обязательные поля перехода), ошибки доступа Jira показываются пользователю как есть.

### Однозначность

**ISS-004** 🟡 Существенная  
- **Проблема:** FR-019 не задаёт правило подсчёта средней и медианной ставок при разных валютах, признаке НДС и единице измерения. Jira хранит ставку четырьмя полями: сумма (customfield_20809), «Включает НДС» (20810), «Валюта» (20811), «Единица измерения» (20812; в примере «ч (час)»), плюс «Кто предлагает ставку» (21105). Вопрос про единицу ставки по данным снят частично (поле есть, допустимые значения не получены), но агрегирование по валютам и НДС остаётся открытым.  
- **Пример:** 4.2: FR-019, БП-3, БП-4, белые пятна 4–6; ANALYTICS-5853.md §C.1 (поля 20809–20812, 21105)  
- **Источник:** `4_2_elicitation_results + input/jira/ANALYTICS-5853.md`  
- **Рекомендация:** Уточнить правило агрегирования (предложение: отдельно по сочетанию валюта + единица измерения; для рублей с НДС и без НДС — отдельно либо с приведением по ставке НДС).

**ISS-005** 🟡 Существенная

- **Пример:** 4.2: FR-014, белое пятно 7  
- **Источник:** `4_2_elicitation_results`  
- **Рекомендация:** Задать порог (число совпавших строк или доля текста) и пороги градаций; согласовать на примерах реальных дублей «Прямой контракт» / «Субподрядчик».

**ISS-014** 🟢 Незначительная  
- **Проблема:** Расплывчатые формулировки без критериев: «быстрый доступ к CV» (FR-002), «краткий опыт» (FR-003), «выборочным LDAP-аккаунтам» (FR-021), «современные правила» хранения кредов (NFR-006).  
- **Пример:** 4.2: FR-002, FR-003, FR-021, NFR-006  
- **Источник:** `4_2_elicitation_results`

### Тестируемость

Качество Qwen на русском назван риском, но метрики приёмки нет.  
- **Пример:** 4.2: FR-005, FR-006, FR-023; риск «Качество Qwen на русском тексте»
