### Возможности и процессы

Для потребности система сразу показывает рекомендованного кандидата с процентом соответствия и обоснованием; правила клиента показаны рядом. Пользователь (РО, РН, пресейл) просматривает рекомендацию и выбирает кандидата. После выбора система сама назначает кандидата, меняет статус потребности и прикрепляет заранее подготовленное корпоративное CV (если их несколько — пользователь выбирает). Скрининг кандидата остаётся вне системы (переписка); его результат вносится комментарием в потребность, например «Скрининг от Ивана Ш.: …». Решение о выборе остаётся за человеком. Роли и права в Jira не меняются: действия идут от имени пользователя и в пределах его прав, в том числе когда РО отдела кандидата отсутствует.

**Целевые метрики:**
- время_выбора_кандидата: до 1 минуты
- соблюдение_регламента_назначения_24ч: 100% потребностей (цель, базовое значение не измерено)
- ручные_операции_после_выбора: 0 (назначение, статус, CV выполняет система)

*Addresses BN:* BN-001

*Примечания: 1) Цель «1 минута» — со слов аналитика, нужно определить границы замера (от открытия потребности до назначения). 2) Комментарий о скрининге вносится вручную; автоматический разбор «+/-» вне скоупа. 3) Адаптация CV под шаблон клиента в to-be не описана: открытый вопрос — остаётся ручной или входит в автоматизацию.*

### Технологии и инфраструктура

Веб-приложение работает поверх Jira Server 8.13.0 во внутреннем контуре компании. Вход — через корпоративный LDAP со списком разрешённых пользователей, который ведёт администратор приложения. Действия в Jira выполняются от имени пользователя (OAuth 1.0a через Application Link, токен пользователя хранится зашифрованно). Данные Jira читаются опросом с локальным кэшем: потребности — инкрементально каждые 5 минут, сотрудники — раз в час и по кнопке, правила клиента — при открытии с кэшем 1 час. Компетенции из CV хранятся в отдельной БД в структурированном виде и используются для сопоставления с потребностью. Рекомендацию формирует LLM: настраиваемый внешний или внутренний провайдер (ввод API Key и URL, Qwen по умолчанию), во внешнюю модель уходит только обезличенный текст через шлюз. Запись в Jira: смена статуса, прикрепление CV, комментарий.

**Целевые метрики:**
- открытие_списков_из_кэша: до 2 секунд
- запись_в_Jira: до 10 секунд
- таймаут_LLM: 120 секунд (настраиваемый)
- актуальность_потребностей: до 5 минут
- актуальность_карточек_сотрудников: до 1 часа

*Addresses BN:* BN-001

*Примечания: Решения 4.3 и после него (ISS-001, 006, 008, 012, 013). Зависимость: согласование Application Link администратором Jira (заявка в Support подана 01.10.2026, ответа нет) — внешний риск для 6.3. Конкретный стек и архитектура — за пределами 6.2 (7.5).*

### Политики

Регламент сроков сохраняется: поиск — в течение 1 часа, назначение — в течение 24 часов. Права в Jira равны правам самого пользователя, приложение не ограничивает набор операций у себя. Не назначаются статусы сотрудника Коммерческий проект, Уволен, Декрет, Недоступен для подключения. Приложение работает только во внутреннем контуре. Во внешнюю LLM уходит только обезличенный текст с предпросмотром отправляемого (нулевая утечка ПДн на 5–10 реальных примерах), Claude — только через API-ключ. Файлы CV и примеров работ, прикрепляемые в Jira, остаются как есть. Правила клиента показываются только заполненные, только как информация. Корпоративным считается CV с именем файла на SimbirSoft. Показывается причина отказа Jira как есть, при 401 выполняется повторная авторизация без потери введённых данных. Скрининг кандидата вне системы, результат вносится комментарием в потребность вручную.

**Целевые метрики:**
- утечка_ПДн_во_внешнюю_LLM: 0 на 5–10 реальных примерах
- метрики_качества_LLM: не вводятся (решение ISS-006)

*Addresses BN:* BN-001

*Примечания: Собрано из решений 4.3 и последующих (ISS-006, 008, 009, 011, 013). Регламент 1 ч / 24 ч передан устно, документ не приложен. Нужен ли контроль соблюдения регламента отчётом в приложении — не решено.*

## Ограничения

### Jira Server 8.13.0 без PAT (Технологические стандарты) — ✅

Версию Jira обновить пока нельзя. PAT недоступен, остаются OAuth 1.0a (Application Link) или Basic. Любые интеграции и API оформляются заявкой в Support. Application Link технически возможен, но заявка подана 01.10.2026 и ответа нет. Дети эпика доступны только через Agile API, полный граф workflow через REST недоступен.

### Внутренний контур и ПДн при работе с LLM (Регуляторные требования) — ✅

Приложение работает только во внутреннем контуре на серверах компании, доступа извне нет. Во внешнюю LLM передаётся только обезличенный текст через шлюз с предпросмотром; Claude — только через API-ключ, не через личный аккаунт. Критерий: нулевая утечка ПДн на 5–10 реальных примерах. Файлы CV и примеров работ, прикрепляемые в Jira, остаются как есть. Требования по ПДн не расширяются сверх принятого: шифрование токенов, отдельная БД CV, обезличивание для внешней LLM.

### Бюджет, срок и команда проекта не определены (Прочее) — 🔶 предположение

В материалах нет данных о бюджете, сроке запуска и составе команды разработки. Это неизвестные ограничения: до уточнения они считаются риском проекта для 6.3 и влияют на выбор варианта дизайна в 7.5. Нужно уточнить у спонсора.
