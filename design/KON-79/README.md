# KON-79 — «Назначить»: минимальный сценарий (обновлено 15.10.2026, решение владельца в чате)

> **Актуально:** `variant_a.html` (минимальный). Варианты B и C остаются в папке как отвергнутые для истории. Ручной общий перевод статуса из приложения **не входит** в разработку.

## Сценарии
1. **Назначить из приложения:** «Назначить» → выбрать CV, комментарий (+ставка, файлы по FR-008/FR-018) → «Назначить…» → экран подтверждения → «Подтвердить и отправить в Jira» → Jira сама переводит потребность в «Кандидат назначен» (вручную статус не меняется; файлы и комментарии статус не меняют). После успеха приложение перечитывает потребность и показывает новый статус.
2. **Назначение в самой Jira** (вне приложения): статус меняется в Jira; приложение узнаёт его при опросе (FR-028) или по кнопке «Обновить».
3. **Нет кандидатов или нужен найм:** в строке потребности два вторичных действия «Кандидатов нет…» и «Найм…». «Кандидатов нет» — причина из справочника Jira и комментарий (обязательны); «Найм» — перевод (поля — по запросу Jira). Общего списка переходов нет.

## Что убрано относительно первого пакета
- Чип статуса как меню «Сменить статус ▾» и диалог со списком всех переходов Jira.
- Ручная смена статуса как шаг назначения.

## Решение по требованиям
CR-005 (5.4, score 7.5): FR-026 сужается до двух переходов, UC-002 и FR-011 уточняются, в FR-008 добавляется автоматический перевод статуса Jira. Решение — за владельцем (`output/reports/re_web_presale/…CR-005…` после resolve).

## Риск
Автоперевод статуса при записи через API (не через экран Jira) должен быть подтверждён пробой на тестовой потребности в KON-42/KON-43: в UI Jira это переход «Назначить» со своим экраном. Если одной записи полей недостаточно, backend выполняет этот переход сам (для пользователя шаг всё равно один).

# KON-79 — «Назначить» и смена статуса: три варианта

Прототипы (кликабельное переключение состояний в чёрной полосе сверху): `variant_a.html`, `variant_b.html`, `variant_c.html`; PNG — `variant_{a,b,c}_<состояние>_{dark,light}_1280.png` (+ `refused_dark_1024`).
Состояния в каждом варианте: форма, ставка обязательна, подтверждение, отправка в Jira (прогресс), отказ Jira (текст как есть, введённое сохранено), сессия Jira истекла (повторный ввод пароля), смена статуса — переходы, обязательные поля («Кандидатов нет»), отказ Jira при смене статуса.

| | A. Одно окно + диалог статуса | B. Мастер по шагам | C. Боковая панель «Действия» |
|---|---|---|---|
| Идея | Модалка с формой одним экраном; подтверждение — второй экран; статус — отдельный диалог из чипа | Те же поля, разложенные на 3 шага с проверкой в конце | Панель справа с контекстом потребности и вкладками «Назначить / Статус» |
| Кликов до назначения | 2 (форма → подтверждение) | 3–4 | 2 |
| Контекст потребности на виду | строка над формой | строка над формой | да: требования, ставка, правила клиента, таблица видна |
| Ошибки и повтор | в окне, на месте | возврат на нужный шаг | в панели, на месте |
| 1024px и низкое окно | тело прокручивается, как «Профиль» | как A | панель 520px закрывает ~половину таблицы |
| Цена для Dev | низкая: `Modal wide` + формы | средняя: шаги и состояние мастера | высокая: новый компонент панели, фокус-ловушка, адаптив |
| Риски | длинная форма на 400px | лишние клики для 4 полей | не переиспользует модалки; два разных контейнера (панель + окно CV) |

## Рекомендация UX: вариант A
Форма из четырёх полей не оправдывает мастер (B) — лишние клики на частом действии. Панель (C) даёт контекст, но дорога и ломается на 1024/400px; нужный контекст (ключ, клиент, кандидат, ставка потребности и ориентир) A показывает строкой над формой. A переиспользует `Modal wide` и принятые в KON-78 компоненты.

Что взято из других вариантов: контекстная строка с ключом, клиентом и кандидатом (из C); экран подтверждения с сводкой (общий для всех) — защита от случайной записи в Jira.

## Что общего во всех вариантах (UX-решения)
1. Чип статуса в списке — кнопка со стрелкой ▾ и подписью «Сменить статус…» (доступна клавиатурой, aria-label «Сменить статус потребности 5919»).
2. Основное действие одно на экран («Назначить…» → «Подтвердить и отправить в Jira»); отмена — secondary.
3. При отказе Jira текст показывается дословно в рамке `--err`, введённые данные сохраняются, основное действие «Повторить».
4. Истёкшая сессия: окно не закрывается, над формой блок «Сессия Jira истекла» с полем «Пароль Jira»; после входа отправка продолжается.
5. Прогресс: этапы и общая полоса, закрыть нельзя до завершения (кнопка недоступна).
6. «CV по шаблону клиента…» — вторичная кнопка в блоке «Файлы»; сам диалог — KON-80 (UX-3).
