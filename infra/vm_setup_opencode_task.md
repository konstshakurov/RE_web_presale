# Задача для OpenCode: первичная подготовка ВМ vm-re.simbirsoft (KON-49, шаг 0)

Срок: по готовности. Условие: VPN/внутренняя сеть, у Константина есть пароль пользователя `user` (выдан Support). **Работа только на ВМ `vm-re.simbirsoft`** и в одном файле отчёта в репозитории. Приложение не разворачиваем.

## Зачем

Support выдал чистую ВМ (Ubuntu 24.04, 8 vCPU, 8 ГБ RAM, 132 ГБ SSD). Нужно довести её до состояния «готова к деплою» по инструкции `infra/vm_setup.md` и чек-листу из её раздела 9. Решения владельца уже приняты и внесены в инструкцию (раздел «Принятые решения»); читать нужно именно `infra/vm_setup.md` и `infra/vm.md`. Не пересказывай и не меняй решения.

## Что сделать

Выполнить по инструкции, строго по порядку, с проверкой «Ожидаемо» после каждого шага:

1. **Вход и ключ.** Подключиться по SSH `user@vm-re.simbirsoft` паролем из переменной окружения процесса `VM_SSH_PASSWORD` (никуда не писать, не логировать, не передавать аргументом командной строки, видимым в списке процессов). Отпечаток ключа хоста записать в отчёт. Если Jira/ВМ требует **принудительной смены пароля при первом входе** — остановиться и сообщить Константину (смену пароля делает владелец вручную, новый пароль ты не придумываешь и не узнаёшь).
   Сгенерировать пару ключей ed25519 `~/.ssh/id_ed25519_vm_re` на машине, где запущен OpenCode (без вывода приватного ключа в чат/отчёт/репозиторий), добавить публичный ключ в `~/.ssh/authorized_keys` на ВМ (права 700/600), проверить вход по ключу с `PasswordAuthentication=no` **отдельным новым подключением**. Только после успешной проверки — отключить вход по паролю по шагу 1.8 (файл `00-hardening.conf`, `sshd -t`, `sshd -T`, `reload ssh`, проверка отказа по паролю и входа по ключу из нового подключения). При любой неудаче — не продолжать, откатить (`rm` файла hardening + `reload`) и сообщить.
2. **Система:** `apt update`/`upgrade`, часовой пояс `Europe/Samara`, NTP (раздел 2).
3. **Безопасность:** ufw — сначала `allow 22/tcp`, `allow 443/tcp`, затем `enable` (порт 80 закрыт, подсетей не ограничиваем); `unattended-upgrades` без автоперезагрузки; fail2ban **не ставим** (раздел 3).
4. **Docker Engine и Compose v2** из официального репозитория Docker, пользователь `user` в группе `docker`, `hello-world`, `systemctl is-enabled docker` (раздел 4).
5. **Docker:** `daemon.json` (json-file 10m × 5, live-restore) (раздел 5.1). Лимиты ресурсов контейнеров (5.2) — не делать, это правка compose отдельной задачей.
6. **Каталоги** `/opt/re_web_presale` (750), `/opt/re_web_presale/tls` (700), `/var/backups/re_web_presale` (700) (раздел 6).
7. **Диск:** `df`, `lsblk`, `free`; контроль свободного места (раздел 7). Если `df` показывает ~30 ГБ вместо ~132 ГБ — **не расширять LVM**, остановиться и вернуть вывод `lsblk`/`df` в отчёт.
8. **.env** (раздел 8): шаблон `.env.example` из репозитория скопировать на ВМ в `/opt/re_web_presale/.env` (права 600), **сразу после копирования с Windows нормализовать окончания строк** (`sed -i 's/\r$//'` для `.env.example` и `.env`, затем `grep -c $'\r'` должен дать `0`; CRLF ломает проверку «задано/пусто», раздел 8.1/8.2), блок Confluence удалить, пароли БД и ключи шифрования **сгенерировать на самой ВМ** и записать в файл **без вывода значений на экран, в лог и в отчёт**; `LLM_API_KEY` и прочие значения, которых у тебя нет, оставить пустыми (владелец впишет сам). Какие значения заполнять, а какие оставить пустыми — по спискам в разделе 8.3. Проверка — только «задано/пусто» командой с `tr -d '\r'` (раздел 8.4).
9. **Чек-лист** раздела 9: прогнать пункты 1–20 и отметить результат. Пункты 19–20 (исходящий доступ к Jira и LDAP) — если не проходят, это вопрос к Support, на остальное не влияет.

## Чего НЕ делать

- Не разворачивать приложение, не запускать `docker compose up` для проекта, не создавать TLS-сертификаты, не ставить мониторинг и не писать скрипты бэкапов (это следующие части KON-49).
- Не перезагружать ВМ без необходимости (если нужно после обновления ядра — спросить Константина).
- `docker system prune --volumes` и любые массовые удаления — запрещены.
- Не менять пароль `user`, не создавать других пользователей, не трогать sudoers.
- Не печатать и не сохранять: пароль, приватный ключ, содержимое `.env`, сгенерированные секреты, токены. Не класть в репозиторий.
- Не менять код продукта, `docker-compose*.yml`, `.env.example` в репозитории (замечания — в отчёт).

## Ограничения безопасности

Одно активное подключение к ВМ за раз (кроме проверок входа по ключу из нового подключения), пауза между командами не нужна, но не запускать параллельно сканирования. Перед каждым изменением SSH/ufw — убедиться, что есть работающий откат и открытая сессия. Все выполненные команды и ключевые части вывода — в отчёт, секреты маскировать (`<скрыто>`), имена пользователей и хосты можно оставлять.

## Как запустить (Константину)

Пароль задаётся только в окне, где запускается OpenCode, и не копируется в чат и файлы:

```powershell
$env:VM_SSH_PASSWORD = "<пароль user>"
```

После завершения закройте окно или выполните `Remove-Item Env:VM_SSH_PASSWORD`.

## Область записи

На ВМ — только то, что перечислено выше. В репозитории — только `infra/vm_setup_report.md` (отчёт). Остальное не менять.

## Что вернуть

`infra/vm_setup_report.md`: что выполнено по шагам 1–9 (команда, результат, отметка ожидаемого), отпечаток ключа хоста, итог чек-листа (20 пунктов: пройден / не пройден / не проверен и причина), что не удалось и почему, отклонения от инструкции (если нужны — с причиной), версии установленного ПО (Docker, Compose), фактические значения `df -h /`, `free -h`, `timedatectl`. Явно отдельным списком: что должен сделать владелец вручную (смена пароля при принудительном требовании, резервная копия приватного ключа и `.env` в менеджер паролей, `LLM_API_KEY`, вопросы к Support).
