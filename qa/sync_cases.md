# Кейсы синхронизации Jira (Pre.QA-7, KON-63)

Область: FR-028, FR-029, FR-034, FR-035, NFR-002, NFR-008 (опрос, пауза, отказы, кэш, список на 500 записей).
Код продукта: `backend/app/sync/` (KON-35). Стенд: `qa/stand/` (отдельный compose-проект, тестовый LDAP,
фейк Jira `qa/stand/fake_jira.py`); живая Jira и VPN не используются. Живая часть (реальные ответы Jira Server
8.13.0, объёмы, время сессии) вынесена в `architecture/probes/KON-63_opencode_task.md` и здесь не проверяется.

Уровни: **S** - автотест на стенде (`backend/tests/qa/`), **U** - тест Dev (`backend/tests/unit/`), QA не
дублирует. Интервалы стенда: потребности 20 с, сотрудники 30 с, пересмотр паузы 5 с, пересечение окна 5 с
(`qa/stand/.qa.env`); умолчания 300 / 3600 / 15 / 60 с проверяются отдельно (`test_nfr008_default_intervals_*`).
Для фильтров ожидание берётся независимым SQL по кэшу, а не повтором логики API.

Файлы S: `P` = `test_sync_poll_qa.py`, `F` = `test_sync_failures_qa.py`, `C` = `test_sync_cache_qa.py`
(общие помощники - `_sync_qa.py`). Запуск (последовательно, не параллельно с другими стендовыми наборами):
`cd backend && python -m pytest tests/qa/test_sync_poll_qa.py tests/qa/test_sync_failures_qa.py tests/qa/test_sync_cache_qa.py -s`.

### 3.2 Наблюдения (не дефекты, для аналитика и Dev)

1. Текст отказа Jira приходит с техническим префиксом клиента: `GET /rest/api/2/search -> 403 : <текст Jira>`.
   Текст Jira содержится целиком (FR-029 выполнен); префикс без query-строки, секретов нет.
2. `rates_dropped` попадает только в журнал (`app.sync.service`, поле `rates_dropped`), а не в ответ
   `POST /sync/refresh`; у отброшенной ставки `unit` и `proposer` остаются в ответе при `amount = null`.
   Требования этого не оговаривают.
3. «Обновить» при отсутствии сохранённого токена Jira отвечает 409 с `detail.state = "not_checked"` и пустым
   `message`, а не `needs_reauthorization` (так отвечает `require_jira_ok`). Достижимо при ручном удалении
   секрета; для пользователя без текста подсказки. Если сценарий реален (например, после смены ключа
   шифрования), нужен единый ответ - решает Dev/аналитик.
4. Фоновый опрос с отвергнутым токеном (401) не обращается к Jira, пока пользователь не войдёт заново, даже
   если Jira уже отвечает (поведение по ADR-004, проверено SYNC-06). При одном пользователе это значит:
   данные не обновляются до следующего входа, в интерфейсе виден `needs_reauthorization`.
5. Старые сессии приложения не отзываются при повторном входе (на стенде у qa-jirablock 46 живых сессий).
   Влияет на подсчёт «активных пользователей» только тем, что пользователь с неотозванной сессией считается
   активным до `expires_at` (SESSION_TTL_HOURS = 8): опрос после выхода пользователя может идти до 8 ч,
   если он закрыл вкладку без выхода - это штатное поведение, но не «вышли все» в узком смысле.

### 3.4 Не проверялось и почему

- Реальная Jira Server 8.13.0 (формат ставки, валюты в живых данных, лимиты поиска, время сессии,
  CAPTCHA при повторных неверных паролях) - живая проба OpenCode, файл `architecture/probes/KON-63_opencode_task.md`.
- Настоящие интервалы 300 с / 3600 с в работе: на стенде 20 / 30 с; значения по умолчанию проверены
  тестом настроек, а возраст штампа в 5 мин - расчётом (интервал + цикл).
- Одновременная запись в кэш из api и worker (гонка «Обновить» и фонового опроса) проверена косвенно:
  `busy` отдаётся Dev-тестом `test_second_run_while_first_is_running_is_busy`; на стенде повтор при `busy`.
