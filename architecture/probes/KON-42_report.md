## 1. Что реализовано

### 1.1 Порт — `backend/app/integrations/jira/port.py`

Добавлены типы записи той же формы, что в `app.assign.port`:

```python
@dataclass(frozen=True)
class AllowedValue:      id: str; name: str
@dataclass(frozen=True)
class TransitionField:   field_id: str; name: str; required: bool; allowed_values: tuple[AllowedValue, ...] = ()
@dataclass(frozen=True)
class TransitionView:    id: str; name: str; to_status: str; fields: tuple[TransitionField, ...] = ()
```

и методы в протокол `JiraPort` (реализация — `JiraAdapter`):

| Метод | Сигнатура порта |
|---|---|
| `get_transitions` | `(sealed_token, issue_key) -> list[TransitionView]` |
| `do_transition` | `(sealed_token, issue_key, transition_id, *, fields, comment=None) -> None` |
| `set_fields` | `(sealed_token, issue_key, fields) -> None` |
| `add_comment` | `(sealed_token, issue_key, body) -> None` |
| `attach_file` | `(sealed_token, issue_key, filename, content, mime_type) -> None` |
| `assign_candidate` | `(sealed_token, issue_key, username) -> None` |

Типы **продублированы**, а не импортированы из `app.assign`: направление
зависимостей — `assign → integrations`, обратной зависимости быть не должно.
Форма совпадает намеренно, чтобы мост снялся без правки сервиса.

### 1.2 Адаптер — `backend/app/integrations/jira/adapter.py`

- `_write(sealed_token)` — контекст-менеджер: `ValueError` клиента (пустой
  комментарий/файл, пустой набор полей) переводится в
  `JiraIntegrationError(code=jira_error)` — ровно как делал мост
  `assign.jira_write._call`.
- `get_transitions` → `_transition_view()` (единственное место, где форма
  `jira_client.Transition` пересекает границу порта).
- `do_transition` → `JiraClient.transition(..., comment=..., validate=False)`:
  комментарий уходит через `update.comment.add` (его ставит `JiraClient`);
  `validate=False` — как в мосте (один вызов, без повторного запроса переходов,
  NFR-009).
- `set_fields`, `add_comment`, `attach_file` (`size_limit=0`, заголовок
  `X-Atlassian-Token: no-check` ставит клиент), `assign_candidate`
  (`JiraClient.assign`).
- `__init__.py` интеграции экспортирует новые типы.

Лимит 10 с и «повторов нет» наследуются от `JiraConfig` (NFR-009), как в KON-34.

## 2. Совпадение сигнатур с `app.assign.port`

Эталон — `backend/app/assign/port.py` (`JiraWritePort`) и мост
`backend/app/assign/jira_write.py`. Сравнение (`token`/`key` в эталоне ⇄
`sealed_token`/`issue_key` в `JiraPort` — имена иные, позиции/виды те же):

| Метод | Эталон `JiraWritePort` | `JiraPort` |
|---|---|---|
| `get_transitions` | `(token, key)` | `(sealed_token, issue_key)` |
| `do_transition` | `(token, key, transition_id, *, fields, comment)` | `(sealed_token, issue_key, transition_id, *, fields, comment=None)` |
| `set_fields` | `(token, key, fields)` | `(sealed_token, issue_key, fields)` |
| `add_comment` | `(token, key, body)` | `(sealed_token, issue_key, body)` |
| `attach_file` | `(token, key, filename, content, mime_type)` | `(sealed_token, issue_key, filename, content, mime_type)` |
| `get_issue` | `(token, key)` | уже был в `JiraPort` |

`JiraAdapter` теперь удовлетворяет `JiraWritePort` (проверено
`isinstance`, `TestWritePortShape`): мост `JiraAdapterWritePort` заменяется
созданием `JiraAdapter` без правки `assign/service.py`. Разбор `ValueError` и
форма `TransitionView` в `_transition_view` совпадают с мостом **дословно**.

**Расхождение (D5).** В `app.assign.port.JiraWritePort` метода `assign_candidate`
**нет** — эталон содержит шесть методов без него. KON-42 перечисляет
`assign_candidate` наравне с остальными. Реализовал его как сеттер `assignee`
(`JiraClient.assign`, тело `{"fields": {"assignee": {"name": <логин>}}}`) и
выношу расхождение на решение: либо `assign_candidate` — это «назначить
исполнителя» (тогда эталон нужно дополнить), либо это составное действие
(профиль + исполнитель + переход), которое должно жить в сервисе, а не в порту.

## 4. Z1. Переход 21 «Кандидат назначен»

`GET /issue/ANALYTICS-5925/transitions?expand=transitions.fields` из «Поиск
кандидата» отдаёт 4 перехода: **21, 171, 181, 801**. У перехода 21 поля:
`customfield_10707`, `customfield_10712`, `customfield_11602`, `customfield_11603`,
`attachment` — **у всех `required:false`**.

| Вопрос Z1 | Ответ |
|---|---|
| Обязательные поля по REST | **Ни одного.** Но Jira накладывает **необъявленный** валидатор «Вложение» — см. ниже. |
| Комментарий для 21 | **Не нужен**: переход прошёл (шаг 10) без комментария. Для 171 комментарий **нужен** (KON-30: 400 `errors.comment`). |
| Формат option при PUT | `{"value": "…"}` — **работает** (шаг 1, 204). |
| Формат option при переходе | `{"id": "…"}` — **работает** (KON-30: 171 с `{"id":"23300"}` → 204; на шаге 6 Jira к форме поля не придиралась). |
| Допущение backend «ставка через PUT `{"value": …}` вне перехода» | **Опровергнуто** для этой потребности: PUT `20810`/`20809` → **400 «not on the appropriate screen»** (шаги 2–3). Поля ставки есть только на экране перехода **801**. |

**Главное открытие Z1 — необъявленный валидатор «Вложение».** Даже при уже
приложенном к задаче CV переход 21 отклоняется, пока
`customfield_11506` «Нужно предоставить CV» = «Да»:

- шаг 6 (CV приложен) → **400** `Необходимо в поле "Вложение" добавить CV кандидата`;
- шаг 7 (вложение полем перехода) → 400 `Field does not support update 'attachment'`
  (у поля `operations: []`);
- шаг 8 (multipart) → 415;
- шаг 9–10: `customfield_11506`=«Нет» снимает валидатор, переход выполняется.

То есть валидатор **условен** и зависит от правила клиента «Нужно предоставить
CV». См. D1.

## 8. Расхождения с допущениями backend

1. **Ставка вне перехода.** Backend кладёт ставку в `direct` (`set_fields`) для
   полей, которых нет на экране перехода 21. На `ANALYTICS-5925` это даёт **400**
   (шаги 2–3): поля `20809`–`20812` не на экране редактирования, а только на
   переходе **801**. Значит `assign.assign()` со ставкой на этой потребности
   **откажет** на шаге `STEP_FIELDS`. См. D2.
2. **Обязательные поля перехода 21.** Backend считает обязательными только
   поля с `required:true` из `transitions.fields`. У 21 таких нет; фактически
   обязателен **экранный** валидатор «Вложение» (условно по `11506`). Это тот
   же класс расхождения, что и «комментарий 171» в KON-30. См. D1.

## 9. Дефекты

### D1 (блокирующий, Jira-процесс). Переход 21 не выполняется через REST, если «Нужно предоставить CV» = Да

- **Шаги:** приложить CV к задаче → `POST /transitions` id=21.
- **Ожидалось:** переход выполнен (CV приложен).
- **Факт:** **400** `attachment: Необходимо в поле "Вложение" добавить CV кандидата`,
  хотя вложение на задаче есть. `attachment` в `fields` → 400 `Field does not
  support update 'attachment'`; multipart → 415.
- **Условие:** `customfield_11506` «Нужно предоставить CV» = «Да». При «Нет»
  переход проходит (шаг 10).
- **Следствие:** приложение (KON-43/Dev-18) **не может** назначить кандидата на
  потребность с этим правилом напрямую через REST.

**Решение согласовано с Константином (в Jira доработок не будет):**

1. Jira-side фикс валидатора — **отклонён** (Jira не дорабатывают).
2. **Основной путь — обход через `customfield_11506`.** Перед переходом 21
   выставить `customfield_11506` = «Нет» → выполнить переход 21 → вернуть
   `customfield_11506` = «Да». Порядок и условия:
   - CV прикладывается **до** перехода (как и сейчас);
   - переключение и возврат «Да» — **в одном шаге** назначения, чтобы при
     падении посередине остаться в предсказуемом состоянии; возврат «Да»
     выполнять даже при ошибке перехода (`finally`);
   - если конечный статус задачи по правилам не допускает редактирование
     `customfield_11506` через `PUT` — возврат «Да» может дать 400; тогда
     значение остаётся «Нет», и это нужно показать оператору явно.
3. **Резервный путь — вариант 3.** Если обход не сработал (Jira отклонила
   переключение `11506` или переход всё равно вернул 400 по «Вложению»):
   назначение через интеграцию не выполняется, оператору показывается понятная
   ошибка с предложением назначить вручную в Jira; введённые данные не теряются
   (FR-029, NFR-009). Комментарий к переходу/история Jira при этом не портятся.

**Цена обхода (зафиксировать в реализации):** это отклонение от FR-015
(«Система ТОЛЬКО информирует; отправка не блокируется» — приложение не должно
менять правило клиента) и +2 записи к сессии (NFR-009). Отклонение осознанное и
согласовано; в коде его нужно пометить комментарием-ссылкой на этот отчёт.

### D2 (блокирующий для ставки). Поля ставки не выставляются через PUT

- **Шаги:** `PUT /issue` `customfield_20810`/`20809` (не на переходе).
- **Ожидалось (допущение backend):** 204.
- **Факт:** **400** `Field 'customfield_20810' cannot be set. It is not on the
  appropriate screen, or unknown.` Поля `20809`–`20812` входят только в экран
  перехода **801** «В найм», не в экран редактирования.
- **Следствие:** ставку можно записать только **полями перехода**, а не отдельным
  `PUT`. В сценарии «назначить» (21) её записать нельзя.

**Решение (оптимальное, Jira не дорабатывают) — ставка пишется на найме (801).**

1. **Ставка «от производства», если она отправляется в Jira, уходит полями
   перехода 801 «В найм»**, а не отдельным `PUT` и не в теле перехода 21:

   ```json
   {
     "transition": {"id": "801"},
     "fields": {
       "customfield_20809": 3000,
       "customfield_20810": {"id": "20999"},
       "customfield_20811": {"id": "21001"},
       "customfield_20812": {"id": "21006"}
     },
     "update": {"comment": [{"add": {"body": "…"}}]}
   }
   ```

   `20809` — число; `20810`/`20811`/`20812` — справочники `{"id": …}`
   (НДС «Да» = 20999, руб. = 21001, ч (час) = 21006 — подтверждено пробой).
   Эти три поля у 801 ещё и `required:true` (KON-30), поэтому ставка на 801
   задаётся вместе с ними — это единственное корректное место.

2. **В сценарии «Назначить» (21) ставку не трогаем.** Поле «Планируемая ставка»
   остаётся пустым до найма; это осознанно, а не ошибка.

3. **Правка backend (KON-43/Dev-18):** в `assign` перестать класть ставку в
   `direct` (`set_fields`); атрибуты ставки формировать в `fields` **перехода
   801**. Порт менять не нужно — `JiraPort.do_transition` уже принимает
   произвольные `fields`.

4. **Если ставку всё же нужно задавать при назначении** — это невозможно без
   доработки Jira (экран перехода 21), а доработок не будет. Значит
   единственный путь — фиксировать ставку на 801; логику «ставка от
   производства → уходит на 801» нужно закрепить в требованиях (FR-015/FR-018).

### D3 (мелкий). Неизвестный id перехода → 500

- **Шаги:** `POST /transitions` id=`999999`.
- **Ожидалось:** 400/404 (неверный запрос).
- **Факт:** **500** `Внутренняя ошибка сервера` → карта ошибок даёт
  `jira_unavailable` (**retryable**). Приложение может повторять заведомо
  неверный переход, считая Jira недоступной.

## 11. Безопасность

- Одна сессия, пауза ≥ 250 мс между запросами; записи только в `ANALYTICS-5925`
  и синтетический ключ; массовых записей и удалений нет; неверный пароль не
  подбирался.
- Пароль/токен — только в переменных окружения процесса; в репозиторий, логи и
  отчёт не попадают. В пробных скриптах (временные, вне репозитория) тело
  логина и cookie маскировались.
- Тестовые секреты — с префиксом `FAKE_` (`FAKE_RAW_TOKEN`,
  `FAKE_no_such_login_kon42`, `FAKE_no_such_profile_kon42`).
- Реальные данные (ФИО, логины, имя файла CV) в репозиторий не перенесены;
  в отчёте обезличены.
- `TestWriteNoSecrets` проверяет, что логи записи не содержат пароль, сырой и
  запечатанный токен.
