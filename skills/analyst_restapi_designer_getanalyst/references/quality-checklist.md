# Финальная проверка постановки

Перед ответом пройти все применимые пункты и молча исправить документ.

## Граница задачи

- Описан ровно один REST API-метод.
- До проектирования один раз запрошены отсутствующие доступные материалы: Base URL, архитектура, макет, модель БД и особенности алгоритма; уже переданные сведения повторно не запрашивались.
- Отсутствие опционального материала не остановило работу после ответа пользователя и не привело к выдуманным деталям.
- Постановка не содержит OpenAPI, Postman, SQL DDL, тест-кейсы или отдельный дизайн БД.
- Все нюансы, рекомендации и допущения находятся до постановки, а не внутри.
- В постановке нет `TBD`, `TODO`, подсказок, конкурирующих вариантов и комментариев аналитика.
- «История изменений» и «Связанные документы» добавлены только при наличии реальных данных.
- «Ограничения» содержит только исключения из scope текущей задачи, а не доступы, валидации или НФТ.

## Структура требований

- В «Доступах» описаны аутентификация, авторизация, роли/scopes, владение и условия допуска.
- Rate limit, timeout, производительность, payload и надежность находятся в «Нефункциональных требованиях».
- НФТ измеримы, релевантны и не содержат выдуманных чисел.
- «Контракт запроса» отделен от примера запроса и алгоритма backend.

## Контракт

- HTTP-метод соответствует бизнес-семантике, safety и idempotency.
- Если Base URL, API name и версия подтверждены, они согласованы между контрактом и примерами; если не подтверждены, используется относительный URI без выдуманного домена или версии.
- Endpoint, path/query/body и JSON используют единый naming convention.
- Headers применяются по назначению; `Content-Type` не добавлен к GET без body как обязательный request header.
- Каждый request-параметр имеет required, nullable, тип/формат, ограничения, default и ошибку.
- Обязательность и `nullable` response-полей подтверждены, а не выведены из примера, статуса объекта или структуры БД.
- Валидный JSON не содержит комментариев, неправильных кавычек или кириллической `с` в `code`.
- Даты/timezone, duration, деньги и файлы имеют однозначный формат и преобразование.

## Ответы и ошибки

- Success status соответствует результату (`200`/`201`/`202`/`204`).
- При `201` рассмотрен `Location`.
- Пустая коллекция возвращает `200` и пустой массив.
- `401`, `403`, `404`, `409`, `422`, `429`, `500`, `502`, `503`, `504` используются только по их причине.
- `408` не используется для backend timeout без подтвержденного проектного правила и предварительного предупреждения.
- Все ошибки имеют один формат и уникальные стабильные code/errorCode.
- В client response нет stack trace, SQL, internal URL, credentials и provider secrets.
- Поля JSON-примеров совпадают с таблицами и маппингом.

## Алгоритм и данные

- Использованы только подтвержденные названия компонентов, сервиса-владельца, БД и внешних систем; без архитектурной схемы применены нейтральные логические роли.
- Порядок authentication, authorization, validation и business checks однозначен.
- Для каждой ошибки указан этап остановки.
- Все response-поля имеют источник или формулу.
- Физические таблицы, столбцы, связи и SQL указаны только при наличии переданной модели БД; иначе маппинг выполнен на логическом уровне.
- Нет прямого доступа микросервиса к чужой БД.
- Для записи нескольких таблиц определена транзакция/атомарность.
- Для бронирования/уникальности есть constraint/lock, а не только предварительный `SELECT`.
- Для POST оценены duplicate/idempotency и безопасный retry.
- Для PUT/PATCH оценены конкурентные изменения и семантика отсутствующего поля/`null`.
- Для DELETE явно выбран вид удаления и учтены связанные read-модели, аудит и cache invalidation.
- Для интеграции определены timeout, retry eligibility, fallback и безопасный error mapping.

## Списки и кэш

- Фильтры имеют AND/OR, нормализацию и лимиты.
- Сортировка имеет whitelist, default и уникальный tie-breaker.
- Pagination стабильна; `count/pageSize/totalCount` не неоднозначны.
- Cursor непрозрачен, связан с фильтрами/сортировкой и проверяется.
- Решение о кэшировании принято явно; кэш не добавлен механически.
- Cache key учитывает representation и security scope.
- Определены TTL, invalidation, failure mode и stampede protection, если Redis используется.
- Не смешаны Redis cache и HTTP/CDN cache.

## НФТ и эксплуатация

- Логи не содержат токены, PII и полный чувствительный payload.
- Метрики не используют high-cardinality labels.
- Трассировка передается в downstream.
- Алерты имеют подтвержденные пороги либо перечислены без вымышленных чисел.
- Для mutation/delete добавлен аудит.

## Финальный формат

- Разделы идут в порядке шаблона GetAnalyst: метаданные документа, общее описание, доступы, НФТ, ограничения, контракт, примеры, реализация, кэширование, маппинг, эксплуатация.
- Неприменимые разделы исключены, а не заполнены лишними пояснениями.
- Постановка читается как утвержденное техническое задание.
- Авторский блок находится вне постановки и является последним элементом сообщения.
