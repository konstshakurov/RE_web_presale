## Сравнение вариантов

| | **A — по референсу, inline-блоки** | **B — поповеры + компактная плотность** |
|---|---|---|
| Идея | В точности референс; раскрытие «Правила»/кандидатов — как сейчас, широкой полосой под строкой | Тот же стиль, но раскрытие — плавающая панель под ячейкой: таблица не перестраивается; плотность строк повышена |
| Плюсы | Максимальное совпадение с референсом (скрин 3); минимум изменений поведения — предсказуемо для QA; широкие блоки (правила в 2 колонки, карточки кандидатов) показываются без стеснения | Строка и позиция прокрутки не «прыгают»; можно сверить несколько строк подряд; на 2000+ строк компактная плотность показывает больше без прокрутки |
| Минусы | Открытый блок сдвигает таблицу вниз; при сверке строк теряется контекст | Два поповера перекрываются; блок правил 660px тесноват на 1024; позиционирование и закрытие (клик вне, Esc) — дополнительный код |
| Цена для Dev | Минимальная: переоформление существующих `needs__details`-строк + новые токены | + позиционирование поповера (CSS absolute в ячейке), клик-вне/Esc, `aria-haspopup="dialog"`; ~1–2 дня сверху |

Вариант 0 нужен только как точка сравнения — его не выбирают.

## Рекомендация

**Вариант A.** Причины: (1) владелец просил «в точности по референсу» — A совпадает с ним
максимально, включая ширину строк; (2) FR-036 v1.3 прямо отдаёт «раскрывающееся поведение
кнопки» на решение этого design-кейса — A сохраняет текущее поведение, значит меньше риска
и меньше объём Dev; (3) блок правил клиента широкий (две колонки, референс «Сотрудники —
правила» показывает именно широкую полосу) — inline показывает его лучше поповера.
B имеет смысл, если владелец приоритизирует работу с длинным списком без «прыжков»
таблицы — тогда компактную плотность можно забрать и в A отдельным решением.

## Открытые вопросы владельцу

1. **Пагинация** — вне пунктов 3.1–3.12: в референсе нумерация страниц («‹ 1 2 3 … 98 ›», «20 строк»), сейчас — «Назад/Вперёд» + «На странице». В прототипах оставлена текущая. Менять?
2. **Шеврон ⌄ внутри чипа статуса** (есть на скринах 3 и 4): в прототипах он декоративный — интерактивен только «Изменить ⌄» (FR-011). Оставить декоративным или убрать из чипа?
3. **Тёмная тема пилюль**: FR-038 v1.3 «тёмная тема не меняется» → в прототипах тёмные пилюли остались в текущем виде (фон `--panel-2`, цветной текст). Подтвердить; альтернатива — яркие пилюли в обеих темах.
4. **Точные цвета референса**: у прототипа только PNG — ярче-значения подобраны с контрастом белого ≥ 4.5:1 (см. `brief.md`). Если есть исходник макета — сверить hex до `decision.md`.
5. **Чип «Суб»** добавлен для демонстрации 3.9; появляется только если группа «Субподряд» настроена в «Настройках» (FR-035). Подтвердить состав групп для скрина утверждения.
6. **Стрелка сортировки ▼ у «Создана»** — на референсе её нет; сортировка по FR-034 осталась. Оставить как сейчас?

## Допущения

1. Состав меню «Изменить ⌄» в прототипах — по FR-026 для показанного статуса (для «Требуется кандидат»: Поиск / Найм / Кандидатов нет); скрин 4 задаёт вид пунктов, не состав.
2. Состав групп чипов и все числа (счётчики, даты, ставки) — вымышленные, для демонстрации.
3. Имя пользователя в шапке («Анна Смирнова») — вымышленное; логотип — заглушка, Dev использует ассеты KON-135 (logo_head.svg / logo_wordmark.svg).
4. Активная группа «Все статусы» — чтобы показать все цвета пилюль в одном экране; стартовая группа по FR-035 — «Без кандидата».
5. Состояния загрузки/ошибки/пусто CR-022 не меняет, в прототипах не показаны (вне скоупа).
6. «Контракт» = «Прямой контракт» / «Суб» — по формулировке FR-034 v1.2.
