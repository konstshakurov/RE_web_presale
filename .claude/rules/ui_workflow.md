# UX-воркфлоу: изменения интерфейса идут через согласование

Правило владельца (Константин, с 14.10.2026): **любые задачи и изменения в UI
согласуются с ним до реализации.** Правило наследуют все агенты разработки.

## Цепочка

```
Аналитик (спецификация) → Arch (декомпозиция) → UX (варианты) → [апрув владельца] → Dev → QA
```

1. **Arch** раскладывает спецификацию на задачи по ролям, включая `Pre.UX-N`. Каждая задача
   с видимым изменением интерфейса получает пару: `Pre.UX-N` → `Pre.Dev-N`, где Dev зависит
   от UX. Чисто серверные задачи UX не требуют.
2. **UX** проектирует 2-3 варианта (прототипы в `design/<KON-N>/`), готовит рекомендацию.
3. **Владелец** выбирает вариант или даёт правки. До явного апрува Dev не стартует.
4. **UX** фиксирует `design/<KON-N>/decision.md` со статусом `approved` и комментарием в
   Linear. Только это — вход для Dev.
5. **Dev** реализует по `decision.md`. Отклонение от решения — только через возврат к UX.
6. **QA** проверяет UI против критериев приёмки из `decision.md`.

## Что считается изменением UI

Новый или изменённый экран, компонент, поток, расположение элементов, тексты интерфейса,
состояния (пусто/ошибка/загрузка), стили и токены. Не считается: исправление ошибки без
видимого изменения, рефакторинг, серверная логика.

## Приёмка реализации (с 14.10.2026, поручение владельца)

Реализацию UI по утверждённому `decision.md` принимает **QA-агент**; апрув владельца на
реализацию не требуется. Владельцу апрув нужен на дизайн (шаг 3) и на изменение скоупа.

1. Dev завершает задачу и переводит её в «На проверке QA» (код не коммитится без запроса).
2. QA сверяет стенд с критериями приёмки из `decision.md` и PNG макета: ключевые экраны,
   обе темы, 1280 и 1024; результат — в `qa/` и комментарием в Linear (Pass / замечания по
   пунктам критериев). Расхождения QA заводит багами на Dev-задачу, а не владельцу.
3. Pass → задача Done. Владельцу приходит короткая сводка, а не запрос на проверку.

К владельцу возвращаются: изменение дизайна или скоупа, расхождение макета и требований
(CR аналитику, 5.4), вопрос вкуса, который критерии приёмки не закрывают.

## Ворота для Dev

Задача с изменением UI без `design/<KON-N>/decision.md` со статусом `approved` — **не
реализуется**. Dev называет причину, сообщает номер ожидаемой UX-задачи и ничего не пишет
во `frontend/src/`. Исключение — только прямое указание владельца в чате.

## Кто что пишет

| Область | Писатель |
|---|---|
| `design/` | только `ux` |
| `frontend/src/` | только `dev` (по `decision.md`) |
| `.claude/skills/` | владелец платформы агентов; агенты читают |

## Границы

- UX не меняет требований; пробел или противоречие — через аналитика (CR, 5.4).
- Решения, меняющие скоуп или срок, — рекомендация; финал за владельцем.
- Предупреждай, не блокируй: если UX-согласование задерживает критический путь, назови
  это владельцу и предложи вариант («один вариант + как сейчас» для точечной правки).
