## Слои кода

```
UI (React) ─► api (FastAPI): auth/router · sync/router · assign/router
                   │                          │
        jira_session.service          sync.service (+ worker/scheduler)   assign.service
                   └──────────────┬───────────┴──────────────┬────────────────┘
                                  ▼  JiraPort (backend/app/integrations/jira/port.py)
                          JiraAdapter (adapter.py) — запечатывает/открывает токен, карта ошибок
                                  ▼
                          src/jira_client (JiraClient, httpx) ──► Jira REST
```

| Модуль | Роль |
|---|---|
| `src/jira_client/` | низкоуровневый клиент: запросы, вход, шифрование токена (`TokenVault`, AES-256-GCM), модели, карта исключений |
| `backend/app/integrations/jira/port.py` | единственный интерфейс Jira для приложения (`JiraPort`): `login, check_session, search_incremental, get_issue, get_epic, get_epic_children, get_transitions, do_transition, set_fields, add_comment, attach_file, assign_candidate, set_rate` |
| `…/adapter.py`, `errors.py` | реализация порта; единая карта отказов (`needs_reauthorization / no_permission / auth_failed / login_blocked / jira_unavailable / jira_error`) |
| `backend/app/jira_session/` | создание и хранение сессии Jira при входе; статус `ok / not_checked / needs_reauthorization / …`; зависимость `require_jira_ok` |
| `backend/app/sync/` | опрос и кэш (потребности, сотрудники, эпики), штамп «актуально на», `scheduler` в процессе `worker` |
| `backend/app/assign/` | назначение кандидата, статус-действия, ставка |

## Модель доступа (ADR-005, решение владельца 05.10)

* Технической учётки и Application Link **нет**. Каждый пользователь действует своей сессией Jira.
* Логин и пароль Jira = LDAP. При входе в приложение один ввод пароля используется дважды в рамках одного HTTP-запроса: LDAP bind и `POST /rest/auth/1/session` (хук `after_login_hooks` → `JiraSessionService.establish`).
* Пароль не сохраняется (ни в БД, ни в логах, ни в трассировке). Хранится только сессионный токен: запечатан `TokenVault` (AES-256-GCM, ключ из env), затем повторно шифруется ключом приложения в `secret_store` (kind `jira_session`). Наружу (API, UI) токен не отдаётся.
* Истёкшая сессия Jira → `409 needs_reauthorization` → UI просит пароль → `POST /auth/jira-relogin`; введённые пользователем данные остаются на клиенте.
* Отказ Jira при верном LDAP: вход в приложение выполняется, работа с Jira блокируется (`require_jira_ok`: 409, либо 503 при недоступности) с текстом отказа.
* Запись видна в истории Jira под учёткой пользователя (BR-001); права определяет Jira (BR-001, FR-026).
* Фоновый опрос идёт токеном любого активного пользователя (только чтение); без активных сессий опрос приостановлен (штамп `paused`).

## Режимы работы

| Режим | Кто | Что |
|---|---|---|
| Чтение, фон | `worker` (собственный цикл `Scheduler`, один фоновый поток) | потребности каждые 5 мин (инкрементально по `updated`), сотрудники раз в час; первый запуск сразу при старте; период считается от начала цикла |
| Чтение, по кнопке | `POST /sync/refresh` | токен самого пользователя, инкрементально; параллельный запуск блокируется (`busy`) |
| Чтение, при открытии | `GET /sync/epics/{key}` | эпик + правила клиента + потребности эпика (Agile API); кэш 1 час, `?refresh=true` — принудительно |
| Запись | `assign/router` | назначение, смена статуса, комментарий, вложения, ставка — токеном пользователя |

## Особенности Jira 8.13.0, обнаруженные пробами (не очевидны из документации Atlassian)

1. `parent` в JQL всегда даёт 0 результатов; дети эпика — только Agile API или `"Epic Link"` (`customfield_10101`) — KON-30.
2. Комментарий перехода принимается только как `update.comment[].add`; `fields.comment` → 400. У перехода 171 «Кандидатов нет» комментарий обязателен, хотя REST не объявляет его обязательным — KON-30.
3. Неизвестный/недоступный `transition.id` → HTTP 500 (не 4xx); приложение трактует это как `jira_error`, а не «Jira недоступна» — KON-42 (D3).
4. Переход 21 «Кандидат назначен» при `customfield_11506 «Нужно предоставить CV» = Да` отклоняется экранным валидатором «Вложение» даже с приложенным CV; обход: 11506→«Нет» → переход → 11506→«Да» (всегда, `finally`) — KON-42 (D1), CR-006.
5. Поле `customfield_11602 «Поддержка»` проверяется на переходе 21, хотя REST отдаёт `required:false`; всегда отправляется «Не требуется» — KON-42 (Z1), KON-122.
6. Ставка пишется кнопкой Jira (ScriptRunner `POST /rest/scriptrunner/latest/custom/rateCalculationLogic`); Jira отвечает 200 и **без записи** при неверном id справочника или без `customfield_21105`; 500 — на пустую ставку/несуществующий ключ. Поэтому адаптер валидирует id до отправки и перечитывает поле после записи — KON-99, CR-008.
7. `GET /issue/{key}/attachment` отдаёт 404; вложения читаются через `fields=attachment`.
8. Agile `GET /epic/{key}` возвращает плоский объект (`name, summary, done…`), параметр `fields` игнорирует.
9. `POST /rest/auth/1/session` принимает только плоское тело `{"username","password"}`.
10. Jira не присылает отсутствующие поля вовсе — все ключи читаются через `.get()`.

## Мониторинг и логи (MON)

* Healthcheck `worker`: файл-пульс `WORKER_HEARTBEAT_PATH` (по умолчанию `/tmp/worker.heartbeat`), обновляется каждые 5 с независимо от длительности опроса.
* Состояние опроса — таблица `sync_state` (`last_success_at`, `last_error_code`, `last_error`), штамп `GET /sync/status`.
* В логи не попадают пароли, токены, тексты комментариев (NFR-006; `logging_setup.redact`); тексты отказов Jira усекаются до 2000 символов.
