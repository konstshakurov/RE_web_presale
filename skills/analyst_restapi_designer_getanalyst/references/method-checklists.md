## GET одного ресурса

- Убедиться, что операция не изменяет бизнес-состояние.
- Идентификатор разместить в path и валидировать до обращения к БД.
- Определить поведение для отсутствующей, скрытой, архивной и логически удаленной записи.
- Проверить доступ к конкретному объекту, а не только роль.
- Вернуть `200` с детальным представлением либо `404`/`403` по принятой политике раскрытия.
- Рассмотреть `ETag`/`If-None-Match`, HTTP cache или Redis только при подходящей стабильности и повторяемости чтений.
- Если response зависит от пользователя, языка, валюты, роли или tenant, отразить это в cache policy/key либо запретить shared cache.
- Проверить N+1 для связанных массивов и размер payload.

## GET списка

- Пустая выборка возвращается как `200` с пустым массивом.
- Определить фильтры, AND/OR, текстовый поиск, сортировку и pagination.
- Добавить стабильный `ORDER BY` с уникальным tie-breaker.
- Выбрать offset для небольших/стабильных наборов либо cursor для больших и быстро меняющихся.
- Определить смысл `count`, `pageSize`, `totalCount`; не использовать неоднозначное поле.
- Ограничить `limit`, длину поисковой строки и число значений в массивных фильтрах.
- Проверить индексы под фильтры/сортировку, M:N duplicates, стоимость `totalCount` и N+1.
- Принять явное решение о кэшировании. Не добавлять кэш, если данные персональны, почти уникальны, должны быть строго свежими или hit rate будет низким.
- Для логически удаляемых ресурсов явно исключить `isDeleted = true`/`deletedAt IS NOT NULL` и учесть архив по правилам метода.

## QUERY

QUERY определен RFC 10008 как safe и idempotent method с request content.

- Использовать для безопасного поиска/вычисления, когда содержательное описание запроса велико или неудобно для URI.
- Для коротких простых фильтров предпочесть GET.
- Не изменять целевой бизнес-ресурс как ожидаемый эффект.
- `Content-Type` обязателен; отсутствие отклонять 4xx, неподдерживаемый media type — `415`.
- Определить `Accept`; неподдерживаемое представление — `406`, если negotiation реализован.
- Валидировать syntax content отдельно от семантики; `400` и `422` разделять по стандарту проекта.
- При JSON-body определить обязательность `{}`, nullable, неизвестные поля и максимальный размер.
- Разрешить QUERY в API Gateway, service mesh, WAF, CORS `Access-Control-Allow-Methods` и OPTIONS; браузер выполнит preflight.
- При необходимости сообщать поддержку через `Allow` и `Accept-Query`.
- Ответ QUERY может кэшироваться. Cache key обязан учитывать request content и значимые metadata.
- Не включать `X-Request-Id`, trace id или JWT целиком в query identity/cache key.
- Для cursor вычислять query hash по canonical content + sorting и проверять, что cursor относится к тому же запросу.
- Проверить возможность автоматического retry инфраструктурой.
- Если инфраструктура не поддерживает QUERY, вынести это как нюанс до постановки и согласовать GET или POST fallback.

## POST создания или команды

- Для создания ресурса обычно вернуть `201 Created`, representation и `Location`.
- Для асинхронного запуска вернуть `202 Accepted` и ресурс/идентификатор операции.
- Для команды без нового ресурса выбрать `200` или `204` по наличию response body.
- Не считать POST идемпотентным автоматически.
- Для заказа, платежа, бронирования, записи, отчета и дорогой команды согласовать `Idempotency-Key` или иной механизм защиты от дублей.
- Для idempotency определить scope, TTL, request hash, сохраненный status/response и конфликт одинакового ключа с другим request.
- Определить уникальные constraints и поведение при повторном бизнес-объекте.
- Все связанные DB-записи создавать одной локальной транзакцией, если сценарий требует атомарности.
- Для слота/остатка/лимита обеспечить блокировку, serializable/appropriate isolation либо constraint; предварительный `SELECT` без защиты недостаточен.
- Не выполнять необратимый внешний side effect до точки, из которой можно безопасно продолжить/повторить; рассмотреть outbox/saga только если архитектура распределенная.
- Не кэшировать mutation response как обычный read cache. После commit инвалидировать затронутые чтения.

## POST для поиска

Использовать только как подтвержденный стандарт проекта или fallback, когда GET/QUERY невозможно применить.

- Явно зафиксировать, что операция не меняет бизнес-состояние, хотя POST не сообщает safe/idempotent semantics инфраструктуре.
- Не рассчитывать на автоматический retry без отдельного договора.
- Если результаты кэшируются во внутреннем Redis, cache key строить из canonical body, pagination, sorting и representation metadata.
- Не использовать `X-Request-Id` как идентификатор набора результатов или cursor.
- Если сервер сохраняет результаты поиска как отдельный ресурс, моделировать его явно и определить TTL/доступ.
- До постановки предложить QUERY по RFC 10008 как актуальную альтернативу, если инфраструктура его поддерживает.

## PUT

- Определить, заменяется ли ресурс полностью.
- Указать, что происходит с отсутствующими optional-полями: сброс, default или ошибка. Не превращать PUT в неявный PATCH.
- URI ресурса известен клиенту; определить допустимость create-if-absent.
- Вернуть `201` при создании, `200` с representation либо `204` при замене.
- Повтор идентичного PUT должен приводить к тому же целевому состоянию.
- Для конкурентного обновления рассмотреть `ETag` + `If-Match` и `412 Precondition Failed`.
- Проверить полномочия на объект и неизменяемые/server-managed поля.
- Изменение ресурса и связей выполнять атомарно либо явно описать частичный результат.
- Инвалидировать связанные кэши после commit.

## PATCH

- Выбрать и указать формат: `application/merge-patch+json`, `application/json-patch+json` либо проектный JSON.
- Для каждого поля определить: отсутствие означает «не менять»; `null` означает удалить/очистить или запрещен.
- Whitelist изменяемых полей; server-managed поля отклонять.
- Для enum/status описать разрешенные переходы и конфликт текущего состояния.
- Для массивов определить замену всего массива, добавление/удаление элементов, порядок и дубликаты.
- Для конкурентных изменений рассмотреть `If-Match`/version и `412` либо проектный `409`.
- Вернуть `200` с обновленным representation либо `204`.
- Частичное изменение и связанные записи выполнять атомарно, если бизнес-сценарий не допускает частичного успеха.
- Инвалидировать связанные кэши после commit.

## DELETE

Перед проектированием обязательно спросить, что означает удаление для данного ресурса. Не выбирать вариант молча.

### Архивация

Ресурс скрывается/замораживается и может быть восстановлен пользователем или администратором.

- Предпочтительный смысл — изменение состояния через `PATCH /resource/{resourceId}/archive` либо проектный action endpoint.
- В БД установить `isArchived = true` или статус `ARCHIVED`.
- Определить restore, доступ к архиву, срок хранения и влияние на списки/поиск.
- `DELETE /resource/{resourceId}/archive` использовать только по утвержденному проектному стандарту и предварительно отметить неоднозначность.

### Физическое удаление

Запись и допустимые связи удаляются без штатного восстановления.

- Использовать для черновиков, временных/технических данных или объектов без обязательной истории.
- Проверить FK, cascade/restrict, события, файлы, search index и cache invalidation.
- Запретить физическое удаление при юридической, финансовой, аудиторской или бизнес-необходимости хранения.
- Определить резервную копию и фактическую необратимость, не обещая мгновенное исчезновение из backup.

### Логическое удаление

Ресурс недоступен обычным потребителям, но остается в БД.

- Установить `isDeleted = true`, `deletedAt`, `deletedBy` либо подтвержденный статус.
- Не путать со значением `isDeleted = false`.
- Все связанные GET/QUERY/списки должны исключать удаленную запись, если роль/режим не разрешает ее видеть.
- Определить повторное DELETE, восстановление, уникальные ключи и использование удаленных значений.

### Удаление с анонимизацией

Ресурс исчезает для пользователя, связи/история сохраняются, персональные данные удаляются, псевдонимизируются или шифруются согласно применимым требованиям.

- Сохранить технический идентификатор и ссылочную целостность.
- Перечислить поля, правила необратимой анонимизации, токены/session, внешние провайдеры, файлы и search index.
- Не утверждать требования GDPR/ФЗ-152 без контекста юрисдикции и согласованной политики хранения.
- Описать повторный запрос и невозможность восстановления персональных данных, если анонимизация необратима.

### Блокировка не является удалением

Для запрета действий при сохранении доступности данных администраторам использовать `PATCH /user/{userId}/block` или статус `BLOCKED` по проектному стандарту.

### Общие требования DELETE

- Успешный синхронный DELETE: `204` без body либо `200` с подтверждением; асинхронный — `202` с operation resource.
- DELETE идемпотентен по целевому эффекту, но контракт повторного вызова (`204`, `404` или `410`) нужно определить.
- Request body для DELETE не использовать без специального подтвержденного контракта.
- Определить проверки зависимостей, conflict/restrict, каскады, событие, аудит и cache invalidation.
- Для логического/архивного удаления описать влияние на все read-модели и бизнес-процессы.

## Интеграционный метод

- Использовать только официальную документацию или результаты подтвержденного исследования внешней системы.
- Отделять контракт нашего API от provider contract.
- Сделать маппинг request → provider и provider → response/БД.
- Зафиксировать authentication внешней системы и безопасное хранение secret без реального значения.
- Определить connect/read/overall timeout, допустимые retry status/network errors, число попыток и backoff только после подтверждения.
- Retry выполнять только для безопасной/идемпотентной операции либо при надежной provider idempotency.
- Определить circuit breaker, fallback/degradation и поведение при пустом/частичном provider response.
- Не проксировать provider error body клиенту без маппинга; provider code помещать в защищенные логи.
- Различать `502` для некорректного upstream response, `503` для временной недоступности и `504` для gateway/upstream timeout.
- Проверить schema drift/ошибку парсинга, неизвестные поля, missing required fields и версию внешнего API.
- Логировать dependency, outcome, duration, provider request id; не логировать provider credentials и PII целиком.
