## Требования для согласования

### FR-015: Показ правил и условий клиента
**Тип:** functional | **Версия:** 1.2 | Приоритет: Should  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА при работе с потребностью показывать заполненные полевые правила клиента из эпика и потребности, а также тезисы правил, агрегированные LLM из комментариев эпика. Полевые источники эпика: Рекомендации (12000), Условия для производства (21801), Критерии приемки (20909), Штрафы (20910), Привлечение третьих лиц (20907), Разрешение на PR (20913), Постановка задач (20903), РИД (20904), Обязанности Заказчика (20905), Автоприемка (20906), Формат работы (14024), Тип договора (14023), NDA (14205), Описание; источники потребности: Рисовать опыт нельзя (20302), Работа вне РФ (20914), Нужно предоставить CV (11506), Требования к кандидату (10811). Комментарии эпика система ДОЛЖНА синхронизировать ежедневно и догонять при обновлении эпика не позднее 5 минут; сохранять комментарии в app.epic_comment. Тезисы и хеш источников ДОЛЖНЫ кэшироваться в app.epic_rules_cache; повторная агрегация выполняется лениво только при изменении хеша комментариев. Вызов внешней LLM выполняется через шлюз с обезличиванием и правилами FR-023. GET /needs/{key}/client-rules/theses возвращает кэшированные тезисы; при устаревшем хеше возвращает HTTP 202 и статус асинхронного пересчёта. Администратор МОЖЕТ запустить ручной пересчёт через POST /needs/{key}/client-rules/regenerate. Тезисы ДОЛЖНЫ отображаться в раскрытой строке потребности с подписью «Сгенерировано LLM», раскрываемыми ссылками на исходные комментарии и отметкой возможного противоречия полевым правилам. Правила клиента только информируют и не блокируют отправку согласно BR-006; исключение при назначении для поля «Нужно предоставить CV» описано в FR-008.

**Критерии приёмки:** 1. При раскрытии потребности отображаются заполненные полевые правила клиента из эпика и потребности; пустые поля не выводятся.
2. Система синхронизирует комментарии эпиков ежедневно и догоняет изменённый эпик не позднее 5 минут; полученные комментарии сохраняются с идентификатором источника.
3. При совпадении хеша комментариев возвращаются кэшированные тезисы без повторного вызова LLM; при изменении хеша запускается не более одной активной асинхронной задачи пересчёта.
4. Если пересчёт ещё не завершён, GET /needs/{key}/client-rules/theses отвечает HTTP 202 со статусом обновления; после завершения отдаёт тезисы из кэша.
5. Каждый тезис имеет доступный первоисточник (ссылка на комментарий); интерфейс указывает, что текст сгенерирован LLM, и отмечает возможное противоречие полевым правилам.
6. Администратор может запросить ручной пересчёт; для внешнего провайдера соблюдаются обезличивание и правила FR-023.
7. Показ правил и тезисов сам по себе не блокирует отправку; исключение для назначения по правилу «Нужно предоставить CV» соответствует FR-008.
