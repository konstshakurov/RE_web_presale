# backend

Python 3.12, FastAPI. Каркас: `app/main.py` (api, `/health`), `app/worker.py` (worker).
Локально: `pip install -r requirements-dev.txt; ruff check .; pytest`.

## Синхронизация Jira (KON-35)
Модуль `app/sync`, процесс `python -m app.worker`, API `/sync/*` (см. `openapi.json`).
Необязательные переменные (умолчания в `app/sync/settings.py`): `SYNC_NEEDS_INTERVAL_SEC` (300),
`SYNC_EMPLOYEES_INTERVAL_SEC` (3600), `SYNC_EPIC_TTL_SEC` (3600), `SYNC_INITIAL_LOAD_DAYS` (183),
`SYNC_PAUSE_RECHECK_SEC` (15), `JIRA_UTC_OFFSET_HOURS` (4), `JIRA_NEED_PROJECT`, `JIRA_NEED_ISSUETYPE`,
`JIRA_EMPLOYEE_PROJECT`, `JIRA_EMPLOYEE_ISSUETYPE`. Нужна миграция V005 (app_db и cv_db).
БД-тесты: `TEST_APP_DB_URL`, `TEST_CV_DB_URL` (роли app_rw / cv_rw, миграции app_db V001-V008 и cv_db V001-V008).

## Файлы сотрудников (KON-36)
Форматы заданы в одном месте, `app/cv/formats.py`, и отдаются в `GET /cv/limits` (`extensions_by_kind`).
CV (основное и доп.): только doc и docx, иначе 415; текст извлекается из doc/docx. Материалы: doc, docx,
pdf, txt, xls, xlsx, ppt, pptx, png, jpg, jpeg; текст не извлекается (статус `none`).

## Группы статусов (KON-64)
Модуль `app/status_groups`, API `/admin/status-groups` (только admin, CSRF на изменяющих): список групп с составом, статусами для выбора и статусами «Прочих»; создать, переименовать, удалить группу; добавить/убрать статус; порядок (`PUT /order`). «Прочие» и «Все статусы» зарезервированы и в таблицы не кладутся. БД-тест: `tests/unit/test_status_groups_db.py`.

## Шлюз LLM (KON-37)
Модуль `app/llm_gateway`; все обращения к LLM только через него (ADR-007). Миграция app_db V008 (колонка
`llm_provider.model`, очередь `llm_task`). Внутренняя Qwen (OpenAI-совместимый API) создаётся при старте из
`LLM_BASE_URL` (по умолчанию адрес из архитектуры), `LLM_MODEL` (по умолчанию `qwen/qwen3.6-35b-a3b`), ключ `LLM_API_KEY` (только env; ключи
админских провайдеров - шифртекстом в `secret_store`, `kind=llm_key`). Внешний провайдер: обезличивание
(regex, словари из кэша Jira и CV и админский словарь, natasha NER) -> предпросмотр -> подтверждение
(`POST /llm/tasks/{id}/confirm`) -> worker вызывает с таймаутом провайдера (по умолчанию 120 с) -> обратная
подстановка. Внутренний - без обезличивания, сразу в очередь. Повтор: `POST /llm/tasks/{id}/retry`.
API: `/llm/tasks*`, `/llm/providers` (выбор модели), `/admin/llm/providers*`, `/admin/llm/dictionary`.
Завершённые задачи хранятся `LLM_TASK_TTL_DAYS` (7) дней. Модуль вызывается из Python так:
`request.app.state.llm.submit(login, "match", prompt, provider_id=None, ref="ANALYTICS-1")`.
БД-тест: `tests/unit/test_llm_db.py`.

## Навыки из CV и сопоставление (KON-38)
Модуль `app/matching`; нужны миграции cv_db V007 (`file_skill_state`, `match_run`, `match_batch`,
`recommendation.note_snapshot_at`), V008 (`search_run`, `search_batch`, `search_result`) и V009 (кэш скрининга
`match_screen`/`search_screen`, `stage`/`run_id` пакетов, `chain_state` прогонов, `search_run.scope`).
Все вызовы LLM идут через шлюз (задачи `purpose=skills|match|search|match_screen|search_screen`);
результат забирает worker сразу после задачи и API лениво при запросе состояния (оба идемпотентны).
- Навыки (FR-027): ставятся при загрузке основного CV и по `POST /resume/employees/{key}/skills`,
  `POST /resume/skills/backfill`; хранятся по файлу, без замены файла не пересчитываются.
- **Двухступенчатая оценка** (масштаб 200+ сотрудников; сопоставление и поиск по смыслу):
  - Ступень 1, скрининг: LLM оценивает ВСЕХ допустимых кандидатов (допустимые статусы, основное CV с текстом;
    в поиске - в области фильтров) только по выделенным навыкам, без текста CV, заметок, ФИО и ключей; пакеты
    по `screen_batch` (50), метки K1..Kn; результат - предварительный балл 0..100. Кандидат без выделенных
    навыков (или без ответа LLM) не выпадает: его балл считается детерминированно (технологии из потребности/
    запроса * 3 + слова в тексте CV, в % от числа значимых слов), в рейтинге он стоит наравне с остальными.
  - Ступень 2, глубокая оценка: топ-N (`deep_size`, 30) рейтинга оценивается по тексту CV, как раньше (пакеты по
    5, обрезка 6000 знаков, заметка и «подробнее об опыте» учитываются). Запускается автоматически, когда
    скрининг завершён (worker или опрос GET). Кому оценка уже в кэше (CV + модель + версия потребности + заметка),
    LLM не вызывается. Если допустимых не больше N - скрининг пропускается, оценивается сразу весь список.
  - «Оценить следующих»: `POST /needs/{key}/match/next` и `POST /resume/semantic-search/next` - глубокая оценка
    следующей порции (N) рейтинга, у кого нет свежей оценки; уже оценённые не пересчитываются. В состоянии:
    `evaluated` (оценено глубоко), `remaining` (ещё нет), `deep_size`, `screened`/`screen_total`,
    `can_evaluate_next`, `stage` (`screening|deep`) и `run_id` текущего прогона.
  - Кэш скрининга: потребность|запрос + основное CV + модель (+ хэш набора навыков; для потребности ещё версия
    `jira_updated_at`). Устаревает при смене потребности, модели, набора навыков, замене файла; правка заметки
    скрининг не устаревает (заметка в нём не участвует) - она учитывается на ступени 2.
  - Настройки администратора (`app_setting` `match_deep_size`, `match_screen_batch`):
    `GET|PUT /admin/matching/settings` (только admin, PUT с CSRF; N 5..100, пакет скрининга 10..100). Действуют
    на новые прогоны.
- Сопоставление (FR-005, FR-036): `POST /needs/{key}/match` (`provider_id`, `force`), `GET /needs/{key}/match`
  (`limit`=10, `offset` - «Показать ещё»). Устаревает при смене потребности, заметки или модели.
- Внешний провайдер (FR-023, **один предпросмотр и один confirm на прогон**): прогон = одна ступень = группа
  задач шлюза с общим `run_id` (он в `tasks[].run_id` и в `run_id` состояния). `GET /matching/runs/{run_id}` -
  статус и обезличенный предпросмотр ВСЕХ пакетов (`tasks[].prompt`, `replacements`); `POST
  /matching/runs/{run_id}/confirm` (CSRF) - подтверждает все ожидающие задачи прогона одной транзакцией
  (`gateway.confirm_many`: либо все, либо ни одной); `POST .../cancel` - отмена. Отправка без подтверждённого
  предпросмотра по-прежнему невозможна. Скрининг - один прогон; ступень 2 строится уже по результату скрининга,
  поэтому предпросмотреть её раньше нельзя: после скрининга она появляется как новый прогон в
  `awaiting_confirmation` со своим `run_id` и подтверждается отдельно; «Оценить следующих» - тоже отдельный
  прогон. Внутренняя Qwen - без подтверждений. Старый `POST /llm/tasks/{id}/confirm` работает, как раньше
  (подтверждает одну задачу; остальные прогона подтверждаются `.../confirm` по `run_id`).
- «Резюме» (FR-032, FR-003): `GET /resume/employees` (`q`, `status`, `technology`, `match=all|any`),
  `GET /resume/technologies`, `GET /resume/employees/{key}/profile` (без LLM). Профиль: разделы BR-007
  (профиль, основной стек, отрасли, ключевые навыки, языки, образование и сертификаты, проекты) по заголовкам,
  годы опыта - только если CV называет их явно («более 5 лет опыта», «опыт работы 7 лет»).
- «Поиск по смыслу (LLM)» (FR-032): `POST /resume/semantic-search` (CSRF; `query` 3-500 символов, `provider_id`,
  `force`, фильтры `status`, `technology[]`, `match`, `q`, `limit`) и `GET /resume/semantic-search` (те же
  параметры + `offset`) - состояние и результат пользователя по запросу. Область: допустимые статусы (или явно
  выбранный статус), основное CV с текстом, фильтры. Область не больше N - детерминированный отбор (технологии
  из запроса, вес 3, слова запроса в тексте CV; без совпадений - все) и сразу глубокая оценка; больше N -
  двухступенчатая оценка, ступень 2 берёт ту же область (фильтры запуска хранятся в `search_run.scope`). Кэш по
  запрос (нормализованный) + основное CV + модель, общий для пользователей; прогон принадлежит автору (он
  подтверждает отправку внешнему провайдеру). Правка заметки или смена модели - `stale`; замена файла - новая
  оценка. В выдаче сначала оценённые глубоко (`source=llm`, `percent`), затем остальные по рейтингу: с
  предварительной оценкой скрининга (`source=screening`, `screen_percent`), затем по технологиям и тексту
  (`source=fallback`). Без LLM (нет провайдера, ошибка, таймаут, обезличивание не удалось) список строится так
  же, а `notice` и `status` (`unavailable` | `failed` | `partial`) объясняют причину. Запросы и оценки хранятся
  30 суток (чистятся при новом запуске).
- Поведение при сбоях: все пакеты скрининга упали - ступень 2 не запускается, статус `failed`; часть пакетов или
  часть ответа - остальные остаются в рейтинге по детерминированному баллу; ступень 2 не удалось поставить
  (обезличивание, шлюз) - скрининг сохранён, `can_evaluate_next=true`, «Оценить следующих» вернёт причину.
  Ступень 2 ставится в том числе из `GET` (ленивый сбор), от имени автора прогона.
Тесты: `tests/unit/test_matching_*.py` (двухступенчатая оценка - `test_matching_twostage*.py`); БД-тест
`test_matching_db.py` (`TEST_CV_DB_URL`, `TEST_APP_DB_URL`, cv_db V001-V009, app_db V001-V008).
