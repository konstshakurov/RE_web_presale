# KON-133 — проба поля «Руководитель отдела» (customfield_14401)

**Дата пробы:** 2026-10-28
**Среда:** корпоративная сеть, Jira Server 8.13.0 (SimbirSoft Jira, подтверждено `GET /rest/api/2/serverInfo`), проект ANALYTICS, тип Epic — карточки сотрудников
**Метод:** живая проба через сессионную cookie: единственный `POST /rest/auth/1/session` (вход), далее только GET. Пауза между запросами 300 мс (≥ 200 мс), лимит 10 с на вызов (NFR-009), одна сессия. Всего 17 запросов. Доступ — переменные окружения процесса; в отчёт и логи не попадает.
**Скрипт пробы:** вне репозитория (временный), не коммитится.
**Файл отчёта:** `architecture/probes/KON-133_report.md`

## 1. Что проверялось

1. **Формат значения** `customfield_14401` у карточки с заполненным РО (ANALYTICS-96) — и главное противоречие первого отчёта: отдаёт ли REST значение вообще.
2. **Метаданные поля** — имя, `schema.type`, `custom`, идентификация поля.
3. **Ключ для JQL-фильтра** — `cf[14401] = "<name>"` / `= "<key>"` / `= "<displayName>"` / `currentUser()`.
4. **Пустое значение** — как Jira отдаёт незаполненное поле.
5. **Список различных РО** — полная выгрузка 256 карточек, числа сотрудников по каждому РО.
6. **Варианты написания одного человека** — регистр, `key` vs `name`, displayName-аномалии, `active: false`.
7. **Сравнение с «Профилем сотрудника» `customfield_10707`** — подходит ли существующий разбор `_profile_login`.
8. **Время и объём запросов** (NFR-008) — фактические замеры.

## 2. Результаты

### 2.1 Формат значения и «противоречие» первого отчёта

Форма user-объекта — все ключи получены живым ответом, значения заменены заглушками:

```json
{
  "self": "<url профиля пользователя>",
  "name": "<логин>",
  "key": "<ключ пользователя; на этом экземпляре отличается от name>",
  "emailAddress": "<email>",
  "avatarUrls": { "48x48": "<url>", "24x24": "<url>", "16x16": "<url>", "32x32": "<url>" },
  "displayName": "<Имя Фамилия>",
  "active": true,
  "timeZone": "<часовой пояс>"
}
```

Проверка тремя способами на ANALYTICS-96 (РО заполнен, виден в интерфейсе Jira):

| Способ | Код | Время | Объём | Значение |
|---|---|---|---|---|
| `GET /rest/api/2/issue/ANALYTICS-96?fields=customfield_14401,customfield_10707` | 200 | 73 мс | 1 542 байт | есть, оба ключа в `fields`, объект user |
| `GET /rest/api/2/issue/ANALYTICS-96` (без `fields`, полный ответ) | 200 | 420 мс | 97 303 байт | есть: ключ среди 646 полей полного ответа |
| `GET /rest/api/2/search?jql=key=ANALYTICS-96&fields=customfield_14401` | 200 | 136 мс | 980 байт | есть, объект user |

**Противоречие закрыто: REST отдаёт значение всеми тремя способами.** Контрольная сверка: JQL `cf[14401] IS NOT EMPTY` обещает 197 карточек; полная выгрузка (п. 2.5) нашла заполненное значение ровно у 197 из 256. Заявление первого отчёта «у всех 197 значение `None`» — ошибка скрипта той пробы (значение не попадало в параметр `fields=` запроса поиска либо читалось не из того ответа), а не поведение Jira. Псевдопроверок (`renderedFields`, «права учётки») не потребовалось — значение отдаётся обычным путём.

Выводы:

- `currentUser()` синтаксически принимается (0: учётка пробы никем не назначена РО) — приложению не нужно, фильтр идёт по значению из кэша.

### 2.4 Пустое значение («Без РО»)

- JQL `cf[14401] IS EMPTY` — 59 карточек.
- Пример (ANALYTICS-1915, статус «Уволен»): в ответе search с явным `fields=customfield_14401,status` **ключ присутствует в `fields`, значение `null`** (88 мс, 641 байт).
- Код синхронизации читает через `.get()` — покрывает оба случая («ключа нет вообще» из KON-30 п. 10 и «ключ есть, значение null»); в `mapping.py` эта конвенция уже действует для всех полей.
- В кэше «Без РО» = `dept_head_login IS NULL`.

### 2.7 Сравнение с `customfield_10707` и разбор `_profile_login`

У ANALYTICS-96 `customfield_10707` — тот же формат user-объекта (форма идентична п. 2.1; 73 мс, 1 542 байт на оба поля). Разбор `_profile_login` из `backend/app/sync/mapping.py` подходит **без изменений**:

- берёт `name` с приоритетом над `key` — корректно: `key` на этом экземпляре отличается от `name` у всех РО;
- проверку длины проходит (фактический логин — 12 символов ≤ 128);
- приводит к нижнему регистру — конвенция та же, что у `jira_login`.

РО и «Профиль сотрудника» у одной карточки — разные люди (поля независимы). Общий разбор user-поля переиспользуется целиком; своя остаётся только логика фильтрации и подписи.

## 4. Расхождения, дефекты и открытые вопросы

1. **РЕШЕНИЕ владельца (28.10.2026): «Не ***» — заглушка «Не назначен», считается «Без РО»** (в фильтре «Без РО» = 59 + 16 = 75; реальных РО — 6). Реализация: значение логина-заглушки сопоставляется как NULL (точное написание уточнить у владельца при реализации KON-136). Исходное наблюдение:
   **«Не ***» — подозрение на псевдопользователя.** Один из 7 РО имеет логин из кириллицы с пробелом, начинается с «Не» (16 карточек, все «Уволен»). Похоже на заглушку вида «Не назначен», а не на реального руководителя. Реальные значения знает Константин: если это заглушка — решить, считать ли её «Без РО» в фильтре (тогда «Без РО» = 59 + 16 = 75, а различных РО = 6).
2. **Два РО с `active: false`** (ale***, ari***): их сотрудники в кэше есть. Показывать таких РО в фильтре как есть, помечать или скрывать — решение UI (KON-136/KON-143); данные для любого варианта есть.
3. **«Декрет» — 0 карточек** на момент пробы: статус в модели есть, данных нет. Для фильтра некритично, просто не появится в числах.
4. Дефектов Jira по этому полю не обнаружено: значение отдаётся во всех способах чтения, JQL ведёт себя предсказуемо (кроме документированного выше «key не матчится» — это особенность user-полей Jira Server, REST при этом отдаёт `key` нормально).
