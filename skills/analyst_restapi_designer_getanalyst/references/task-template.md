## Пример ответа — Успех

Указать условие, HTTP-код, значимые response headers и валидное тело. Для создания использовать `201 Created` и `Location`, если ресурс создан синхронно и имеет URI. Для успеха без body использовать `204 No Content`.

Для каждого response-поля обязательность, `nullable`, тип и формат должны быть подтверждены. Не выводить `nullable` только из того, что объект может находиться в определенном статусе; при влиянии на контракт уточнить это до постановки.

Для списка отдельно показать успешный пустой результат `200 OK` с пустым массивом. Не использовать `404` для пустой коллекции.

## Ошибочные ответы

Включать только применимые подразделы. Во всех примерах использовать один согласованный формат ошибки. Перед примерами можно дать компактную таблицу:

| Условие | Этап проверки | HTTP | errorCode/code | message | Response headers |
|---|---|---:|---|---|---|

### Пример ответа — Ошибка авторизации

Включать, если метод защищен или опциональный credential валидируется при передаче. Различать:

- `401 Unauthorized` — credentials отсутствуют, истекли или недействительны;
- `403 Forbidden` — субъект известен, но действие запрещено.

### Пример ответа — Запись не найдена

Включать для конкретного запрашиваемого или связанного ресурса. Использовать `404 Not Found`, если проект не скрывает существование объекта другим кодом. Для логически удаленной записи применять подтвержденное проектом поведение.

### Дополнительные ошибочные ответы

Добавить отдельные подразделы только для применимых условий: неверный формат, семантическая валидация, конфликт, conditional request, неподдерживаемый content type, превышение лимита, отказ зависимости, timeout, внутренняя ошибка.

## Требования к реализации

Описать нумерованный исполнимый алгоритм. Использовать подтвержденные названия компонентов. Если схема архитектуры не передана, применять нейтральные логические роли и не придумывать сервисы, БД, брокеры или внешние системы:

1. Прием запроса и протокольные проверки.
2. Rate limit в подтвержденном месте архитектуры.
3. Аутентификация.
4. Авторизация, роль/scope и владение ресурсом.
5. Форматная и семантическая валидация.
6. Поиск связанных сущностей и бизнес-проверки.
7. Основное чтение/изменение/внешний вызов.
8. Транзакция, блокировка, constraint, идемпотентность или асинхронная публикация, если применимо.
9. Обработка альтернативных сценариев и частичных отказов у соответствующего шага.
10. Формирование и возврат ответа.

Для каждой ошибки указать точный момент остановки и контракт ответа. Не дублировать таблицы полей, если алгоритму достаточно ссылки на раздел маппинга.
