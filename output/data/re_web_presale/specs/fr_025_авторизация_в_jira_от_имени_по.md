## Формулировка

> _Формулировка: «Система ДОЛЖНА [действие]...»_

Система ДОЛЖНА выполнять действия в Jira от имени конкретного пользователя через его сессионный токен Jira (cookie сессии). Логин и пароль Jira совпадают с корпоративными (LDAP): при входе в приложение один ввод пароля ДОЛЖЕН использоваться и для проверки в LDAP, и для создания сессии Jira (`POST /rest/auth/1/session`); пароль НЕ ДОЛЖЕН сохраняться ни в БД, ни в кэше, ни в логах. Сессионный токен ДОЛЖЕН храниться зашифрованно (NFR-006). При истечении сессии (401) система ДОЛЖНА запросить пароль повторно, не теряя введённых данных. Если Jira отказала при верных данных LDAP, вход в приложение ДОЛЖЕН выполняться, а действия в Jira ДОЛЖНЫ блокироваться с показом текста отказа (FR-029).

## Обоснование

PAT на Jira 8.13.0 невозможен; Application Link и OAuth 1.0a не используются (проба KON-30, ADR-005, решение владельца 05.10.2026): чтение и запись сессионной cookie пользователя подтверждены. Действия видны в истории Jira от имени пользователя (BR-001).

## Ограничения и допущения

Фоновый опрос идёт токеном любого активного пользователя только на чтение; без активных сессий опрос приостанавливается (FR-028). Срок жизни сессии Jira не измерен. Заявка в Support на Application Link (ISS-001, риск RK-001) больше не блокирует; Application Link остаётся запасным вариантом.

## Связанные требования

`NFR-006`, `FR-029`

## История изменений

- 2.0 (26.10.2026, CR-009): OAuth 1.0a (Application Link, RSA, access token) заменён на сессионный токен Jira: один ввод пароля при входе, пароль не хранится, повторный ввод при 401. Текст приведён в соответствие реализации (KON-30, ADR-005, KON-52).
