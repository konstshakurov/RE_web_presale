# Правила PlantUML для UML Sequence

## 1. Участники

- Пользователь или внешняя роль: `actor`.
- Frontend, Backend, микросервис, сервис, файловое хранилище и внешняя система: `participant`.
- База данных: `database`.
- Kafka, RabbitMQ и другой брокер сообщений: `queue`.
- Объявлять каждого участника один раз и использовать короткий уникальный alias.
- Показывать только участников, которые реально задействованы в описанном сценарии.
- Если в тексте отдельно названы Web/iOS/Android, несколько Backend-сервисов, БД или внешних
  систем, не объединять их в одного участника.

## 2. Сообщения и стрелки

| Смысл | Синтаксис | Требование к подписи |
|---|---|---|
| Запрос, команда, вызов | `A -> B : ...` | Глагол, действие и API-метод, если он известен |
| Ответ на запрос | `B --> A : ...` | Данные, статус или пользовательское сообщение |
| Внутренний вызов | `A -> A : ...` | Конкретное внутреннее действие |
| Доставка события брокером | `Queue --> Consumer : ...` | Название события и ключевые данные |

- Все запросы подписывать действием: `Зарегистрировать пользователя POST /users`.
- Если Frontend или другой клиент вызывает Backend, но метод не указан, писать:
  `Выполнить действие [рекомендуется указать API метод]` на языке пользователя.
- Не придумывать конкретный HTTP-метод или URI.
- Если API-метод указан пользователем, сохранять его без переименования и исправлять только
  явную опечатку, если смысл однозначен.
- Все ответы на синхронные запросы показывать пунктирной стрелкой `-->`.
- Не оставлять ответ без подписи. Возвращать данные, статус или сообщение, а не действие.
- Публикацию события в брокер показывать обычной стрелкой `Producer -> Queue`.
- Доставку сообщения из брокера потребителю показывать пунктирной стрелкой
  `Queue --> Consumer`, как сообщение с данными, а не как ответ на вызов.
- Не рисовать подтверждение брокеру, если acknowledgement не описан в Use Case.

## 3. Бары активации

- Активировать каждую линию жизни, когда участник начинает выполнять работу.
- Деактивировать её сразу после окончания этой работы.
- Каждый `activate X` обязан иметь соответствующий `deactivate X`.
- Активировать первого инициатора сценария до первого сообщения. Если инициатор — actor,
  у него также должен быть бар активации.
- При повторной активации участника после завершённого этапа или в новой ветке сначала
  показать его новое исходящее сообщение и только затем написать `activate X`. Не ставить
  `activate X` до сообщения, если предыдущий `deactivate X` не отделён от него другим
  сообщением: PlantUML привяжет обе команды к одной позиции и вернёт ошибку
  `Activate/Deactivate already done`.
- Участник, ожидающий результат вложенного синхронного вызова, остаётся активным.
- После ответа деактивировать исполнителя, затем продолжить работу вызывающего участника.
- Никогда не создавать бары активации для `queue`, включая Kafka и RabbitMQ.
- Не использовать `autoactivate on`.

### Самовызов

Если компонент вызывает внутреннюю функцию, добавить второй бар поверх текущего:

```plantuml
activate Backend
Backend -> Backend : Сгенерировать новый пароль
activate Backend
deactivate Backend
deactivate Backend
```

Не закрывать внешний бар вместе с внутренним. После самовызова компонент может продолжать
обработку в рамках внешней активации.

## 4. Управление потоком

- `alt` — взаимоисключающие ветки, включая успешный и ошибочный результат.
- `else` — следующая ветка того же `alt`.
- `opt` — условный необязательный фрагмент без альтернативной ветки.
- `loop` — повторение, например обработка каждого элемента массива.
- `break` — прекращение сценария, только если оно явно следует из требований.
- Не добавлять альтернативы, ошибки, таймауты или повторы, которых нет в исходном описании.
- В каждой ветке самостоятельно соблюдать баланс активаций.

## 5. Читаемость

- Использовать `== Название этапа ==` для крупных логических частей длинного сценария.
- Использовать `autonumber` для сценария с пятью и более сообщениями, если пользователь не
  попросил иначе.
- Использовать `\n` для переноса длинных подписей.
- В подписи API-вызова сначала писать действие, затем метод и URI, затем в квадратных или
  фигурных скобках ключевые данные.
- Не перегружать стрелку полным JSON, если пользователь не просит показать сообщение целиком.

## 6. Самопроверка перед ответом

1. Все ли участники сценария объявлены правильными типами?
2. Не объединены ли отдельно названные Frontend, Backend, микросервисы, БД и внешние системы?
3. Есть ли у первого инициатора бар активации?
4. Получает ли каждый работающий участник бар активации?
5. Имеет ли каждый `activate` парный `deactivate` в правильном порядке?
6. Нет ли повторного `activate X` в той же позиции, где только что выполнен
   `deactivate X`, без промежуточного сообщения?
7. Есть ли вложенный бар у каждого самовызова?
8. Отсутствуют ли активации у всех `queue`?
9. Подписан ли каждый запрос глаголом и известным API-методом?
10. Использован ли плейсхолдер вместо выдуманного метода?
11. Все ли ответы пунктирные и содержат данные, статус или сообщение?
12. Отражены ли все шаги основного сценария в исходном порядке?
13. Добавлены ли только описанные пользователем альтернативы и ошибки?
14. Соответствует ли язык всех подписей языку пользователя?
15. Начинается ли код с `@startuml` и заканчивается ли `@enduml`?
