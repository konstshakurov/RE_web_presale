## Приоритет решений

Использовать порядок:

1. Явно подтвержденный стандарт конкретного проекта.
2. Решение пользователя по текущему методу.
3. Актуальная общая рекомендация HTTP/REST после подтверждения пользователем.

Если проектное решение технически спорное, не исправлять его внутри постановки. До постановки кратко указать отличие, риск и примененное решение.

Не считать универсальными правила одного проекта. Если стандарт не задан, уточнять:

- единственное или множественное число ресурсов;
- схема версионирования;
- формат ошибки;
- offset или cursor pagination;
- формат денег и валюты;
- политика timezone;
- HTTP/Redis/CDN caching;
- правила nullable и неизвестных JSON-полей.

## Ресурсы, URI и версия

- Моделировать бизнес-ресурсы, а не CRUD-глаголы: `/orders/{orderId}`, а не `/getOrder`.
- Для обычного REST API общая рекомендация — ресурсы во множественном числе. Если проект MyMovie или другой утвержденный гайд требует единственное число (`/movie`, `/cinema/{cinemaId}`), сохранить его и отметить отличие до постановки.
- Составные сегменты писать lowercase `kebab-case`: `/user-profile`.
- Идентификаторы именовать предметно: `{movieId}`, `{appointmentId}`, а не `{id}`, если контекст может быть неоднозначным.
- Не создавать чрезмерно глубокую вложенность. В path оставлять только обязательный контекст идентификации.
- Доменные команды выражать подресурсом или явным action endpoint только когда CRUD-модель не передает смысл: `PATCH /user/{userId}/block` или `POST /order/{orderId}/cancellation` по стандарту проекта.
- Не менять утвержденный URI молча.

Версию в URI оформлять как `/vN/`, если это стандарт проекта: `/api/admin/v1/employee`.

Повышать major-версию при несовместимом изменении, например:

- удалении или переименовании поля;
- изменении типа, формата или смысла поля;
- превращении optional в required;
- несовместимом изменении URI, HTTP-метода, успешного статуса или модели ошибки;
- изменении семантики пагинации/сортировки, которое ломает клиента.

Не повышать major автоматически при добавлении нового endpoint или нового optional-поля, если политика совместимости обязывает клиентов игнорировать неизвестные response-поля. Для enum отдельно оценивать совместимость: новый вариант часто ломает закрытый client-side switch.

## Выбор HTTP-метода

- `GET` — безопасное получение представления; request body не использовать.
- `QUERY` — безопасный и идемпотентный серверный запрос с содержательным request content, когда фильтры слишком сложны или велики для URI.
- `POST` — создание подчиненного ресурса или неидемпотентная команда. Для поиска использовать только при подтвержденном ограничении инфраструктуры или стандарте проекта.
- `PUT` — полная идемпотентная замена ресурса по известному URI либо создание по client-selected URI, если это разрешено контрактом.
- `PATCH` — частичное изменение; определить patch format и семантику отсутствующего поля/`null`.
- `DELETE` — удаление связи URI с текущей функциональностью; физическое удаление хранилища не следует из HTTP автоматически.

Проверять safe/idempotent semantics, допустимость автоматического retry и влияние повторного запроса.

## Размещение входных данных

- Path — идентификация ресурса и обязательный контекст.
- Query — фильтрация, сортировка, пагинация и необязательный режим представления для GET.
- Headers — метаданные протокола, credentials, трассировка, content negotiation и preconditions.
- Body/request content — данные создаваемого/изменяемого ресурса или содержательное описание QUERY.

Не дублировать одно поле в path и body без правила проверки равенства. Не принимать `userId` от клиента как источник прав, если субъект надежно определяется по токену.

## JSON-контракт

Если проект не определил иное, рекомендовать:

- поля и объекты — `camelCase` с маленькой буквы: `cinemaId`, `cityName`;
- массивы — имя во множественном числе: `movies`, `cinemas`, `participantEmails`;
- boolean — имя, отражающее состояние: `isInStock`, `hasAccess`;
- enum — единый регистр и закрытый перечень значений, например `IN_CLINIC`, с описанием бизнес-смысла;
- идентификаторы UUID — `string` + формат `uuid`;
- неизвестные request-поля — отклонять либо игнорировать только по утвержденной политике;
- JSON-примеры — синтаксически валидные, без комментариев и висячих запятых.

Для каждого поля определить:

- required;
- nullable;
- поведение при отсутствии;
- допустимость пустой строки/массива;
- default;
- тип и формат;
- min/max, длину, шаблон, enum;
- trim, регистр и Unicode normalization для строк;
- дубликаты и значимость порядка для массивов;
- источник, преобразование и ошибку.

Не смешивать отсутствующее поле, `null`, пустую строку, `0`, `false` и пустой массив. Не использовать binary floating-point для точных денежных вычислений.

## Даты, время и длительность

JSON не имеет отдельного типа даты/времени, поэтому передавать строку в согласованном профиле ISO 8601. Для интернет-контрактов рекомендовать RFC 3339:

- дата: `2012-04-21`;
- локальное время: `18:25:43`, только если timezone задается контекстом;
- date-time с offset: `2012-04-21T18:25:43-05:00`;
- date-time в UTC: `2012-04-21T23:25:43Z`.

`Z` означает UTC, а не отсутствие timezone. Определить точность (секунды/миллисекунды), правила округления, допустимость прошлого/будущего и источник текущего времени.

Для длительности:

- если стандарт проекта требует минуты, передавать целое количество минут, например `cookingTimeMinutes: 192` либо подтвержденное проектом имя;
- если нужна календарная или составная длительность, согласовать ISO 8601 duration либо отдельные поля;
- не использовать безразмерное число без явной единицы в имени или описании.

Timezone offset вида `3` не учитывает получасовые зоны и DST. Для новой политики рекомендовать IANA timezone (`Europe/Moscow`) либо date-time с offset. Если проект требует `X-TIME-ZONE: 3`, уточнить знак, диапазон, DST и поведение при отсутствии.

## Деньги

Сначала определить валютность и формат проекта.

Если проект требует формат `РУБ.КОП.`:

- API передает decimal-значение, например `120.00`, `3000.00`, `4845.46`;
- БД может хранить сумму в копейках;
- в алгоритме и маппинге явно указать точное преобразование из minor units без `float`, масштаб 2 и правило округления;
- при приеме суммы проверить диапазон и неотрицательность/знак по бизнес-правилу.

Учесть, что JSON number семантически не гарантирует сохранение завершающих нулей. Если именно текстовое представление с двумя знаками является частью контракта, согласовать decimal string либо объект `amount` + `currency`. Для мультивалютности всегда передавать валюту или закреплять ее на уровне API.

## Файлы и изображения

В response возвращать абсолютный HTTPS URL, а не внутренний путь или имя bucket:

```json
{
  "imageUrl": "https://files.example.com/images/movies/name.png"
}
```

Для private-файла определить подписанный URL, срок жизни, права и поведение после истечения. Для загрузки выбрать и подтвердить один сценарий:

- `multipart/form-data` через API;
- прямую загрузку по pre-signed URL с последующим подтверждением;
- отдельный файловый сервис.

Определить media types, максимальный размер, число файлов, проверку фактического содержимого, antivirus/malware scan, имена, метаданные, идемпотентность и очистку незавершенных загрузок.

## Headers

Использовать headers только по назначению:

- `Content-Type: application/json` — формат request content; обязателен для JSON-body/QUERY content, но не нужен для GET без body;
- `Accept: application/json` — желаемый формат response; определить `406` для неподдерживаемого значения, если content negotiation реализован;
- `Authorization: Bearer <token>` — credentials; никогда не логировать значение;
- `X-Request-Id` или утвержденный `Request-Id` — корреляция/трассировка; не использовать как cursor, идентификатор поиска или cache key;
- `traceparent` — передавать между компонентами, если проект использует W3C Trace Context;
- `User-Agent` — информация о клиентском ПО; не использовать как надежный источник прав или бизнес-решений;
- `Location` — URI созданного ресурса при `201`;
- `Retry-After` — подсказка повтора для `429`/`503`, если применимо;
- `WWW-Authenticate` — challenge при `401`;
- `ETag`, `If-None-Match`, `If-Match` — cache validation или optimistic concurrency по принятому решению.

Для custom-header описать владельца, обязательность, формат, доверенность, fallback и передачу между компонентами. Новые `X-`-префиксы считать проектным решением, а не универсальным стандартом.

## Фильтрация, сортировка и пагинация

Для фильтрации определить:

- точное совпадение, префикс, подстрока или полнотекстовый поиск;
- регистр, язык, Unicode и обработку пробелов;
- AND/OR между фильтрами;
- OR/AND для нескольких значений одного фильтра;
- поведение при неизвестном идентификаторе фильтра: пустая коллекция или `404` по стандарту проекта;
- whitelist разрешенных полей и пределы массивов.

Для сортировки допускается проектный формат `order=field,asc|desc` либо поле в QUERY body. Всегда определить:

- whitelist полей;
- `asc`/`desc`;
- default sort;
- обработку неизвестного значения;
- сортировку `null`;
- уникальный tie-breaker, обычно `id`, для стабильной пагинации.

Не смешивать размещение `order` в URL и body без явного правила.

Для offset pagination определить `limit`, `offset`, defaults, maximum, `pageSize` и необходимость `totalCount`. Поле `count` использовать только после определения: размер текущей страницы или общий размер.

Для cursor pagination:

- использовать непрозрачный cursor;
- включать версию, выбранную сортировку, значения sort anchor и уникальный id;
- связывать cursor с нормализованными фильтрами и сортировкой через query hash;
- защищать от подмены подписью/HMAC, если cursor содержит доверяемое состояние;
- определить срок действия и ответы для поврежденного cursor и cursor другого запроса;
- возвращать `nextCursor: null`, когда следующей страницы нет.

## Успешные ответы

- `200 OK` — чтение или успешная операция с representation.
- `201 Created` — ресурс создан; добавлять `Location`, если URI известен.
- `202 Accepted` — асинхронная операция принята, но не завершена; вернуть идентификатор операции/статусный ресурс.
- `204 No Content` — успешная операция без response body.
- Пустая коллекция — `200 OK` и пустой массив.

Для response-поля определить required/nullable, тип, источник и преобразование. Не возвращать поля «на будущее» без потребителя.

## Ошибки и HTTP-коды

Выбирать код по фактической причине:

| HTTP | Когда применять |
|---:|---|
| 400 | malformed JSON, неверный тип/формат или другая техническая ошибка клиента |
| 401 | нет действительных credentials; для Bearer добавить `WWW-Authenticate` по политике проекта |
| 403 | субъект известен, но не имеет права или нарушено владение ресурсом |
| 404 | конкретный ресурс не найден или его существование скрывается |
| 408 | сервер не получил полный request message за отведенное время; не использовать автоматически для долгой backend-обработки |
| 409 | конфликт текущего состояния, занятый слот, уникальность или несовместимый повтор |
| 410 | ресурс удален окончательно и это известно/допустимо раскрыть |
| 412 | не выполнено условие `If-Match`/другая HTTP precondition |
| 413 | request content превышает допустимый размер |
| 415 | неподдерживаемый `Content-Type` |
| 422 | синтаксис корректен, но содержательные инструкции семантически невыполнимы, если это принято проектом |
| 429 | превышен rate limit; рассмотреть `Retry-After` |
| 500 | непредвиденная внутренняя ошибка |
| 502 | gateway/proxy получил некорректный ответ upstream |
| 503 | временная недоступность/перегрузка/maintenance; рассмотреть `Retry-After` |
| 504 | gateway/proxy не получил своевременный ответ upstream |

Если проект требует `408` при превышении внутреннего `timeout`, до постановки отметить, что RFC 9110 определяет `408` как неполучение полного запроса. После подтверждения сохранить проектный код без комментария внутри постановки.

Использовать единый формат ошибки проекта. Если он отсутствует, предложить RFC 9457 (`application/problem+json`) либо стабильный проектный объект, например:

```json
{
  "errorCode": "VALIDATION_ERROR",
  "message": "Запрос содержит некорректные данные",
  "details": [
    {
      "field": "priceFrom",
      "reason": "MUST_NOT_EXCEED_PRICE_TO"
    }
  ],
  "traceId": "b2d6949c-60fa-4ef8-8a18-1bde451f7e7d"
}
```

Не использовать кириллическую `с` в имени `code`. Не раскрывать SQL, stack trace, credentials, внутренние URL и непроверенный provider response. Клиентская логика должна опираться на стабильный code/errorCode, а не на локализованный `message`.

## Маппинг, БД и вычисления

Для каждого поля определить единственный источник:

- path/query/header/body;
- субъект из токена;
- конкретная `table.column`;
- связующая таблица M:N;
- справочник;
- вычисление/формула;
- ответ внешней системы;
- константа или текущее время.

Показывать преобразование типов, timezone, денег, enum, nullable, объединение имени, выбор главной фотографии и агрегаты. Для вычисления приводить формулу и округление.

Не описывать прямой доступ микросервиса к БД другого сервиса. Указывать вызов сервиса-владельца. Не держать внешний HTTP-вызов внутри долгой DB-транзакции без обоснования.

Для конкурентного создания/бронирования не ограничиваться `SELECT`, а определить транзакцию, lock/constraint и обработку конфликта. Для M:N определить атомарность, дубликаты и порядок.

## Безопасность

- Проверять authentication, authorization и object ownership отдельно.
- Защищаться от IDOR: наличие роли не заменяет проверку доступа к конкретному объекту.
- Использовать whitelist для сортировки, фильтров, enum и полей patch.
- Ограничивать payload, строки, массивы, pagination limit и частоту запросов.
- Не логировать Bearer/JWT, пароли, API keys, session cookies, платежные реквизиты и чувствительный payload.
- Маскировать PII и не помещать его в cursor/cache key/метрики.
- Для SQL использовать параметризованные запросы; не конкатенировать пользовательский `order`.
- Для private response определить `Cache-Control` и scope кэша так, чтобы не смешивать пользователей/организации.
- Для CORS разрешать только нужные methods/headers/origins; `QUERY` требует preflight.
