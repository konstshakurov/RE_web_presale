# SKILL: Оценка трудозатрат аналитика по нормочасам СимбирСофт

**Источник методики:** внутренний тарификатор нормочасов АО «СимбирСофт»
(см. `references/normo_hours_catalog.md`, `references/discovery_checklist.md`,
`references/estimation_criteria_pp.md`, `references/normo_hours_pp.md`).
Это НЕ часть стандарта BABOK v3, поэтому скилл не привязан
ни к одной из глав 3–7 и не требует переключения фазы платформы (`phase.py`).
Работает в любой активной фазе, как и базовые инструменты Главы 3.

**MCP-сервер:** отсутствует. Это лёгкий скилл — Claude сам читает справочники и
считает оценку, без сохранения промежуточного состояния через MCP.

---

## Зачем эта задача

Дать BA быструю, обоснованную оценку трудозатрат на аналитику по конкретному
проекту — в часах, по этапам работ (приёмка → требования → ТЗ → проектирование →
рабочий проект → внедрение → документация), с чёткой границей: это **оценка
снизу** («от X часов»), а не точная цифра, и с явными допущениями там, где в
проекте ещё не хватает данных для точного скоупинга.

**Ключевые входы:**
- Состав работ проекта — из существующих артефактов (`estimate/concept.md`,
  спецификация 7.1 в `output/specs/`, если есть) или напрямую от BA
- `references/normo_hours_catalog.md` — основной тарификатор для полной аналитики (этапы 0–8)
- `references/discovery_checklist.md` — чек-лист состава Discovery-фазы (пресейл),
  используй только если оценивается именно Discovery, а не полноценная разработка ТЗ
- `references/estimation_criteria_pp.md` — критерии Блоков A/B/C для продуктового
  проекта (ПП), читай первым на ветке ПП, до расчёта часов
- `references/normo_hours_pp.md` — компактный тарификатор для продуктового
  проекта (ПП), используй только на ветке ПП

**Ключевой выход:**
- `estimate/estimate.md` (или `estimate_v2.md` и т.д. при
  повторной оценке — по правилу 3.2.2 `Rules.md`)
- Опционально, по запросу BA — `estimate.xlsx` рядом с ним, готовый к импорту
  в CashMeter (см. Шаг 6)

## Когда читать references

| Ситуация | Читай |
|----------|-------|
| Оценивается продуктовый проект (ПП) | `references/estimation_criteria_pp.md` (Блоки A/B/C) → `references/normo_hours_pp.md` |
| Любая оценка трудозатрат по стадиям 0–8 для полной аналитики (сбор требований, ТЗ, проектирование, внедрение, документация) | `references/normo_hours_catalog.md` |
| Оценивается именно Discovery/пресейл-фаза, а не полноценная разработка ТЗ | `references/discovery_checklist.md` (и таблицу соответствия в конце файла — для перевода в часы через аналогию с основным каталогом) |
| BA просит экспорт оценки в xlsx для CashMeter (Шаг 6) | `references/xlsx_export_rules.md` |

Не читай оба файла целиком в начале «на всякий случай» — сначала пойми с BA, какие
этапы вообще применимы к проекту (шаг 1 ниже), потом читай только нужные разделы.

## Pipeline — этапы

```
0. Входные данные оценки → input/
        ↓
0.5. Концепция проекта из контекста (опционально, но рекомендуется)
        ↓
1. Определить вид оценки (ПП / Полная / Discovery) и границы в его рамках
        ↓
2. Собрать состав работ и количество единиц по каждому применимому пункту
        ↓
3. Определить уровень сложности (1/2/3) по каждому пункту
        ↓
4. Посчитать оценку: Σ (кол-во × норма нижней границы) по этапам и итог
        ↓
5. Сохранить как estimate/estimate.md с допущениями
        ↓
6. (Опционально, по запросу BA) Экспорт в xlsx для CashMeter
```

### Шаг 0 — Входные данные

Один экземпляр Ai_RE_Project ведёт один продуктовый проект — папки `input/`,
`output/` и `estimate/` уже существуют в составе установки, создавать их не
нужно. Входные данные для оценки (материалы от заказчика, вводные от BA)
сохраняй в `input/` — это контекст проекта (`Rules.md`, п. 3.1).

### Шаг 0.5 — Концепция проекта (опционально, но рекомендуется)

Если в `estimate/` ещё нет `concept.md` — предложи BA создать концепцию из
материалов `input/`, используя релевантные скиллы Ai_RE_Project BABOK (например,
`planning_prep` для первичного подхода, `future_state` для целей и границ
решения) и экспертизу LLM напрямую там, где отдельного скилла для конкретного
раздела концепции нет. Концепция повышает точность последующей оценки — легче
оценить состав и объём артефактов, когда есть целостная картина проекта, а не
только разрозненные вводные. **Не блокируй:** если BA не хочет тратить на это
время сейчас — переходи к Шагу 1 без концепции, это рекомендация, а не
обязательное условие.

### Шаг 1 — Вид оценки и границы

Сначала определи **вид оценки** — спроси BA (или определи по контексту
проекта, если уже обсуждали):

- **Продуктовый проект (ПП)** — компактная методика, приоритет на
  конкурентоспособность КП по срокам/стоимости
- **Полная аналитика** — максимально подробная оценка на полноценную
  разработку ТЗ и далее (крупный/долгий проект)
- **Discovery/пресейл** — предпроектное исследование, до старта самого проекта

**Если ПП:** читай `references/estimation_criteria_pp.md` и пройди Блоки A/B/C
по порядку — A: бизнес-ограничения (спрашивать первыми, всегда: тип оценки
КП/внутренняя, срок, бюджет, AI-агент/человек), B: архитектурный и продуктовый
контекст (определяет состав ситуативных артефактов), C: организационный
контекст/аудитория документации. Они определяют состав артефактов и целевую
детализацию для расчёта. Дальше считай по `references/normo_hours_pp.md` —
шаги 2–4 ниже выполняются на его шкале часов (стартовая, не откалиброванная
эмпирически — см. статус в начале файла).

**Если Полная:** читай `references/normo_hours_catalog.md`, определи границы:
- Какие этапы точно НЕ применимы к этому проекту? (например: 7.1 регистрационная
  документация по ГОСТ не нужна для коммерческого digital-проекта; 8.1 промышленное
  ПО не нужна почти никогда; 0.3–0.5 не нужны, если это разработка с нуля, а не
  доработка существующей системы)

  Не проходи по всем 9 этапам одним вопросом — если BA не готов ответить сразу,
  предложи разумный дефолт по типу проекта (см. пример ниже) и явно пометь как
  допущение, которое можно скорректировать.

  **Пример дефолта для типового digital-проекта «с нуля» (не доработка legacy):**
  исключить 0.3–0.5 (нет legacy-системы), 7.1 (нет требования по ГОСТ), 8.1 (не
  промышленное ПО); остальные этапы — по составу артефактов проекта.

**Если Discovery:** читай `references/discovery_checklist.md` — это чек-лист
состава работ, не тарификатор с нормочасами на каждый пункт (см. «Быстрые
ответы» в конце этого файла).

### Шаг 2 — Состав работ и количество единиц

Шаги 2–4 ниже описаны на примере `normo_hours_catalog.md` (ветка «Полная»).
На ветке ПП работай точно по той же логике, но единицы измерения, состав
пунктов и особые правила бери из `normo_hours_pp.md` (раздел 2 — состав
артефактов, раздел 3 — ставки и особые правила, например его собственная
формула для НФТ и «ТЗ — компоновка»).

Для каждого применимого пункта каталога нужно количество единиц измерения:
- 2.1 — количество бизнес-процессов
- 2.2 — количество ролей пользователей
- 2.3.1 — количество Use Case
- 2.3.2 — количество User Story
- 4.1 — количество сущностей
- 4.3 — количество прототипов экранов
- 4.5 — количество функциональных требований (точнее — количество «совокупностей
  ФТ», выведенных из одного бизнес-правила/пользовательского/системного требования)
- 4.6 / 4.7 — количество методов интеграции (по каждой внешней системе отдельно)
- и т.д.

Бери числа из уже готовых артефактов проекта, если они есть (концепция, спецификация
7.1 — экраны, use case, сущности, роли уже перечислены — считай по факту, не
придумывай заново). Если артефактов нет — спроси BA напрямую количество по
укрупнённым пунктам (не по всем 20+ позициям сразу, а по тем этапам, что выбраны
на шаге 1).

### Шаг 3 — Уровень сложности

По каждому пункту — критерии 1/2/3 находятся в `normo_hours_catalog.md` рядом с
описанием пункта. Если BA явно не указал сложность — не блокируй работу: возьми
«средний» уровень как рабочее допущение и пометь это в колонке «Описание» строки
этого пункта (Шаг 5, п. 3), чтобы BA мог найти и скорректировать допущение прямо
рядом с цифрой, не листая весь отчёт.

### Шаг 4 — Расчёт

Для каждого пункта: `оценка_пункта = количество_единиц × норма_нижней_границы(уровень)`.

Особые правила:
- **2.6 Нефункциональные требования** — не считать по количеству единиц, а взять
  30–40% от итоговой оценки 4.5 (функциональные требования)
- **5.1 Документация** и **7.1 Регистрационная документация** — фиксированные
  оценки не по уровням сложности (см. справочник), не умножай на количество
- Пункты без нормочасов в источнике (2.3.3, 2.4, 2.5, 2.7, 4.8, 8.1) — либо
  оценивай по явно указанной в справочнике аналогии, либо помечай как «требует
  экспертной оценки отдельно», не изобретай цифру от себя без пометки

Просуммируй по этапам и дай общий итог. По запросу BA переведи в рабочие дни
(8 ч./день) и в деньги (если BA дал ставку руб./час — не предполагай ставку сам).

**Всегда явно указывай:** это МИНИМАЛЬНАЯ оценка («от X ч.») по методике
источника — в файле нет верхней границы. Не выдавай сумму нижних границ как
единственное число без этой пометки. Буфер на риски (обычно +20–30% в подобных
оценках) — предложи как отдельную строку, но решение о его размере или включении
оставь BA (аналогично принципу «решения остаются за BA» из скиллов 5.3/5.4/6.3).

### Шаг 5 — Сохранение

Сохрани результат в `estimate/estimate.md`. Если файл оценки
уже существует для проекта — спроси BA по правилу 3.2.2 `Rules.md`: «Обновить
существующую оценку или создать новую?» — при «новая» используй следующий
порядковый номер (`estimate_v2.md` и т.д.).

**Структура отчёта:**
1. Заголовок, проект, дата, границы оценки (что включено/что нет и почему)
2. Таблица по этапам: № этапа | Этап | Итого часов
3. Детализация по каждому пункту — таблица с колонками: № | Артефакт | Кол-во |
   Уровень сложности | Норма | Итого | **Описание**. Колонка «Описание» — компактно,
   1–2 строки на пункт, без абзацев:
   - **Сложность** — какой уровень (1/2/3) применён и по какому критерию из
     `normo_hours_catalog.md`/`normo_hours_pp.md` (кратко, не пересказывай весь критерий)
   - **Допущения** — что предположено по нехватке данных именно по этому пункту,
     включая допущенный уровень сложности из шага 3 (если не указан явно BA) — только
     если для пункта есть допущение, иначе не пиши пустую строку
   - **Что входит в оценку** — что конкретно покрывает норма по этому пункту (например,
     «Интеграции — описание в Swagger и sequence diagram», «ТЗ — компоновка, без
     содержимого разделов»)
   - Опционально — ссылка на исходный пункт методики («катал. 4.5» / «ПП 3.1»)

   Если для пункта описание не помещается компактно (редкий случай сложной
   многофакторной оценки) — вынеси развёрнутый текст в сноску под таблицей
   («см. [1]»), а не разрастай ячейку — это единственный способ, которым таблица
   остаётся читаемой при 15–20+ пунктах детализации.
4. Общий итог (часы, при наличии данных — дни/деньги), с пометкой «минимальная
   оценка»
5. Открытые вопросы к заказчику/BA, которые могут изменить оценку

Отдельного сводного блока «Допущения» после таблицы больше нет: раньше допущения
собирались одним списком в конце отчёта без привязки к конкретному пункту — было
сложно проверить, к какой именно строке относится допущение, не листая весь
документ. Теперь допущение по пункту живёт в колонке «Описание» этой же строки.
«Открытые вопросы» (п. 5) — отдельная категория (вопросы заказчику, которые ещё не
решены и могут изменить саму оценку, а не то, что уже предположено при расчёте) —
остаётся отдельным блоком, как и раньше.

**Пример строки детализации** (иллюстративный, формат — не реальная оценка):

| № | Артефакт | Кол-во | Сложность | Норма | Итого | Описание |
|---|---|---|---|---|---|---|
| 1 | Функциональные требования | 95 совокупностей | 2 (Средняя) | 5 ч. | 475 ч. | Типовые CRUD-сценарии без сложной бизнес-логики (катал. 4.5). Не включает UI-макеты (см. п.8) |
| 2 | Интеграция REST/SOAP | 2 метода | 3 (Подробная) | 6 ч. | 12 ч. | Описание в Swagger и sequence diagram на метод. Внешние системы без готовой документации API |
| 3 | Роли пользователей | 6 ролей | 1 (Краткая) | 4 ч. | 24 ч. | Допущение: количество оценено по CONCEPT.md, не подтверждено интервью |

### Шаг 6 — Экспорт в xlsx для CashMeter (опционально)

Только после того, как `estimate.md`/`estimate_pp.md` полностью сохранён (Шаг 5
завершён). Это не обязательный шаг — выполняй его только по прямому запросу
BA («сделай xlsx», «выгрузи в CashMeter» и т.п.) или один раз явно спроси
после сохранения оценки: «Сделать xlsx для импорта в CashMeter?». Не предлагай
его повторно в рамках той же сессии, если BA отказался.

Запусти:
```
python skills/analyst_estimate/scripts/export_to_xlsx.py <путь_к_estimate.md>
```
Результат сохраняется рядом с исходным md, тем же именем, с расширением
`.xlsx` (например, `estimate.md` → `estimate.xlsx`). Точный маппинг колонок и
обработка краевых случаев — `references/xlsx_export_rules.md`; шаблон-источник
— `assets/Шаблон для импорта.xlsx`.

После генерации сообщи BA:
- путь к xlsx-файлу;
- если скрипт вывел строки с откатом «Норма → Итого» — покажи их BA, это
  места, где колонка «Норма» в оценке была не чистым числом (формула,
  диапазон, «фикс.») и часы взяты из «Итого» вместо неё;
- если исходный md не содержит колонку «Описание» в таблице детализации
  (старый формат отчёта) — предупреди, что колонка «Комментарий» в xlsx
  получится пустой.

## Важные принципы

**Не блокируй — предупреждай.** Нехватка данных по конкретному пункту не должна
останавливать всю оценку — помечай допущением и продолжай.

**Решения по буферу и уровням сложности — за BA.** Ты даёшь методически честную
нижнюю границу и явно показываешь допущения; финальные корректировки — решение BA.

**Не вываливай все 9 этапов и 25+ позиций сразу.** Двигайся по шагам 1→5, уточняя
по ходу только то, что нужно для текущего этапа оценки.

**Это компания-специфичная методика, не BABOK-стандарт.** Не путай нормочасы
СимбирСофт с общими практиками оценки (story points, T-shirt sizing и т.д.) — если
BA просит другую методологию оценки, это не про этот скилл.

## Быстрые ответы на типичные вопросы BA

**«Можно оценить только часть проекта (например, только MVP)?»**
Да — шаг 1 как раз про то, чтобы явно очертить границы. Считай только применимые
этапы/пункты для нужного объёма (например, только по экранам и функциональности
одной фичи), явно укажи в отчёте, что это оценка по ограниченному скоупу.

**«В файле только нижняя граница, а верхняя?»**
