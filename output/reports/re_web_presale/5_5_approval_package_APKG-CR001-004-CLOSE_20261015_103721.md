Ставка ДОЛЖНА показываться вместе с валютой, признаком «Включает НДС» и единицей измерения (поля Jira: Планируемая ставка 20809, Включает НДС 20810, Валюта 20811, Единица 20812); пустая ставка допустима и показывается как «не указана».


### FR-002: Список сотрудников со статусами и фильтром

### FR-004: Хранение сотрудников и нескольких CV
**Тип:** functional | **Версия:** 1.0 | Приоритет: Must

CV» (любое число), «Материалы» (примеры работ и др.), «CV по шаблону клиента» (создаётся системой, FR-017; с указанием клиента). Кроме файлов хранятся: поле Jira «Подробнее об опыте» и свободная заметка (FR-033). Файлы типов «Доп. CV» и «Материалы» ДОЛЖНЫ быть доступны для прикрепления к потребности (FR-008).


### FR-005: Рекомендация кандидата с % соответствия и обоснованием
**Тип:** functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА по запросу пользователя («Сопоставить», FR-036) оценивать соответствие сотрудников выбранной потребности: процент и краткое текстовое обоснование, рассчитанные LLM по Основному CV (FR-027) и требованиям потребности — опыт в годах, отрасли, инструменты, опыт в системах, профессия. В оценку ДОЛЖНА учитываться свободная заметка о сотруднике (FR-033, например «не подключать в ЛеманаПРО»). Оцениваются только сотрудники в статусах, допустимых для назначения (FR-002) и имеющие Основное CV. Результат — рекомендация; решение принимает пользователь. Метрик качества не задаётся (ISS-006). Для снижения нагрузки на LLM система ДОЛЖНА сначала отобрать сотрудников детерминированно (по технологиям, статусу), а LLM оценивать только отобранных (предложение); результат кэшируется по связке «потребность + Основное CV + модель» и пересчитывается при изменении потребности или CV.

### FR-014: Выявление дублей потребностей
**Тип:** functional | **Версия:** 1.0 | Приоритет: Could  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА выявлять дубли потребностей по описанию (не по названию) и показывать % совпадения. Сравнение ведётся с потребностями на аналитиков за последние 2 недели во всех статусах. Дублем с очень высокой вероятностью считается совпадение 15% и более текста, описывающего требования к кандидату (опыт, компетенции, навыки, инструменты), полностью совпадающего в последовательном изложении (не вразброс). Для сравнения ДОЛЖЕН использоваться статус, а не резолюция (БП-10).

### FR-022: Добавление файла сотрудника в разделе «Резюме»
**Тип:** functional | **Версия:** 2.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Файлы сотрудников загружаются вручную по одному в разделе «Резюме». В столбце «Файлы» ДОЛЖНА быть кнопка «Добавить»: если файлов у сотрудника нет, она единственный элемент столбца; если файлы есть, показывается их список и та же кнопка. ### FR-023: Обезличивание текста перед отправкой во внешнюю LLM
**Тип:** functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики

Обезличивание НЕ ДОЛЖНО применяться ко внутренней LLM и к файлам CV и примеров работ, прикрепляемым в Jira.

### FR-027: Основное CV — главный источник компетенций

Файл «Основное CV» ДОЛЖЕН быть главным источником компетенций сотрудника для сопоставления с потребностями (FR-036). ### FR-028: Синхронизация данных из Jira (опрос и кэш)

### NFR-006: Защита токенов и ключей
**Тип:** non_functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

OAuth-токены Jira пользователей, API-ключи LLM и прочие креды интеграций ДОЛЖНЫ храниться зашифрованно; ключ шифрования ДОЛЖЕН быть вынесен в переменные окружения. Пароли LDAP НЕ ДОЛЖНЫ храниться. Токены и пароли НЕ ДОЛЖНЫ попадать в логи в открытом виде.

Критерии приёмки: (1) в БД нет ни одного токена или ключа в открытом виде (проверка выборкой по хранилищу); (2) ключ шифрования отсутствует в коде и в репозитории, задаётся переменной окружения; (3) пароль LDAP нигде не сохраняется (ни в БД, ни в кэше, ни в логах); (4) поиск по логам за период тестирования не находит значений токенов, ключей и паролей.

### FR-035: Фильтр потребностей по группам статусов

Названия статусов берутся из Jira как есть.

Критерии приёмки: (1) клик по группе сразу оставляет в таблице потребности только с её статусами; (2) счётчик группы равен числу потребностей в ней; (3) при первом входе активна группа «Без кандидата»; (4) любая потребность видна хотя бы в группе «Прочие» или в режиме «Все статусы»; (5) после повторного входа активна ранее выбранная группа.


### FR-036: Сопоставление потребности с кандидатами
**Тип:** functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики

Для каждого кандидата показываются: ФИО, статус сотрудника, % совпадения (цветовая шкала), значок заметки (FR-033), кнопки «Резюме» (открыть Основное CV, FR-037) и «Назначить» (FR-008). Первоначально показываются 10 лучших, остальные — по «Показать ещё». Подсказка с обоснованием оценки показывается по клику на %. Повторное открытие потребности показывает сохранённый результат с датой расчёта и кнопкой «Пересчитать». Если подходящих нет — сообщение; пользователь может перейти к смене статуса «Кандидатов нет» (FR-011).

### FR-039: Замена основного CV с архивом прежних версий
**Тип:** functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

При загрузке файла типа «Основное CV» (FR-022) Система ДОЛЖНА заменять прежнее основное CV сотрудника новым. Прежняя версия ДОЛЖНА сохраняться в архиве (последние 3 версии) и быть доступной для восстановления пользователем. При загрузке четвёртой и последующих версий самая старая версия из архива удаляется.

Критерии приёмки: (1) после загрузки нового основного CV у сотрудника ровно одно актуальное основное CV; (2) прежнее основное CV появляется в архиве; (3) в архиве не более 3 версий; (4) восстановление версии из архива делает её актуальным основным CV, а текущее уходит в архив.


### FR-040: Скачивание и удаление файлов сотрудника
**Тип:** functional | **Версия:** 1.0 | Приоритет: Should  
**Owner:** Руководитель направления Аналитики  

Пользователь ДОЛЖЕН мочь скачать любой файл сотрудника и удалить файл типа «Доп. CV» или «Материалы» из списка в столбце «Файлы». Загруженное актуальное (последнее) основное CV напрямую не удаляется, оно только заменяется новым (FR-039).

Критерии приёмки: (1) кнопка скачивания отдаёт исходный файл без изменений; (2) удалённый файл исчезает из списка и не участвует в сопоставлении и назначении; (3) для актуального основного CV действие «Удалить» недоступно.
