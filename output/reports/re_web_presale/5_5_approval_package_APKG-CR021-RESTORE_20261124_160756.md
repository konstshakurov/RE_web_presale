### FR-002: Список сотрудников со статусами, мультивыбором статусов и фильтром по РО
**Тип:** functional | **Версия:** 1.1 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА отображать список сотрудников (карточки Jira типа Epic) с фильтром по статусу из 10 статусов Jira: Выход новичка, Программа обучения, Внутренний проект, Свободен, Коммерческий проект, Ожидает подключения, Скоро освобождается, Недоступен для подключения, Уволен, Декрет. Для каждой карточки ДОЛЖНЫ показываться описание, отпуска и переход к CV. Для назначения на потребность ДОЛЖНЫ быть доступны сотрудники в статусах: Выход новичка, Программа обучения, Внутренний проект, Свободен, Ожидает подключения, Скоро освобождается. Сотрудники в статусах Коммерческий проект, Недоступен для подключения, Уволен, Декрет НЕ ДОЛЖНЫ назначаться.

Фильтр статусов ДОЛЖЕН быть мультивыбором: ряд чипов «Все N» и девяти статусов, кроме «Уволен» — он остаётся отдельным тумблером «Уволенные». Статусы между собой ДОЛЖНЫ сочетаться по ИЛИ; статусы, РО, поиск и «Уволенные» — по И. Повторное нажатие чипа ДОЛЖНО снимать выбор; при нуле выбранных нажат чип «Все N». Выбранный чип ДОЛЖЕН быть отличим без цвета (галочка перед подписью).

Система ДОЛЖНА предоставлять фильтр «РО»: список «Все» (по умолчанию), отображаемые имена руководителей отдела из Jira по алфавиту, последним «Без РО». Данные — поле Jira «Руководитель отдела» (customfield_14401, отображаемое имя). Значение-заглушка «Не назначен» ДОЛЖНО трактоваться как отсутствие РО («Без РО»); неактивные и скрытые настройкой окружения РО в списке НЕ ДОЛЖНЫ показываться. РО в карточке сотрудника НЕ ДОЛЖЕН показываться.

Под панелью ДОЛЖНА быть строка «Показано N из M»: M — число сотрудников с учётом «Уволенные», без остальных фильтров; счётчики статусов и «Все» ДОЛЖНЫ считаться с учётом РО и «Уволенные», без учёта поиска. При заданном хотя бы одном фильтре в строке ДОЛЖНЫ перечисляться только заданные условия и быть ссылка «Сбросить фильтры», возвращающая все фильтры в исходное состояние. Фильтр по технологии на «Сотрудниках» НЕ ДОЛЖЕН добавляться.

**Критерии приёмки:** 1. Можно выбрать несколько статусов; список показывает сотрудников любого из выбранных (ИЛИ); повторное нажатие снимает выбор; при нуле выбранных нажат «Все N».
2. «РО» по умолчанию «Все»; выбор имени оставляет сотрудников этого РО; в сочетании со статусами, поиском и «Уволенные» результат — пересечение (И).
3. «Сбросить фильтры» возвращает все фильтры в исходное состояние; ссылка видна только при заданном фильтре.
4. Строка «Показано N из M» совпадает с числом карточек; перечень условий называет только заданные.
5. «Без РО» — последний пункт списка; выбор показывает сотрудников с пустым РО («Не назначен» в Jira трактуется как пустое); сочетается с остальными фильтрами по И.
6. Неактивные и скрытые настройкой окружения РО в списке фильтра не показываются; РО в карточке сотрудника не выводится.
7. Счётчики статусов и «Все» считаются с учётом РО и «Уволенные», без учёта поиска.
8. Состояния (загрузка, ошибка списка, ошибка списка РО с работающими остальными фильтрами, пустой результат) показаны текстами решения KON-134 v5.
9. На 1280 и 1024 в обеих темах фильтры помещаются без наложений и горизонтальной прокрутки; выбранный чип отличим без цвета (галочка); Tab/Enter/Space работают, фокус виден.
10. Правила назначения по статусам из первой части требования не изменены.

### FR-005: Рекомендация кандидата с % соответствия и обоснованием
**Тип:** functional | **Версия:** 1.1 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА по запросу пользователя («Сопоставить», FR-036) оценивать соответствие сотрудников выбранной потребности: процент и краткое текстовое обоснование, рассчитанные LLM по Основному CV (FR-027) и требованиям потребности — опыт в годах, отрасли, инструменты, опыт в системах, профессия. В оценку ДОЛЖНА учитываться свободная заметка о сотруднике (FR-033, например «не подключать в ЛеманаПРО»). Оцениваются только сотрудники в статусах, допустимых для назначения (FR-002) и имеющие Основное CV. Результат — рекомендация; решение принимает пользователь. Метрик качества не задаётся (ISS-006). Для снижения нагрузки на LLM система ДОЛЖНА сначала отобрать сотрудников детерминированно (по технологиям, статусу), а LLM оценивать только отобранных (предложение); результат кэшируется по связке «потребность + Основное CV + модель» и пересчитывается при изменении потребности или CV.

### Правила объективности вывода (v1.1, CR-019)

1. **Только по требованиям потребности:** критерии и формулировки — из текста потребности (описание, требования, поля Jira) и заметки о сотруднике (FR-033). Модель НЕ привносит собственные пороги и знания о грейдах (уровни «Senior» и прочее); требование не сформулировано явно в потребности — не учитывается ни в проценте, ни в обосновании, ни в «чего не хватает».
2. **Формулировка нехватки — «в CV не указан/не упомянут X»:** «нет опыта X», «отсутствует опыт X», «нет упоминания X» — запрещены (не-упоминание в CV ≠ отсутствие опыта).
3. **Согласованность вывода:** percent < 100 ⟺ в gaps перечислены причины; каждый пункт gaps — причина снижения процента; формулировки вида «полностью закрывает требования» при percent < 100 — запрещены.
4. **Без модальностей домысла:** «может считаться», «может не соответствовать», «ожидаемый уровень» — запрещены.
5. **Пост-обработка (защитный слой):** нормализация формулировок (п. 2–3) и отсечение модальностей (п. 4) реализуются в коде приложения и покрыты unit-тестами.
6. **Golden-кейсы:** фиксированные пары «CV + потребность» — для регрессии при смене промптов/моделей (правила от смены модели не меняются).

### FR-011: Статусы «Кандидатов нет» и «Найм»
**Тип:** functional | **Версия:** 1.3 | Приоритет: Should  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА позволять перевести потребность в статусы «Поиск кандидата», «Найм» и «Кандидатов нет» кнопками в столбце «Статус» раздела «Потребности». Кнопка показывается, только если Jira отдаёт этот переход для текущего статуса потребности (FR-026): «Требуется кандидат» → Поиск / Найм / Кандидатов нет; «Поиск кандидата» → Найм / Кандидатов нет; «Кандидатов нет» → Поиск / Найм; «Найм» → Поиск / Кандидатов нет; «Кандидат назначен» → Поиск / Найм / Кандидатов нет. Для прочих статусов (включая «Отказ по кандидату») кнопок нет; «Кандидат назначен» выставляется только при назначении (FR-008).

При переходе «Кандидатов нет» ДОЛЖНЫ запрашиваться обязательные поля Jira: «Причина отсутствия кандидата» (значения справочника Jira: Нет специалистов данного уровня, но есть слабее; …конкретного набора стека; …нужной отраслевой экспертизой; …нужным специфичным стеком (стек в комментарии); Низкая ставка; Увольнение/декрет кандидата; Требуется очное присутствие; Есть прямой запрос) и «Комментарий» (видимость «для всех»). Для «Поиск кандидата» — подтверждение одним кликом. Для «Найм» (переход «В найм») Jira требует ставку целиком — «Включает НДС», «Валюта», «Единица измерения» (customfield_20810–20812): значения предзаполняются из потребности, при отсутствии запрашиваются; проверка обязательности — до отправки (проба KON-30). Саму ставку («Планируемая ставка», 20809) при найме не вводят: она вносится при назначении (FR-018); значения справочников передаются по id, полученным у Jira. Значения справочника и обязательные поля ДОЛЖНЫ запрашиваться у Jira, а не храниться в приложении (см. FR-026).

### FR-014: Выявление дублей потребностей

### Правила объективности вывода (v1.1, CR-019)

1. **Только по требованиям потребности:** критерии и формулировки — из текста потребности (описание, требования, поля Jira) и заметки о сотруднике (FR-033). Модель НЕ привносит собственные пороги и знания о грейдах (уровни «Senior» и прочее); требование не сформулировано явно в потребности — не учитывается ни в проценте, ни в обосновании, ни в «чего не хватает».
2. **Формулировка нехватки — «в CV не указан/не упомянут X»:** «нет опыта X», «отсутствует опыт X», «нет упоминания X» — запрещены (не-упоминание в CV ≠ отсутствие опыта).
3. **Согласованность вывода:** percent < 100 ⟺ в gaps перечислены причины; каждый пункт gaps — причина снижения процента; формулировки вида «полностью закрывает требования» при percent < 100 — запрещены.
4. **Без модальностей домысла:** «может считаться», «может не соответствовать», «ожидаемый уровень» — запрещены.
5. **Пост-обработка (защитный слой):** нормализация формулировок (п. 2–3) и отсечение модальностей (п. 4) реализуются в коде приложения и покрыты unit-тестами.
6. **Golden-кейсы:** фиксированные пары «CV + потребность» — для регрессии при смене промптов/моделей (правила от смены модели не меняются).
