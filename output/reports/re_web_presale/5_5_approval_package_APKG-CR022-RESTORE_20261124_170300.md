### FR-005: Рекомендация кандидата с % соответствия и обоснованием
**Тип:** functional | **Версия:** 1.1 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА по запросу пользователя («Сопоставить», FR-036) оценивать соответствие сотрудников выбранной потребности: процент и краткое текстовое обоснование, рассчитанные LLM по Основному CV (FR-027) и требованиям потребности — опыт в годах, отрасли, инструменты, опыт в системах, профессия. В оценку ДОЛЖНА учитываться свободная заметка о сотруднике (FR-033, например «не подключать в ЛеманаПРО»). Оцениваются только сотрудники в статусах, допустимых для назначения (FR-002) и имеющие Основное CV. Результат — рекомендация; решение принимает пользователь. Метрик качества не задаётся (ISS-006). Для снижения нагрузки на LLM система ДОЛЖНА сначала отобрать сотрудников детерминированно (по технологиям, статусу), а LLM оценивать только отобранных (предложение); результат кэшируется по связке «потребность + Основное CV + модель» и пересчитывается при изменении потребности или CV.

### Правила объективности вывода (v1.1, CR-019)

1. **Только по требованиям потребности:** критерии и формулировки — из текста потребности (описание, требования, поля Jira) и заметки о сотруднике (FR-033). Модель НЕ привносит собственные пороги и знания о грейдах (уровни «Senior» и прочее); требование не сформулировано явно в потребности — не учитывается ни в проценте, ни в обосновании, ни в «чего не хватает».
2. **Формулировка нехватки — «в CV не указан/не упомянут X»:** «нет опыта X», «отсутствует опыт X», «нет упоминания X» — запрещены (не-упоминание в CV ≠ отсутствие опыта).
3. **Согласованность вывода:** percent < 100 ⟺ в gaps перечислены причины; каждый пункт gaps — причина снижения процента; формулировки вида «полностью закрывает требования» при percent < 100 — запрещены.
4. **Без модальностей домысла:** «может считаться», «может не соответствовать», «ожидаемый уровень» — запрещены.
5. **Пост-обработка (защитный слой):** нормализация формулировок (п. 2–3) и отсечение модальностей (п. 4) реализуются в коде приложения и покрыты unit-тестами.
6. **Golden-кейсы:** фиксированные пары «CV + потребность» — для регрессии при смене промптов/моделей (правила от смены модели не меняются).

### FR-014: Выявление дублей потребностей
**Тип:** functional | **Версия:** 1.1 | Приоритет: Could  
**Owner:** Руководитель направления Аналитики  

Система ДОЛЖНА выявлять дубли потребностей по описанию (не по названию) и показывать % совпадения. Сравнение ведётся с потребностями на аналитиков за последние 2 недели во всех статусах. Дублем с очень высокой вероятностью считается совпадение 15% и более текста, описывающего требования к кандидату (опыт, компетенции, навыки, инструменты), полностью совпадающего в последовательном изложении (не вразброс). Для сравнения ДОЛЖЕН использоваться статус, а не резолюция (БП-10).

Расчёт дублей ДОЛЖЕН выполняться при синхронизации (FR-028); допущение: список дублей отдаётся со списком потребностей (GET /sync/needs, поле duplicates: ключ, %, название, тип, ставка).

Для каждой найденной связи-дубля система ДОЛЖНА предоставлять классификацию «Похожая / Дубль»: в строке дубля — кнопка «Похожая ⌄» с выпадающим списком «Похожая» / «Дубль»; выбранный пункт ДОЛЖЕН сохраняться персистентно и НЕ ДОЛЖЕН сбрасываться при пересинхронизации или пересчёте. Сохранённая классификация отображается как текст кнопки.

Место и форма показа — design/KON-165/decision.md (approved): индикатор «N дубля/дублей» отдельной строкой под названием потребности (без рамки и анимаций, высота 22px, шрифт 12px/600, склонение); раскрытие — блок под строкой; ключ записи на линии колонки «Название», название одной строкой (ellipsis), тип «Суб»/«Прямой», ставка цифрой или «—», пилюля % совпадения. «Дублей нет» — индикатор не показывается. Предупреждение информирует и не блокирует работу.

**Критерии приёмки:** 1. Дубли выявляются по описанию (не по названию) с порогом 15% и более совпадения требований к кандидату, в окне 2 недели, среди потребностей на аналитиков во всех статусах (по статусу, БП-10).
2. Индикатор «N дубля/дублей» показывается только при наличии дублей; склонение корректно; отдельной строкой под названием с интервалом; без рамки и анимаций; высота 22px.
3. Клик раскрывает блок под строкой; ключ записи — на линии колонки «Название»; название — одной строкой с ellipsis; далее тип «Суб»/«Прямой», ставка цифрой или «—», пилюля %, кнопка классификации.
4. Кнопка «Похожая ⌄» фиксированной ширины (120px), текст слева, шеврон в едином месте справа; меню «Похожая / Дубль», выбранный пункт с ✓.
5. Выбранная классификация сохраняется на сервере и переживает пересинхронизацию и пересчёт дублей.
6. «Дублей нет» — индикатор не показывается.
7. Обе темы, 1280/1024; фокус видимый; длинные названия не ломают строку.

### FR-019: Средняя и медианная ставки за период

Система ДОЛЖНА позволять настроить внешние LLM через ввод API Key и URL. По умолчанию используется корпоративная Qwen. Claude подключается только через API-ключ, не через личный аккаунт. Во внешнюю модель уходит только обезличенный текст (FR-023). Ключи ДОЛЖНЫ храниться зашифрованно (NFR-006). Таймаут запроса к LLM — 120 с, настраиваемый.


### BR-007: Корпоративный формат CV
**Тип:** business_rule | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Корпоративный формат CV включает разделы: профиль, основной стек, отрасли, ключевые навыки, языки, образование, проекты. Корпоративное CV содержит только имя, без фамилии и контактов.


### NFR-007: Отдельная БД для CV
**Тип:** non_functional | **Версия:** 1.0 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

CV, компетенции и навыки ДОЛЖНЫ храниться в отдельной БД на бэкенде, отдельной от интеграционных настроек и токенов.

Критерии приёмки: (1) таблицы с CV, компетенциями и навыками находятся в отдельной БД со своей строкой подключения; (2) таблиц токенов и интеграционных настроек в этой БД нет; (3) учётная запись, под которой приложение работает с БД CV, не имеет доступа к хранилищу токенов, и наоборот.


### NFR-006: Защита токенов и ключей
**Тип:** non_functional | **Версия:** 1.1 | Приоритет: Must  
**Owner:** Руководитель направления Аналитики  

Сессионные токены Jira пользователей, API-ключи LLM и прочие креды интеграций ДОЛЖНЫ храниться зашифрованно; ключ шифрования ДОЛЖЕН быть вынесен в переменные окружения. Пароли LDAP НЕ ДОЛЖНЫ храниться. Токены и пароли НЕ ДОЛЖНЫ попадать в логи в открытом виде.

Критерии приёмки: (1) в БД нет ни одного токена или ключа в открытом виде (проверка выборкой по хранилищу); (2) ключ шифрования отсутствует в коде и в репозитории, задаётся переменной окружения; (3) пароль LDAP нигде не сохраняется (ни в БД, ни в кэше, ни в логах); (4) поиск по логам за период тестирования не находит значений токенов, ключей и паролей.

**CR-история:** CR-009 (approved/Approved)
