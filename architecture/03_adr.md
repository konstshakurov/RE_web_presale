# ADR (все со статусом «предложено», финал за Константином)

## ADR-001. Модульный монолит + отдельный процесс worker
Контекст: 4 пользователя, 10-100 потребностей в неделю, команда из ИИ-агентов, горизонт 1 месяц.
Решение: один кодовый репозиторий бэкенда, модули с чёткими границами (см. 01_c4.md), два процесса (`api`, `worker`).
Отклонено: микросервисы (избыточно, конфликт «малая команда + микросервисы»).
Последствия: проще деплой и отладка; границы модулей фиксируются тестами импортов.

## ADR-002. Стек Python/FastAPI + React/TS + PostgreSQL 16 (подтверждено владельцем)
Причина: скорость агентской разработки, библиотеки для LDAP, DOCX, OAuth1. Альтернатива Node/NestJS отклонена.

## ADR-003. Две БД PostgreSQL с раздельными ролями (NFR-007)
`cv_db` (сотрудники, файлы, текст, навыки), `app_db` (токены, ключи, настройки, кэш Jira, сессии).
Роли `cv_rw` и `app_rw` без прав на чужую БД. Связь между БД только по `jira_key` сотрудника, без межбазовых запросов.
Последствия: нет транзакций между БД; консистентность на уровне приложения (запись в `cv_db` первична).

## ADR-004. Jira: опрос + локальный кэш, без вебхуков (FR-028, NFR-008)
Потребности: инкрементальный JQL `updated >= last_sync - 1 мин` каждые 5 мин, только нужные поля, первичная загрузка за 6 месяцев.
Сотрудники (Epic): раз в час и по кнопке. Эпики клиентов и правила: при открытии, кэш 1 час, дети эпика через Agile API.
Списки читаются только из кэша (индексы по статусу, дате); штамп «актуально на» и кнопка «Обновить».
Перед записью потребность перечитывается. Вебхуки вне скоупа (6.4).
Фоновый опрос идёт сессией активного пользователя и приостанавливается без активных сессий (решение владельца, ADR-005); штамп «актуально на» показывает фактическую свежесть.

## ADR-005. Авторизация в Jira: сессионная cookie пользователя (результат пробы KON-30, решения владельца 05.10)
Факт пробы (`architecture/probes/KON-30_jira_probe_report.md`): Jira 8.13.0, PAT невозможен; чтение и запись подтверждены на живой Jira сессионной cookie `JSESSIONID` конкретного пользователя без тех. учётки и без Application Link; действия видны в истории Jira от имени пользователя.
Решение: основной способ и на этапе 1, и на этапе 2 — сессионная cookie. OAuth 1.0a на этапе 1 не используется. Application Link — запасной вариант (нужен только если опрос без активных сессий станет неприемлемым).
Порт `JiraPort` и клиент `src/jira_client/` уже готовы (чтение, запись, переходы, классификация 401, шифрование токена `TokenVault`, 258 тестов); задачи Dev-3 и Dev-11 сводятся к доработке и интеграции.
Создание сессии (решение владельца): логин и пароль Jira совпадают с LDAP, поэтому при входе в приложение один ввод пароля используется дважды в рамках одного запроса: LDAP bind (ADR-008) и обмен на сессию Jira (`POST /rest/auth/1/session`, плоское тело `{"username","password"}`); пароль не сохраняется, живёт только в памяти запроса, не попадает в БД, кэш, логи, трассировку. Для этого включается `SessionLoginProvider` (флаг `enabled`). Истёкшая сессия: пароль вводится повторно тем же способом, введённые данные не теряются.
Фоновый опрос (ADR-004): идёт сессией активного пользователя; без активных сессий приостанавливается (решение владельца: приемлемо, соответствует FR-028).
Проверка сессии: `/rest/api/2/myself` перед операцией; 401 неоднозначен, различаем по телу (`no_credentials`, `login_required`, `no_permission`, `auth_failed`, `invalid_cookie_or_expired`); «нет прав» повторной авторизацией не лечится; «Jira недоступна» и «сессия истекла» не смешиваем; HTML-ответ 401 пользователю не показываем.
Особенности записи: смена статуса требует комментарий через `update.comment.add` (переход 171 «Кандидатов нет»; REST его как обязательное не объявляет), вложения требуют `X-Atlassian-Token: no-check`, `transitions[].fields` приходит словарём; связь задача-эпик через `Epic Link` (`customfield_10101`) или Agile API, `parent` не работает.
Сервисная учётка отклонена (OPT-003 нарушает BR-001, FR-009, FR-025).
Последствия: риск RK-001 снят фактом; остаётся срок жизни сессии (не измерен) и частота повторного ввода пароля; браузеру напрямую в Jira нельзя (нет CORS), только через `api`.

## ADR-006. Токены и ключи: AES-256-GCM, ключ в окружении (NFR-006)
Шифруются сессионный токен Jira (`TokenVault`, AES-256-GCM, ключ из env) и API-ключи LLM; пароль пользователя Jira/LDAP не хранится нигде, живёт в памяти запроса. `APP_ENC_KEY` только в env контейнера (не в образе, не в Git),
в записи хранится `key_id` для ротации. Пароль LDAP не хранится нигде (bind и забыть). Фильтр логов вырезает токены, ключи, пароли, заголовки Authorization и Cookie.

## ADR-007. Единый шлюз LLM с обезличиванием (FR-023, FR-030, NFR-010)
Все обращения к LLM идут только через `llm_gateway`. Провайдеры: внутренняя Qwen (по умолчанию, без обезличивания), внешние (URL + ключ).
Для внешнего: конвейер обезличивания (regex, словари клиентов/ФИО/проектов, NER), обязательный предпросмотр и подтверждение,
подстановки (плейсхолдеры) хранятся только в памяти запроса и возвращаются в ответ. Файлы для Jira не проходят через обезличивание.
Запросы асинхронные (задача в очереди), таймаут по умолчанию 120 с из настроек; UI не блокируется.
Исключение: FR-017, модель выбирает пользователь.

## ADR-008. Вход: LDAP bind + список допущенных + серверные сессии (FR-024, FR-021)
Проверка bind, затем наличие `ldap_login` в списке; сессия в `app_db`, cookie HttpOnly, Secure, SameSite=Lax, TTL 8 ч (допущение).
Отзыв доступа действует немедленно (сессия проверяется по списку на каждый запрос).
После успешного bind и проверки списка допущенных тем же запросом создаётся сессия Jira (ADR-005); пароль не сохраняется. Если Jira отказала при верном LDAP, вход в приложение выполняется, а работа с Jira блокируется с текстом отказа (FR-029).

## ADR-009. Файлы CV в `cv_db`, текст извлекается при загрузке (FR-004, FR-027, FR-039)
bytea, лимит 10 МБ, тип файла обязателен; архив основного CV: 3 последние версии; навыки выделяются LLM один раз и пересчитываются при замене файла.
Альтернатива: файловая система + метаданные в БД (отклонена: два места хранения, сложнее бэкап).

## ADR-010. On-premise: Docker Compose, сначала локально, затем ВМ с Linux (решение владельца 05.10)
Разработка и тестирование MVP идут локально (Docker Compose на машине владельца, тестовый LDAP-контейнер). Заявку на ВМ с Linux в Support подаём после локального тестирования готового MVP; Docker и остальное на ВМ настраиваем сами. Репозиторий: личный GitHub, перенос в корпоративный GitLab клонированием. Без HA: цель 99% в рабочее время (NFR-003) достигается restart policy, healthcheck и ежедневным бэкапом; нормативная проверка NFR-003/NFR-004 возможна только после деплоя на ВМ. TLS на nginx, доступ только из внутренней сети.
Последствия: деплой (KON-49) вынесен в конец и не блокирует Dev-цепочку; параметры реального LDAP нужны только к выкладке.

## ADR-011. Без аудит-журнала в БД, только технические логи (NFR-005)
Действия в Jira видны в истории Jira от имени пользователя. Технические логи (ошибки, время, ключи задач) без ПДн, токенов, текстов CV.
Уточнение трактовки отправлено аналитику (см. README).
