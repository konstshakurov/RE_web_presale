# ux_design — проектирование интерфейса внутреннего инструмента

Скилл для агента `ux`. Продукт — внутренний рабочий инструмент (потребности, сотрудники,
резюме, сопоставление, запись в Jira), а не маркетинговый сайт. Приоритет: скорость
работы пользователя, плотность данных, предсказуемость, понятные ошибки. «Выразительность»
вторична.

## Алгоритм

### 1. Понять задачу (Шаг 1)

Ответь письменно в `brief.md`, коротко:
- **Кто и зачем:** роль пользователя, цель, как часто делает (раз в день / сотни раз).
- **Требования:** ID FR/UC/BP и критерии приёмки; что обязано быть на экране.
- **Контекст:** откуда пользователь пришёл, куда идёт дальше, что уже есть в интерфейсе.
- **Ограничения:** стек (ADR), существующие токены и компоненты, данные, которых нет.
- **Допущения:** помеченные явно.

### 2. Опереться на существующее (Шаг 2)

Прежде чем рисовать новое — найди в `frontend/src/components/` и `design/` то, что можно
переиспользовать. Токены — из `frontend/src/styles.css` (`--bg`, `--panel`, `--accent`,
`--err`, `--ok`, `--warn`…), тёмная тема по умолчанию, светлая по `prefers-color-scheme`.
Новый токен или компонент — только с обоснованием, почему существующий не подходит.

### 3. Сколько вариантов (Шаг 3)

| Объём | Вариантов |
|---|---|
| Новый экран, смена структуры или потока | 3 (два допустимо, если третий искусственный) |
| Новый блок/компонент внутри экрана, заметное изменение | 2 |
| Точечная правка (текст, порядок полей, состояние) | 1 + «как сейчас» для сравнения |

Варианты должны различаться **осью решения**: структура (таблица / карточки / master-detail),
поток (одно окно / мастер по шагам / inline-редактирование), плотность и место действия
(панель, модалка, отдельная страница). Не три оттенка одного и того же.

### 4. Спроектировать каждый вариант (Шаг 4)

Для каждого варианта в прототипе должны быть показаны **все состояния**, а не только
«счастливый путь»:
- загрузка, пусто, ошибка (с текстом и действием), частично загружено, «нет прав»;
- для записи в Jira — подтверждение, прогресс, отказ перехода, истёкшая сессия (UC-005);
- крайние данные: очень длинное имя/название, много строк, ноль строк.

В `README.md` варианта: идея в одну фразу → плюсы → минусы → цена для Dev
(новые компоненты, новые эндпоинты, объём) → кому подходит.

### 5. Чек-лист самопроверки (Шаг 5)

- [ ] Каждое требование из задачи покрыто и показано на экране.
- [ ] Основное действие очевидно, одно на экран; деструктивные — с подтверждением.
- [ ] Метки полей видимы (не только placeholder); тексты на русском, единая терминология
      со спецификацией.
- [ ] Клавиатура: порядок Tab, видимый фокус, Enter/Esc в формах и модалках.
- [ ] Контраст текста ≥ 4.5:1 в обеих темах; смысл не передан только цветом.
- [ ] Ошибки: что произошло, что делать; без технических сообщений и без секретов.
- [ ] Пустое состояние объясняет, что делать, а не просто «нет данных».
- [ ] Реализуется в текущем стеке без новых зависимостей (или зависимость вынесена
      отдельным пунктом на согласование).
- [ ] Согласуется с `design/tokens.md` и ранее утверждёнными решениями.

### 6. Согласование и фиксация (Шаг 6)

1. Отдай владельцу: ссылки на файлы вариантов, сравнительную таблицу, **твою
   рекомендацию с причиной** и список открытых вопросов. Один экран — один пакет.
2. Не передавай Dev ничего до явного апрува. «Нравится вариант B, но…» — это правки:
   обнови и согласуй снова.
3. После апрува запиши `decision.md` — см. шаблон ниже — и оставь ссылку в задаче Linear.

## Шаблон `decision.md`

```markdown
# <KON-N> <название> — решение по UI

Статус: approved | дата: ДД.ММ.ГГГГ | утвердил: Константин
Выбран вариант: <A/B/C> (+ поправки владельца: …)

## Что реализовать
Компоненты, состояния, тексты интерфейса, поведение (клавиатура, ошибки).

## Токены и стили
Какие токены из styles.css используются; новые (если согласованы).

## Данные и API
Какие поля/эндпоинты нужны; чего нет и как обработать (допущение).

## Критерии приёмки UI
Проверяемые утверждения для Dev и QA: «при …, на экране …».

## Вне объёма
Что намеренно не делаем и почему.
```

## Внешние источники (для справки, не обязательны)

Идеи, на которые опирались при составлении скилла; сторонний код в проект не подключён:
официальный `frontend-design` (Anthropic) — про визуальное направление;
`ui-ux-pro-max` — база UX-правил; `taste-skill` — вариативность визуальных направлений.
Они ориентированы на публичные сайты; для внутреннего инструмента важнее чек-лист выше.
