## Общая информация

| Атрибут | Значение |
|---------|----------|
| Актор (primary) | РН / РО / Presale-менеджер |
| Акторы (secondary) | Jira, LLM |
| Предусловие | Пользователь вошёл и авторизован в Jira; потребность есть в кэше; у сотрудников загружены Основные CV. |
| Постусловие | В Jira у потребности заполнены профиль сотрудника и исполнитель, прикреплены выбранные файлы, добавлен комментарий (и ставка, если задана). |
| Триггер | Пользователь выбирает потребность в разделе «Потребности». |

## Основной сценарий (Happy Path)

1. Пользователь фильтрует потребности по группе статусов (по умолчанию «Без кандидата»).
2. Система показывает таблицу: запрос, исполнитель, требования, правила клиента и предупреждение о дубле.
3. Пользователь нажимает «Сопоставить».
4. Система отбирает сотрудников в допустимых статусах, оценивает их с помощью LLM и показывает кандидатов с % совпадения.
5. Пользователь при необходимости открывает «Резюме» кандидата.
6. Пользователь нажимает «Назначить».
7. Система открывает окно: резюме (по умолчанию Основное), ставка руб. с НДС, комментарий, файлы из БД сотрудника.
8. Пользователь заполняет поля и подтверждает.
9. Система перечитывает потребность и передаёт данные в Jira от имени пользователя; исполнитель — пользователь.
10. Система показывает результат.

## Альтернативные сценарии

7а. Пользователь нажимает «CV по шаблону» (UC-004) и выбирает созданное CV.
8а. Потребность уже назначена — система предупреждает; пользователь подтверждает замену (FR-010).

## Сценарии исключений

4а. LLM не ответила за 120 с — таймаут, можно повторить.
4б. Подходящих кандидатов нет — сообщение; пользователь может сменить статус на «Кандидатов нет» (UC-002).
9а. Jira отказала — причина показывается как есть, введённые данные сохраняются.
9б. 401 — повторная авторизация в Jira.

## Бизнес-правила и ограничения

BR-001, BR-002, BR-003, BR-006; нарушение правил клиента не блокирует отправку.
