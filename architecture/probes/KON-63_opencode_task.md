# Задача для OpenCode: KON-63 (Pre.QA-7), живая часть — проверка синхронизации на реальной Jira

Срок: по готовности, без жёсткой даты. Условие: доступ к корпоративной сети (VPN) и тестовая учётка Jira у Константина.

## Зачем эта часть отдельно

Основной объём KON-63 (опрос, пауза, отказы, идемпотентность, список на 500 записей) QA проверяет на фейке `JiraPort` и стенде с тестовым LDAP — без VPN и без живой Jira. Здесь остаётся то, что фейк подтвердить не может: поведение **настоящей** Jira Server 8.13.0 и реальные данные. Задача только на **чтение**: ничего не создавать, не менять, не комментировать.

## Контекст

Репозиторий `re_web_presale`. Модуль чтения: `src/jira_client/` (httpx) и адаптер `backend/app/integrations/jira/` (`JiraPort`: `login`, `check_session`, `search_incremental`, `get_issue`, `get_epic`, `get_epic_children`). Синхронизация: `backend/app/sync/` (опрос, кэш, штамп «актуально на», классификация отказов, `rate_dropped`). Прочитать: `src/jira_client/README.md`, `architecture/probes/KON-30_jira_probe_report.md`, `architecture/probes/KON-34_report.md`, `qa/requirements_matrix.md` (FR-028, FR-029, FR-034, FR-035, NFR-002, NFR-008).

Способ доступа: сессионная cookie пользователя, пароль Jira = корпоративный LDAP. Пароль и токен в репозиторий, логи, отчёт, Linear не попадают (передавать через переменные окружения процесса).

Область записи: только `architecture/probes/KON-63_report.md` и, при необходимости, новый скрипт в `scripts/` или `architecture/probes/` (без секретов). Код `backend/`, `src/jira_client/`, миграции и compose не менять — обнаруженные дефекты фиксировать в отчёте.

## Что проверить (только чтение)

1. **Вход и сессия.** `login` + `check_session` на живой Jira: `ok`. Замерить время одного входа и одного `check_session`.
   - Неверный пароль проверять **не более одного раза** и только если Константин подтвердил отдельной учёткой: повторные неверные попытки могут вызвать CAPTCHA/блокировку учётки (`AUTHENTICATION_DENIED`). Если такой учётки нет — этот пункт пропустить и записать «не проверялось».
2. **Классификация отказов на реальных ответах.** Без подбора пароля: чтение задачи, к которой у учётки нет прав (ключ даст Константин) → `no_permission`; несуществующий ключ → ожидаемая ошибка 404 без падения; текст отказа Jira записывается в отчёт как есть (FR-029), без секретов.
3. **Инкрементальный опрос.** `search_incremental` по `updated` с реальным JQL проекта потребностей: число задач, число страниц, время; повторный вызов с курсором «сейчас минус минута» возвращает только изменённые; нет потери задач на границе минуты (курсор с точностью до минуты — сверить с пересечением по границе).
4. **Объём и NFR-002/NFR-008.** Полная выборка потребностей и сотрудников: количество записей, время загрузки, размер ответа; оценить, укладывается ли первичная загрузка в разумное время и сколько занимает цикл опроса. Записать числами.
5. **Данные и маппинг.** По 20–30 реальным потребностям сверить поля с тем, что кладёт синхронизация: ключ, статус как есть, эпик (`customfield_10101` и Agile API), клиент, тип контракта, ставка и валюта. Отдельно перечислить встречающиеся валюты и «НДС», случаи, которые уходят в `rate_dropped` (EUR/GBR, RUB без НДС), и нестандартные форматы ставки, которых парсер, возможно, не знает. Для сотрудников: статусы карточек против 10-статусной модели (FR-002), поле «Отпуск», поле опыта (`customfield_13504`).
6. **Агрегаты для обезличивания (без ПДн в отчёте).** Сколько потребностей содержат e-mail, телефоны, Telegram-логины, ссылки — только **количества**, не сами значения.
7. **Время жизни сессии Jira** (определяет, как часто пользователю вводить пароль повторно): если удаётся замерить без ожидания часов — оценить по `Set-Cookie` (`Max-Age`/`Expires`) и по `check_session` через интервалы; иначе записать как «не измерено».

## Ограничения безопасности

- Только GET и вход (`POST /rest/auth/1/session`). Любые POST/PUT/DELETE в задачи, комментарии, статусы — запрещены.
- Не более одной параллельной сессии, пауза между запросами ≥ 200 мс, лимит 10 с на вызов (NFR-009).
- Фикстуры из реальных данных в репозиторий не класть.

## Что вернуть

Файл `architecture/probes/KON-63_report.md`: что проверено (команда → результат), числа (время, объёмы), расхождения с ожиданиями фейка/кода, список дефектов (для каждого — шаги и ожидаемое/фактическое), что не удалось и почему, открытые вопросы. Дефекты Константин заведёт в Linear с лейблом Bug.
