## Описание CR

**Название:** Откат CR-007: ставка вносится при назначении через ScriptRunner (KON-99)  
**Тип:** change_existing | **Инициатор:** Владелец продукта (Константин Шакуров), по результатам пробы KON-99  
**Открыт:** 2026-10-20  
**Регуляторный:** Нет  

Проба KON-99 (20.10.2026, ANALYTICS-5925) опровергла основание CR-007 (проба KON-42: «ставка только на переходе 801»). Кнопка «Ставка» в карточке — custom REST endpoint ScriptRunner: диалог GET /rest/scriptrunner/latest/custom/rateCalculationWindow, сохранение POST /rest/scriptrunner/latest/custom/rateCalculationLogic (JSON: issueKey, currentUserUsername, customfield_21105 «Кто предлагает ставку» [22412 = Производство], 20809 ставка числом-строкой, 20810 НДС, 20811 валюта, 20812 единица — справочники по id). Запись подтверждена пробой (2500 -> 2700, статус не менялся); доступна в статусах «Поиск кандидата», «Кандидат назначен», «Найм», «Кандидатов нет», «Отказ по кандидату», до и после перехода 21. Решение: CR-007 откатывается. Ставка «от производства» вводится в окне «Назначить» (FR-018 v1.0, ориентир FR-019 рядом) и записывается в Jira отдельным вызовом ScriptRunner в рамках действия «Назначить» (не полями перехода, не PUT /issue); при «Найм» ставка не вводится (значения 20810–20812 для перехода 801 предзаполняются из потребности, FR-011 как в v1.1). Новое требование к интеграции (FR-018/FR-026): валидировать id справочников у себя, не отправлять пустую ставку (Jira отвечает 500), ВСЕГДА передавать 21105, после записи перечитывать поле (на неверный id и отсутствие 21105 Jira отвечает 200, но не пишет), несуществующий ключ (500) классифицировать как ошибку запроса, не недоступность Jira. Нестандартный плагин — зависимость в NFR/рисках. Не проверено: видимость кнопки для ролей РН/РО/Presale; как выставляется 21105 при «Клиент». Затронуто: FR-018 (откат v2.0 -> 3.0 с механизмом ScriptRunner), FR-008, FR-011, FR-026, UC-001; макет KON-98 (ставка в Найм) отменяется, KON-79 — окно «Назначить» со ставкой, KON-97/KON-95 перенацеливаются.

## Решение

**✅🔧 Approved_with_Modification**  
**Принял:** Константин Шакуров  
**Дата решения:** 2026-10-20  

**Обоснование:**  
Проба KON-99 (20.10.2026) опровергла основание CR-007: ставка записывается отдельным эндпоинтом ScriptRunner rateCalculationLogic, доступным и до, и после перехода 21; запись подтверждена (2500 -> 2700, статус не менялся). Действует бизнес-правило владельца: ставка «от производства» вносится при назначении кандидата, при найме не вводится. CR-007 откатывается.

**Изменения скоупа:**  
(1) Ставка вводится в окне «Назначить» (FR-018 по смыслу v1.0, ориентир FR-019 рядом) и пишется в Jira отдельным вызовом POST /rest/scriptrunner/latest/custom/rateCalculationLogic в рамках действия «Назначить» (не полями перехода, не PUT /issue). (2) В диалоге «Найм» ставка не вводится; значения 20810–20812 для перехода 801 предзаполняются из потребности (FR-011 как в v1.1). (3) Ставку отправляем только при «Кто предлагает ставку» = «Производство» (21105 = 22412, поле обязательно по БП-2); если ставку предлагает «Клиент» — свою ставку не отправляем и поле в окне «Назначить» не показываем как вводимое. (4) Требования к интеграции: валидировать id справочников у себя; пустую ставку не отправлять (Jira даёт 500); всегда передавать 21105; после записи перечитывать поле (на неверный id и отсутствие 21105 Jira отвечает 200 без записи); 500 на несуществующий ключ — ошибка запроса, не недоступность Jira. (5) Кнопка/действие «Назначить» в нашей системе доступно по правам нашей системы (BR-001, права операций определяет Jira); видимость кнопки «Ставка» в Jira для ролей РН/РО/Presale не проверялась — открытый вопрос KON-99, проверяется фактическим ответом Jira при записи под учёткой пользователя (ошибка Jira показывается как есть, FR-029).
