# YouGile-трекер: автоматическое передвижение задач по колонкам

Правило владельца (Константин, 05.11.2026): **агент обязан сам передвигать задачу
в YouGile по колонкам доски «Задачи» проекта REW по мере работы.** Ручное передвижение
владельцем не предусмотрено; задача, «зависшая» не в той колонке, — сбой агента.

## Доска и колонки (project REW, board dd90e28c-b1a4-4b9e-ae81-e6d004de5f62)

| Колонка | columnId | Когда |
|---|---|---|
| Backlog | `fba67ebd-ac85-4c82-8501-6c1e797a1856` | задача взята в план, работа не началась |
| In Progress | `e913a187-ed9d-4f92-b0fd-e2c27f982eb3` | работа реально началась |
| In Review | `5e807ed1-4d08-4062-9a8a-9d56e78b20b1` | реализация завершена, ждёт проверки |
| Done | `9fccad5f-1d07-417d-983b-a14371fc0755` | критерии приёмки выполнены и приняты |

## Когда в какую колонку

1. **In Progress** — в момент, когда агент взял задачу и начал хоть что-то делать
   (первое чтение проблемы, планов, код): вызов MCP `yougile.manage_tasks` с
   `columnId` про In Progress и существующим `id` задачи; `color: "primary"`
   (перечень цветов обязателен даже при простом переносе).
2. **In Review** — код готов, QA-гейт прошёл локально (ruff/pytest, lint/vitest),
   описание задачи обновлено (что сделано, что осталось). Это сигнал QA-агенту.
3. **Done** — только после Pass от QA (или по факту приёмки владельцем для задач
   без QA). Не переносить в Done самовольно, если критерии приёмки не выполнены.
4. Ничего не делать, если работа не идёт: Backlog остаётся Backlog; вернуться в
   Backlog из In Progress возможно, если текущий шаг заблокирован извне
   (указать причину в комментарии задачи — `send_chat_message` с коротким пойдём).

## Ограничения

- Одновременно **не более одной** задачи в In Progress на одного агента, чтобы
  владелец всегда видел, что именно «сейчас в работе».
- В In Review не копить больше 5: если очередь больше — разобрать её (QA/принятие)
  и вернуть актуальное состояние в описание задач.
- Описание задачи обновляется на смене In Progress → In Review
  (что сделано / что осталось), чтобы трекер видел современный статус.
- Стикер/приоритет не менять без поручения владельца.

## Как (MCP)

Перенос = `tools.yougile.manage_tasks` с объектом: `{id, title: null,
columnId: <id целевой колонки>, description: null, color: "primary",
complete: null, archived: null}`. id — технический UUID из `get_task_data`
(человеческий id REW-N годится для чтения, но для записи храните полный).
Прочитать текущее состояние задачи — `yougile.get_task_data({ id: "REW-N" })`.

## Ворота и DoD слоя 2 (product_docs — см. `product_docs.md`)

1. **Ворота.** Задачи Dev/QA не берутся в работу без пройденных ворот аналитики:
   карточка БФ в статусе `planned` (`product_docs/01_business_functions/BF-NN_*/README.md`)
   + утверждённые требования (пакет 5.5) + запись в трекере. Ворота не пройдены —
   назови причину и верни задачу аналитику; спецификацию сам не правь.
2. **Задачи привязываются к слою 2.** Задача ссылается на `BF-NN`, ID требований
   (FR-041, UC-ROS, …) и страницы компонентов, а не на файлы `output/reports/`.
3. **DoD перед Done.** Задача, меняющая требования или поведение, не переводится
   в Done, пока слой 2 синхронизирован: обновлены карточка БФ, страница компонента
   (`02_system_components/…`), строка `INDEX.md`, и `python product_docs/check_product_docs.py`
   выполняется без ошибок. Синхронизацию делает **аналитик** — Dev/QA/DevOps
   документацию не правят, а описывают изменение поведения комментарием к задаче.

## Эпики: задачи ↔ бизнес-функции (правило от 09.11.2026)

1. **Эпик = бизнес-функция.** Когда БФ проходит Гейт 2 (пакет 5.5 принят, карточка BF-NN в
   `planned`), создаётся задача-эпик вида «BF-NN: <название>». Все задачи функции (BA, Arch,
   UX, Dev, QA, DevOps, задачи системного анализа/интеграций) — подзадачи этого эпика.
2. **До появления БФ.** Работы BA ведутся в эпиках аналитики: стартовая фаза проекта —
   «Аналитика: <объём>», новая функция в живом проекте — в отдельном эпике «BF-NN: аналитика»
   (создаётся раньше BF-карточки). Работы без БФ (инфраструктура/ops) — эпик
   «Инфраструктура/ops».
3. **Связи.** Задачи ссылаются на BF-NN и ID требований; в карточке BF-NN хранится перечень
   задач эпика — обновляет **аналитик** при синхронизации слоя 2 (Arch создаёт задачи в
   трекере, но редактирует только трекер, не карточку).
4. **Эпик не двигается за подзадачами.** Он переходит: `In Progress` — при старте первой
   подзадачи; `Done` — когда все подзадачи Done и приняты (DoD слоя 2 закрыт).
5. **CR внутри эпика.** Если CR открыт, пока эпик не закрыт, — задачи CR посещают тот же
   эпик; эпик нельзя переводить в Done, пока CR-задачи не закрыты.
6. **CR-эпик после Done.** Для реализованной БФ будущие CR оформляются новым эпиком
   «BF-NN (CR-NNN)» (крупное изменение — «BF-NN v2»); цепочка BA→Dev→QA повторяется;
   документация ведётся в той же карточке BF-NN (растут версии).
7. **Название задач.** Единый формат: «[BF-NN] Pre.Dev-NN: <роль/тип — суть>»
   (для CR-эпиков — «[BF-NN / CR-NNN] …»). Вне YouGile формат читается так же.
8. **Адаптация к трекеру.** Правила описаны на примере YouGile (задача-эпик + подзадачи);
   в других трекерах — эпик/фича/milestone с привязанными задачами, механика та же.
