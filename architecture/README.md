## Architecture Blueprint (единые имена)

| Имя | Описание | Технология |
|---|---|---|
| `web` | SPA: Потребности / Сотрудники / Резюме / Настройки | React + TypeScript, статика под nginx |
| `proxy` | Единая точка входа, TLS внутри контура | nginx |
| `api` | Бэкенд REST, LDAP-вход, бизнес-логика | Python 3.12, FastAPI |
| `worker` | Фоновый опрос Jira, задачи LLM, извлечение текста CV (тот же код, другой процесс) | Python, APScheduler |
| `jira_client` | Модуль доступа к Jira (порт + адаптеры авторизации) | Python (пишет OpenCode) |
| `llm_gateway` | Модуль: провайдеры, обезличивание, предпросмотр, таймаут | Python |
| `app_db` | Пользователи, сессии, кэш Jira, настройки, зашифрованные токены и ключи | PostgreSQL 16, БД `app_db` |
| `cv_db` | Сотрудники, файлы CV, текст, навыки, архив версий | PostgreSQL 16, БД `cv_db`, отдельная роль |

Ключевые решения: модульный монолит (ADR-001); Jira через опрос и кэш (ADR-004);
поэтапно по OPT-001: этап 1 чтение, этап 2 запись; доступ сессионной cookie (ADR-005); один шлюз LLM (ADR-007).

## Открытые вопросы

1. Параметры LDAP-сервера (хост, base DN, формат логина, TLS) не названы: разработка идёт с тестовым LDAP-контейнером, конфиг через env; реальные значения нужны к выкладке на ВМ.
2. Срок выдачи и параметры ВМ: заявка подаётся после локального тестирования MVP; вне критического пути разработки.
3. Срок жизни сессии Jira не измерен (определяет частоту повторного ввода пароля); замеряется на локальном стенде.
4. Какое поле эпика потребности каноническое: `customfield_10101` (Epic Link) или `customfield_11032` («Epic link потребности») — вопрос владельцу процесса; клиент пока использует 10101 и Agile API.

Закрыто 05.10: пароль Jira совпадает с LDAP (сессия Jira создаётся при входе).

## Кандидаты в CR 5.4 (спецификацию сам не правлю; решение аналитика и владельца)

- FR-025 и UC-005: формулировки про OAuth 1.0a/Application Link и «сохранение access token» не соответствуют принятому способу (сессионная cookie, повторный ввод пароля без хранения). Предложение из отчёта пробы: «от имени пользователя через сессионный токен Jira; при 401 повторная авторизация без потери введённых данных».
- FR-026: REST не объявляет обязательный комментарий перехода (переход 171 отклонён без него); требование «НЕ ДОЛЖНА вводить собственных ограничений» уточнить: смена статуса сопровождается комментарием (`update.comment.add`).
- FR-028: фоновый опрос идёт сессией активного пользователя и приостанавливается без активных сессий; убрать противоречие с FR-025 (этап 1 «Basic/сервисная учётка»).
- FR-011: поле «Причина отсутствия кандидата» по схеме необязательно, но передавать его нужно всегда.
- Условия 5.5 по FR-008, FR-025, FR-026, UC-005: проба даёт доказательство (комментарии 519001/519002, вложение 328390, переход 171 в ANALYTICS-5871, оставлено по решению владельца) для `close_approval_condition`.
- NFR-005: технические логи без ПДн и секретов допустимы, аудит-таблицы нет (подтвердить).
- NFR-009: 10 с как лимит на каждый вызов Jira (клиент так и реализован, повторы выключены).
- Каноническое поле эпика: `customfield_11032` или `10101` (вопрос 4).
