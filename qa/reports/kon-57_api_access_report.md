## 4. Приёмка NFR-006 (четыре критерия)

После сценариев (успешный вход, отказ, отказ Jira, повторный ввод пароля Jira, logout) выполнены `qa/nfr006_check.py` и
дополняющие проверки. Канарейки: пароли всех тестовых пользователей, пароль повторного входа Jira, неверные пароли,
префикс токена фейк Jira `fake-session-`, ключи шифрования стенда.

| # | Критерий | Проверка | Результат |
|---|----------|----------|-----------|
| 1 | Нет открытых токенов в БД | `--db-url`: `app.secret_store` 5 строк `jira_session`, `key_id=k1`, nonce 12 байт, шифртекст; нет `fake-session-` | **пройдено** |
| 2 | Ключ не в коде/репозитории | `--repo` (после добавления известной фикстуры, см. ниже) + `git grep -F` значений `APP_ENC_KEY` и `JIRA_TOKEN_ENCRYPTION_KEY` стенда + нет `.env` в индексе | **пройдено** |
| 3 | Пароль нигде не сохранён | текстовые колонки (`--db-url`) + `pg_dump app_db` (текст и hex bytea) без канареек | **пройдено** |
| 4 | Логи без секретов | логи 6 контейнеров стенда (8858 строк): `--logs-file` + поиск канареек; контрольная проба с подброшенным паролем даёт код 1 | **пройдено** |

Оговорки:
- `--repo` сначала дал 1 срабатывание: `backend/tests/unit/test_auth.py: PASSWORD = "Pw-Zq9!unit-test-7731"`. Это вымышленный пароль
  фейкового LDAP в unit-тесте Dev, не секрет; внесён в `KNOWN_FIXTURES` скрипта (ручная проверка). Рекомендация Dev: давать таким константам
  префикс `FAKE_`, тогда исключение не нужно.
- Скрипт `--selftest` (негативная проба): пройден, на «грязных» данных находит нарушения.
- Реальные Jira и LDAP не использовались: токен Jira фейковый; формат реального `JSESSIONID` скрипт ловит по шаблону, но на живой Jira не прогонялся.

## 6. Наблюдения (не баги)

- На стенде после пересоздания контейнера `api` прокси `nginx` (без `resolver`) держит старый IP и отвечает 502, пока его не перезапустить
  (`docker restart ...proxy`). Для KON-49 (деплой) учесть: обновлять api и proxy вместе либо задать `resolver` с переменной в `proxy_pass`.
- Неверный пароль на тестовом LDAP занимает около 1 с (задержка отказа bind на стороне OpenLDAP); успешный вход - 0,05 с (NFR времени входа не задан).
- В `docker-compose.yml` корня стенд по умолчанию читает `SESSION_COOKIE_SECURE=true`; для http-стенда нужно `false` (QA-стенд задаёт сам).
